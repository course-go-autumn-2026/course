# Локальное окружение

Всё, что нужно для работы, поднимает `tripgoctl` — утилита курса. Сервис вы
запускаете сами, а `tripgoctl` даёт то, к чему сервис обращается: бд, брокер,
коллектор телеметрии, заглушку пушей.

Как поставить утилиту и что делать, если что-то не поднялось, — в
[README репозитория `course-infra`](https://github.com/course-go-autumn-2026/course-infra).
В этом файле — состав окружения и откуда брать адреса.

## 1. Как поднять

В каждой работе лежит `environment.toml` — в нём написано, какие компоненты
нужны. Скопируйте его в корень своего репозитория и запустите окружение:

```bash
tripgoctl cluster start          # один раз на машине
tripgoctl environment start      # поднять компоненты этой работы
tripgoctl connect                # адреса и ссылки на веб-интерфейсы
```

`environment start` создаёт в корне файл `.env` с адресами поднятых компонентов.
Оттуда их и берём: в коде и в командах не хардкодим ни хосты, ни порты. Порт у
каждой работы свой, поэтому окружения разных работ не конфликтуют.

`.env` и служебный каталог `.tripgo/` добавьте в `.gitignore`: это локальные
файлы, в репозиторий они не идут.

## 2. Из чего состоит

| Компонент | Что даёт | С какой работы |
|---|---|---|
| PostgreSQL | хранилище поездок и маршрутов | 1 |
| OpenTelemetry Collector | принимает метрики и трейсы по OTLP | 2 |
| Prometheus, Grafana, Jaeger | стоят за коллектором, там смотрим метрики и трейсы | 2 |
| Push Service | заглушка, принимает команды на пуш | 3 |
| Redpanda | брокер, совместимый с Kafka | 4 |
| Redpanda Console | веб-интерфейс: смотреть топики и класть сообщения руками | 4 |

Компоненты подключаются по мере необходимости: в работе 1 поднимается только
PostgreSQL, к работе 4 — всё перечисленное.

## 3. Телеметрия идёт через коллектор

В коде сервиса нет ни Prometheus, ни Jaeger. Есть OpenTelemetry SDK, который
отправляет метрики и трейсы по OTLP в коллектор, а тот уже раскладывает их по
бэкендам:

```
ваш сервис ──OTLP──► OTel Collector ──► Prometheus ──► Grafana
                            └──────────► Jaeger
```

Так инфраструктура может поменять бэкенды, добавить атрибуты или отрезать лишнее,
не трогая код сервисов. К этой модели сейчас переходит индустрия и, в частности,
Авито.

Переменные берём стандартные для OpenTelemetry, свои имена не выдумываем:

```
OTEL_SERVICE_NAME=trip-service
OTEL_EXPORTER_OTLP_ENDPOINT=<из .env>
OTEL_RESOURCE_ATTRIBUTES=service.namespace=tripgo,deployment.environment=local
```

Если коллектор недоступен, сервис должен работать дальше и не падать: телеметрия
не является критичной зависимостью.

## 4. Push Service

Заглушка. Принимает команду отправить уведомление, реальные пуши не шлёт, только
отвечает и пишет в лог. Живёт вместе с остальным окружением, писать её не нужно.
Логи смотрим через `tripgoctl environment logs push-service`.

В работе 3 ходим в неё по HTTP, в работе 4 переводим на gRPC. Контракты:
[`push-service.openapi.yaml`](../contracts/openapi/push-service.openapi.yaml) и
[`push.proto`](../contracts/proto/push/v1/push.proto).

Коды ответов HTTP: `202` — команда принята, `400` — некорректный запрос, `429` —
превышен лимит, в заголовке `Retry-After` указано, когда повторять, `503` —
временная недоступность. В gRPC им соответствуют `INVALID_ARGUMENT`,
`RESOURCE_EXHAUSTED` и `UNAVAILABLE`.

### Управляемые отказы

Заглушку можно заставить отвечать медленно и с ошибками — это нужно в работе 5,
чтобы было на чём проверять backoff и rate limiter. Настраивается на лету, адрес
админки лежит в `.env` в переменной `PUSH_ADMIN_URL`:

```bash
curl -fsS -X POST "$PUSH_ADMIN_URL/admin/behaviour" \
  -H 'content-type: application/json' \
  -d '{"fail_rate":0.5,"latency_ms":2000}'
```

| Параметр | Что делает |
|---|---|
| `fail_rate` | доля ответов `503` и `UNAVAILABLE`, от `0.0` до `1.0` |
| `latency_ms` | искусственная задержка ответа |
| `rate_limit_rps` | лимит, выше которого отвечает `429` и `RESOURCE_EXHAUSTED` |

Сервис должен переживать любую комбинацию этих настроек: не залипать, не копить
горутины, не терять поездки. После проверки настройки сбрасываем обратно в нули.

## 5. Топики

Создаются заранее, руками заводить не надо.

| Топик | Партиций | Кто пишет | Кто читает |
|---|---|---|---|
| `trip.events.v1` | 3 | ваш сервис | внешние потребители |
| `trip.commands.v1` | 3 | вы руками через Console | ваш сервис |
| `trip.commands.v1.dlq` | 1 | ваш сервис | человек |

Адрес брокера и ссылка на Console — в выводе `tripgoctl connect`. Через Console
кладём команды в топик и смотрим, что уехало в события и в DLQ.

## 6. Проверить, что окружение живо

```bash
tripgoctl connect                                   # адреса и ссылки
tripgoctl environment logs push-service             # логи заглушки
psql "$DATABASE_URL" -c 'select 1'
```

Ссылки на Jaeger, Grafana, Prometheus и Console печатает `tripgoctl connect` —
открывайте оттуда, а не по запомненным портам.
