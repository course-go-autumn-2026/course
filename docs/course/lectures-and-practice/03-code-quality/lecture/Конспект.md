# Качество кода в Go

Для проверки кода в Go используется пакет `testing`. С его помощью можно вызвать функцию, сравнить результат с ожидаемым и сообщить об ошибке. Для поиска подозрительных конструкций в исходниках применяются линтеры, а для проверки одновременного доступа к памяти — детектор гонок.

Разберем работу этих инструментов на примере каталога фильмов и бронирования билетов. Сначала напишем тест для одной функции. Затем проверим HTTP-запросы, добавим моки и разберем интеграционные тесты с PostgreSQL. Также рассмотрим TDD, рефакторинг и нагрузочное тестирование.

Выполняйте команды из корня Go-модуля, если рядом с примером не указан другой каталог.

Полные файлы приведены вместе с `package` и импортами. Короткие фрагменты дополняют предыдущий код. Версии зависимостей сохраняются в `go.mod` и `go.sum`, а версии инструментов — в настройках проекта и CI.

## 1. Создание теста с `testing`

Создадим функцию `ParseFilmID`. Она принимает строку и возвращает положительное число типа `int64`. Для пустой строки, текста, нуля, отрицательного числа или переполнения функция должна вернуть `ErrInvalidID`.

Добавим файл `internal/film/id.go`:

```go
package film

import (
	"errors"
	"strconv"
)

var ErrInvalidID = errors.New("invalid film id")

func ParseFilmID(raw string) (int64, error) {
	id, err := strconv.ParseInt(raw, 10, 64)
	if err != nil || id <= 0 {
		return 0, ErrInvalidID
	}
	return id, nil
}
```

`strconv.ParseInt` преобразует строку в число. Если преобразование завершилось ошибкой или число не больше нуля, функция возвращает `0` и `ErrInvalidID`. Для строки `"42"` результатом будут `42` и `nil`.

Теперь проверим результат для строки `"42"`. Для этого нужно выполнить три шага:

1. Создать файл с суффиксом `_test.go`.
2. Добавить функцию `TestParseFilmID`, которая принимает `t *testing.T`.
3. Вызвать `ParseFilmID` и сравнить полученные значения с ожидаемыми.

Имя тестовой функции начинается с `Test`. Следующий за ним символ не должен быть строчной буквой.

Создадим рядом файл `internal/film/id_test.go`:

```go
package film

import "testing"

func TestParseFilmID(t *testing.T) {
	got, err := ParseFilmID("42")
	if err != nil {
		t.Fatalf("ParseFilmID returned an error: %v", err)
	}
	if got != 42 {
		t.Errorf("ParseFilmID = %d, want 42", got)
	}
}
```

В переменную `got` записывается полученный ID, а в `err` — ошибка. Для строки `"42"` ожидаются значения `42` и `nil`.

Если функция вернула ошибку, `t.Fatalf` завершит тест. Если ошибки нет, но ID отличается от `42`, `t.Errorf` отметит тест как упавший. Сообщение покажет фактическое и ожидаемое значения.

Сначала мы подготовили входную строку, затем вызвали функцию и проверили результат. Такая последовательность называется Arrange, Act, Assert: подготовка, действие, проверка.

Пакет `testing` предоставляет следующие методы:

| Метод | Описание |
|---|---|
| `t.Error`, `t.Errorf` | Отмечают ошибку и продолжают выполнение теста |
| `t.Fatal`, `t.Fatalf` | Отмечают ошибку и завершают текущий тест |
| `t.Log`, `t.Logf` | Выводят сообщение при провале теста или запуске с `-v` |
| `t.Run` | Запускает именованный подтест |
| `t.Helper` | Помечает вспомогательную функцию: при ошибке будет показано место ее вызова |
| `t.Cleanup` | Регистрирует очистку после теста и его подтестов |
| `t.TempDir` | Создает временный каталог с автоматическим удалением |

`Fatalf` подходит, когда продолжать проверку нельзя: например, не удалось подготовить данные. Через `Errorf` можно проверить несколько независимых полей и увидеть все различия за один запуск.

Обратите внимание: `Fatal` и `Fatalf` вызываются из горутины теста. Ошибку из рабочей горутины можно передать по каналу и проверить после получения. Подробнее — в [документации `testing`](https://pkg.go.dev/testing).

### Запуск тестов

Для запуска используется команда `go test`:

```bash
go test ./...                              # все пакеты текущего модуля
go test -v ./internal/film                  # подробный вывод одного пакета
go test -run '^TestParseFilmID$' ./internal/film
go test -count=1 ./...                      # выполнить заново, без кэша результатов
go test -timeout=30s ./...                  # ограничить длительность тестового бинарника
```

Первая команда запускает тесты всех пакетов модуля. Без `./...` проверяется только пакет текущего каталога.

Если в выводе появляется `(cached)`, Go использовал сохраненный результат успешного запуска. Чтобы выполнить тесты заново, добавьте `-count=1`. Это удобно при проверке внешнего окружения, например после изменения данных в тестовой БД.

Флаг `-timeout` ограничивает время работы тестового бинарника пакета. Отдельный тайм-аут на каждую функцию он не устанавливает. Правила запуска приведены в [документации `go test`](https://pkg.go.dev/cmd/go#hdr-Test_packages).

В примере тест находится в пакете `film`, поэтому ему доступны и неэкспортируемые имена. Можно также использовать пакет `film_test`. Тогда основной пакет нужно импортировать, и тест будет обращаться только к его публичному API.

## 2. Табличные тесты

### Создание табличного теста

Вернемся к `ParseFilmID`. Для нее уже есть проверка строки `"42"`. Добавим ноль, отрицательное число, пустую строку, текст и переполнение.

Чтобы не писать отдельную функцию для каждого случая, сохраним входные данные и ожидаемые результаты в слайсе структур. Затем переберем его в цикле. Такой подход называется table-driven test, или табличный тест.

Создадим файл `internal/film/id_table_test.go`:

```go
package film

import (
	"errors"
	"testing"
)

func TestParseFilmID_Table(t *testing.T) {
	tests := []struct {
		name    string
		raw     string
		want    int64
		wantErr error
	}{
		{name: "positive", raw: "42", want: 42},
		{name: "smallest", raw: "1", want: 1},
		{name: "max int64", raw: "9223372036854775807", want: 9223372036854775807},
		{name: "empty", raw: "", wantErr: ErrInvalidID},
		{name: "zero", raw: "0", wantErr: ErrInvalidID},
		{name: "negative", raw: "-1", wantErr: ErrInvalidID},
		{name: "text", raw: "film", wantErr: ErrInvalidID},
		{name: "overflow", raw: "9223372036854775808", wantErr: ErrInvalidID},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := ParseFilmID(tt.raw)
			if !errors.Is(err, tt.wantErr) {
				t.Fatalf("error = %v, want %v", err, tt.wantErr)
			}
			if got != tt.want {
				t.Errorf("ParseFilmID(%q) = %d, want %d", tt.raw, got, tt.want)
			}
		})
	}
}
```

Таблица готова. В поле `raw` хранится входная строка, в `want` — ожидаемый ID, в `wantErr` — ожидаемая ошибка.

Обратите внимание на случай `empty`: для него указана ошибка, а поле `want` пропущено. Оно получит нулевое значение, поэтому тест будет ожидать ID `0`.

Метод `t.Run` создает отдельный подтест с именем из поля `name`. Поэтому при провале будет видно, какой случай не прошел. Например, `overflow` указывает на проверку переполнения.

Чтобы запустить только этот подтест, используйте:

```bash
go test -v -run '^TestParseFilmID_Table$/^overflow$' ./internal/film
```

Вызов `errors.Is(err, tt.wantErr)` сравнивает ошибки. Он работает и с ошибкой, обернутой через `%w`. Если `wantErr` равен `nil`, проверка проходит только при отсутствии ошибки.

Сравнение через `err.Error()` проверяет текст сообщения. Для доменной ошибки обычно удобнее `errors.Is`: изменение формулировки не сломает тест. Если нужно проверить тип ошибки, используется `errors.As`.

После проверки ошибки сравниваются `got` и `want`. Если функция вернет нужную ошибку вместе с ненулевым ID, тест тоже упадет.

Таким же способом можно проверять списки: сравнивать элементы, их порядок и отсутствие повторов. Если вызывающий код различает `nil` и пустой слайс, добавьте проверку этого различия.

### Проверки с `testify`

Для сравнения структур, слайсов и JSON можно использовать библиотеку `testify`. Она сокращает код проверок. Установим ее:

```bash
go get github.com/stretchr/testify
```

Добавим импорты `github.com/stretchr/testify/assert` и `github.com/stretchr/testify/require`. Теперь проверку ID можно записать следующим образом:

```go
got, err := ParseFilmID("42")
require.NoError(t, err)
assert.Equal(t, int64(42), got)

_, err = ParseFilmID("0")
require.ErrorIs(t, err, ErrInvalidID)
```

`require.NoError` завершит тест, если функция вернула ошибку. После него `assert.Equal` сравнит ожидаемый ID с полученным. Если сравнение не пройдет, тест продолжится, но его результат будет неуспешным.

В `Equal` сначала передается ожидаемое значение, затем фактическое. В примере используется `int64(42)`: для этой проверки типы `int` и `int64` различаются.

Методы `require`, как и `t.Fatal`, вызываются из горутины теста. Список проверок приведен в [документации `require`](https://pkg.go.dev/github.com/stretchr/testify/require).

Для проверки ожидаемой паники есть `assert.Panics(t, func() { ... })`. Используйте такую проверку только тогда, когда паника является частью контракта. В обычном прикладном и библиотечном коде ожидаемые ошибки лучше возвращать через `error`.

В следующих примерах используем `require` для проверок, после провала которых тест нужно остановить, и `assert` для остальных сравнений.

## 3. Тестирование HTTP-кода с `httptest`

Для тестирования HTTP-кода используется стандартный пакет `httptest`. Он позволяет создать запрос и получить ответ обработчика прямо в тесте. Также с его помощью можно запустить локальный сервер для проверки HTTP-клиента.

В ответе проверяются статус, заголовки и тело. Например, статус `200` сам по себе еще не означает, что обработчик вернул нужный фильм.

### Проверка обработчика

Создадим обработчик, который получает ID из query-параметра `id`. При допустимом значении он возвращает JSON, при ошибке — статус `400`.

Файл `internal/film/handler.go`:

```go
package film

import (
	"encoding/json"
	"net/http"
)

func ValidateFilmIDHandler(w http.ResponseWriter, r *http.Request) {
	id, err := ParseFilmID(r.URL.Query().Get("id"))
	if err != nil {
		http.Error(w, "invalid film id", http.StatusBadRequest)
		return
	}

	body, err := json.Marshal(struct {
		ID int64 `json:"id"`
	}{ID: id})
	if err != nil {
		http.Error(w, "encode response", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	if _, err := w.Write(body); err != nil {
		// Ответ уже начат. Повторный http.Error не исправит ошибку записи.
		return
	}
}
```

Для запроса `/films/validate?id=42` обработчик вернет тело `{"id":42}` и заголовок `Content-Type: application/json`. При неверном ID вызовется `http.Error`, после чего обработчик завершится.

Сначала JSON формируется через `json.Marshal`, затем записывается в ответ. Если ошибка возникла уже при записи, повторный `http.Error` не исправит начатый ответ. В сервисе такую ошибку можно записать в лог или метрику.

Проверим три варианта запроса: правильный ID, отсутствие параметра и текст вместо числа. В каждом случае нужно создать запрос, вызвать обработчик и прочитать ответ.

Добавим файл `internal/film/handler_test.go`:

```go
package film

import (
	"encoding/json"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/require"
)

func TestValidateFilmIDHandler(t *testing.T) {
	tests := []struct {
		name       string
		target     string
		wantStatus int
		wantID     int64
	}{
		{"valid", "/films/validate?id=42", http.StatusOK, 42},
		{"missing", "/films/validate", http.StatusBadRequest, 0},
		{"invalid", "/films/validate?id=abc", http.StatusBadRequest, 0},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			req := httptest.NewRequest(http.MethodGet, tt.target, nil)
			recorder := httptest.NewRecorder()

			ValidateFilmIDHandler(recorder, req)

			resp := recorder.Result()
			defer resp.Body.Close()
			require.Equal(t, tt.wantStatus, resp.StatusCode)

			if tt.wantStatus == http.StatusOK {
				assert.Equal(t, "application/json", resp.Header.Get("Content-Type"))
				var body struct {
					ID int64 `json:"id"`
				}
				require.NoError(t, json.NewDecoder(resp.Body).Decode(&body))
				assert.Equal(t, tt.wantID, body.ID)
				return
			}

			body, err := io.ReadAll(resp.Body)
			require.NoError(t, err)
			assert.Equal(t, "invalid film id", strings.TrimSpace(string(body)))
		})
	}
}
```

`httptest.NewRequest` создает серверный запрос. `httptest.NewRecorder` возвращает объект, который реализует `http.ResponseWriter` и сохраняет записанный ответ.

Теперь передадим оба объекта в `ValidateFilmIDHandler(recorder, req)`. Обработчик запишет ответ в `recorder`; TCP-соединение для этого не требуется.

Чтобы прочитать ответ, используется метод `recorder.Result()`. Он возвращает `*http.Response` со статусом, заголовками и телом. Подробнее — в [документации `httptest`](https://pkg.go.dev/net/http/httptest).

Для успешного ответа тест декодирует JSON и проверяет поле `id`. Так пробелы и порядок полей не влияют на результат. Для ошибочного ответа сравнивается текст сообщения.

Обратите внимание: прямой вызов функции не проверяет маршрутизатор и middleware. Чтобы проверить HTTP-метод, авторизацию или параметры через `r.PathValue`, запрос нужно передать маршрутизатору. Например:

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /films/validate", ValidateFilmIDHandler)
mux.ServeHTTP(recorder, req)
```

Теперь запрос проходит через `ServeMux`. В таком тесте можно проверить `POST` на маршруте для `GET`, неизвестный путь и подключенные middleware.

### Проверка HTTP-клиента

Аналогично можно проверить HTTP-клиент: `httptest.NewServer` запускает локальный сервер, адрес которого передается клиенту вместо адреса внешнего API. Задавая ответы сервера, можно проверить, что клиент правильно отправляет запросы, читает данные и обрабатывает ошибки.

## 4. Моки интерфейсов с `gomock`

Теперь проверим, как сервис обрабатывает ошибку репозитория. Для этого передадим в сервис тестовый объект и настроим его так, чтобы при чтении фильма он возвращал ошибку.

### Создание интерфейса

Service будет получать repository через конструктор. Для этого опишем интерфейс с методом `FindByID`.

Добавим файл `internal/film/service.go`:

```go
package film

import (
	"context"
	"errors"
	"fmt"
)

//go:generate go run go.uber.org/mock/mockgen@v0.5.0 -source=service.go -destination=repository_mock_test.go -package=film

var ErrFilmNotFound = errors.New("film not found")

type Film struct {
	ID    int64
	Title string
}

type Repository interface {
	FindByID(ctx context.Context, id int64) (Film, error)
}

type Service struct {
	repo Repository
}

func NewService(repo Repository) *Service {
	return &Service{repo: repo}
}

func (s *Service) Title(ctx context.Context, id int64) (string, error) {
	if id <= 0 {
		return "", ErrInvalidID
	}
	film, err := s.repo.FindByID(ctx, id)
	if err != nil {
		return "", fmt.Errorf("get film title: %w", err)
	}
	return film.Title, nil
}
```

`NewService` принимает любой объект, который реализует `Repository`. В приложении это будет репозиторий PostgreSQL, а в тесте — сгенерированный mock.

Метод `Title` сначала проверяет ID. При неверном значении он сразу возвращает ошибку. Для положительного ID вызывается `FindByID`, после чего возвращается название фильма или ошибка repository, обернутая через `%w`.

Интерфейс находится рядом с service и содержит только нужный ему метод. Описывать интерфейс для каждой структуры не требуется: здесь он нужен, чтобы передавать разные реализации зависимости.

### Создание мока вручную

Для небольшого интерфейса тестовую реализацию можно написать без генератора. Опишем структуру с функцией, которую тест настроит для конкретного сценария:

```go
type repositoryMock struct {
	findByID func(ctx context.Context, id int64) (Film, error)
}

func (m *repositoryMock) FindByID(ctx context.Context, id int64) (Film, error) {
	return m.findByID(ctx, id)
}
```

Теперь тест может задать ответ зависимости и одновременно проверить аргумент вызова:

```go
func TestService_TitleWithManualMock(t *testing.T) {
	repo := &repositoryMock{
		findByID: func(_ context.Context, id int64) (Film, error) {
			require.Equal(t, int64(42), id)
			return Film{ID: 42, Title: "Arrival"}, nil
		},
	}

	got, err := NewService(repo).Title(context.Background(), 42)

	require.NoError(t, err)
	assert.Equal(t, "Arrival", got)
}
```

Ручная реализация удобна, пока у интерфейса один-два метода. Для большого интерфейса придется самостоятельно поддерживать все методы, хранить историю вызовов и проверять их количество. Эту повторяющуюся работу выполняет генератор моков.

### Генерация мока

Для генерации используется `mockgen` из модуля `go.uber.org/mock`. Генератор и библиотеку `gomock` нужно брать из одной ветки проекта. Параметры инструмента приведены в [репозитории GoMock](https://github.com/uber-go/mock).

Установим выбранную версию библиотеки и запустим генерацию:

```bash
go get go.uber.org/mock@v0.5.0
go generate ./internal/film
go mod tidy
go test ./internal/film
```

Для учебного примера зафиксирована версия `v0.5.0`. Это не обозначение последнего релиза. При обновлении версия генератора меняется вместе с версией библиотеки.

Команда `go generate` находит директиву в `service.go` и запускает указанный в ней `go run`. Отдельно устанавливать бинарник `mockgen` в `PATH` не нужно.

В директиве используются следующие параметры:

| Параметр | Назначение |
|---|---|
| `-source=service.go` | Файл с интерфейсом |
| `-destination=repository_mock_test.go` | Файл для сгенерированного кода |
| `-package=film` | Имя пакета мока |

Команда выполняется из каталога `service.go`, поэтому пути считаются относительно `internal/film`. После генерации структура файлов будет следующей:

```text
internal/film/
    id.go
    service.go
    service_test.go
    repository_mock_test.go    <- сгенерирован mockgen
```

Файл `repository_mock_test.go` содержит реализацию мока. Благодаря суффиксу `_test.go` он попадет только в тестовую сборку пакета `film`.

Если мок нужен в тестах других пакетов, его можно вынести в отдельный пакет и генерировать в обычный `.go`-файл. При этом нужно проверить, что импорты не образуют цикл. Изменения в сгенерированный код вносятся повторным запуском генератора.

Обратите внимание: `go test` и `go build` не запускают `go generate`.
### Использование мока в тесте
Проверим получение названия, отсутствие фильма, ошибку хранилища и неверный ID. Для каждого случая создадим свой mock и зададим ответ repository.

Файл `internal/film/service_test.go`:

```go
package film

import (
	"context"
	"errors"
	"testing"

	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/require"
	"go.uber.org/mock/gomock"
)

func TestService_Title(t *testing.T) {
	errStorage := errors.New("storage unavailable")
	tests := []struct {
		name     string
		id       int64
		repoFilm Film
		repoErr  error
		want     string
		wantErr  error
		wantCall bool
	}{
		{
			name: "found", id: 42,
			repoFilm: Film{ID: 42, Title: "Arrival"},
			want:     "Arrival", wantCall: true,
		},
		{
			name: "not found", id: 42,
			repoErr: ErrFilmNotFound, wantErr: ErrFilmNotFound, wantCall: true,
		},
		{
			name: "storage failure", id: 42,
			repoErr: errStorage, wantErr: errStorage, wantCall: true,
		},
		{name: "invalid id", id: 0, wantErr: ErrInvalidID},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			ctrl := gomock.NewController(t)
			repo := NewMockRepository(ctrl)
			ctx := context.Background()

			if tt.wantCall {
				repo.EXPECT().
					FindByID(gomock.Any(), tt.id).
					Return(tt.repoFilm, tt.repoErr).
					Times(1)
			}

			service := NewService(repo)
			got, err := service.Title(ctx, tt.id)
			require.ErrorIs(t, err, tt.wantErr)
			assert.Equal(t, tt.want, got)
		})
	}
}
```

`require.ErrorIs` проверяет ожидаемую ошибку, в том числе обернутую через `%w`. Если `tt.wantErr` равен `nil`, проверка требует отсутствия ошибки. Затем `assert.Equal` сравнивает название фильма.

Сначала `gomock.NewController(t)` создает контроллер для текущего подтеста. Затем `NewMockRepository(ctrl)` возвращает мок репозитория.

Настройка вызова состоит из нескольких частей:

| Вызов | Назначение |
|---|---|
| `EXPECT()` | Начинает описание ожидаемого обращения |
| `FindByID(gomock.Any(), tt.id)` | Указывает метод и ожидаемый ID |
| `Return(tt.repoFilm, tt.repoErr)` | Задает возвращаемый фильм и ошибку |
| `Times(1)` | Требует ровно один вызов |

Если сервис передаст другой ID, вызовет метод повторно или вообще не обратится к нему, тест упадет.

В случае `invalid id` ожидание не добавляется. Сервис должен сразу вернуть `ErrInvalidID`. Любое обращение к репозиторию в этом случае приведет к провалу теста.

В конце подтеста контроллер проверит, выполнились ли ожидания. Мы передали ему `t`, поэтому эта проверка уже зарегистрирована через cleanup. Добавлять `defer ctrl.Finish()` не требуется.

По умолчанию разные ожидаемые вызовы могут происходить в любом порядке. Для проверки последовательности используются `gomock.InOrder` и `After`. Подробнее — в [API `gomock`](https://pkg.go.dev/go.uber.org/mock/gomock).

`gomock.Any()` в примере означает, что содержимое контекста не проверяется. Если контракт требует передать отмену или deadline, нужна отдельная проверка: например, получить контекст в `DoAndReturn` и проверить его состояние. `AnyTimes()` допускает и ноль вызовов; такое ожидание не доказывает, что зависимость использовали.

Моки помогают проверить решения service, но не подтверждают правильность SQL. Если мок возвращает фильм, хотя реальная таблица не содержит нужного столбца, все unit-тесты останутся зелеными. Этот пробел закрывает интеграционный тест.

### Когда моки мешают и как настроить ожидания

Тест становится хрупким, если закрепляет детали, которые не входят в контракт. Например, service читает два фильма по ID. После рефакторинга он может читать их в обратном порядке или параллельно, сохраняя правильный результат. Если тест без необходимости потребовал строгую последовательность, он упадет при допустимом изменении.

Настроим мок так, чтобы он допускал оба порядка чтения. При этом сохраним проверку ID и количества обращений. Эти настройки задаются независимо друг от друга.

В gomock порядок разных ожидаемых вызовов по умолчанию свободный. Следующие настройки разрешают получить фильм `42` до фильма `7` или наоборот; каждое ожидание должно выполниться ровно один раз:

```go
repo.EXPECT().
	FindByID(gomock.Any(), int64(42)).
	Return(Film{ID: 42, Title: "Arrival"}, nil)

repo.EXPECT().
	FindByID(gomock.Any(), int64(7)).
	Return(Film{ID: 7, Title: "Solaris"}, nil)
```

После такой настройки нужно вызвать метод сервиса, который читает два фильма, и проверить его результат. Мок примет чтение `42`, затем `7`, или наоборот.

Чтобы потребовать определенную последовательность, добавьте `gomock.InOrder` или `After`. Например, это понадобится при проверке того, что подтверждение отправляется после сохранения бронирования.

Количество вызовов настраивается независимо. Если в конкретном тесте важно только получить заданный ответ при чтении фильма, можно разрешить любое число обращений, включая ноль:

```go
repo.EXPECT().
	FindByID(gomock.Any(), int64(42)).
	Return(Film{ID: 42, Title: "Arrival"}, nil).
	AnyTimes()
```

Теперь сервис может прочитать фильм несколько раз или получить его из кэша, вообще не обращаясь к репозиторию. При каждом обращении ID по-прежнему должен быть равен `42`. Вызовы других методов эта настройка не разрешает.

Обратите внимание: `AnyTimes()` допускает отсутствие вызова. Поэтому после обращения к сервису нужно проверить полученное название фильма. Одного ожидания мока для такого теста недостаточно.

| Настройка отдельного ожидания | Допустимое число вызовов |
|---|---|
| Без указания количества | Ровно один |
| `Times(0)` | Ни одного |
| `Times(2)` | Ровно два |
| `AnyTimes()` | От нуля и выше |
| `MinTimes(1)` | Хотя бы один, без заданной верхней границы |
| `MaxTimes(3)` | От нуля до трех |

В таблице каждая настройка применяется самостоятельно к новому ожиданию. При комбинировании ограничений учитывайте их взаимодействие, описанное в [API `gomock.Call`](https://pkg.go.dev/go.uber.org/mock/gomock#Call).

Чтобы потребовать хотя бы одно чтение, замените `AnyTimes()` на `MinTimes(1)`. Если проверяется отсутствие лишних запросов к БД, используйте `Times(1)`.

Для списания денег или отправки уведомления количество вызовов может быть частью требования. В таком тесте нужно явно проверить, что повторного действия не произошло.

Аргументы тоже стоит проверять избирательно. В примерах контекст сопоставляется через `gomock.Any()`, а ID — точно. Заменять оба аргумента на `Any()` ради зеленого теста опасно: service сможет запросить другой фильм. Если важны deadline или отмена, контекст также нужно проверить.

Еще один источник путаницы — пересекающиеся ожидания на один метод. Широкое ожидание с `gomock.Any()` и `AnyTimes()` может принять вызов, который предназначался более точному ожиданию. Старайтесь задавать непересекающиеся условия, а для ответа, вычисляемого по аргументу, рассмотрите `DoAndReturn`.

Когда подмене нужно хранить данные и поддерживать последовательность «создать → прочитать → удалить», небольшой fake на `map` иногда проще набора ожиданий. Когда нужно проверить SQL, транзакции или ограничения схемы, требуется настоящая БД. Настройка мока помогает избежать лишней связанности с реализацией, но не расширяет границы того, что проверяет тест.

## 5. TDD, регрессионные тесты и рефакторинг

Test-Driven Development, или TDD, — подход, при котором изменение поведения начинают с теста. Сначала определяют, что функция должна вернуть, затем пишут реализацию.

### Цикл «красный → зеленый → рефакторинг»

1. **Red:** напишите тест на одно требование и убедитесь, что он падает по ожидаемой причине.
2. **Green:** добавьте реализацию, чтобы новый и ранее написанные тесты прошли.
3. **Refactor:** при необходимости упростите код, сохраняя его поведение и успешное прохождение тестов.

После этого выберите следующее требование и повторите цикл. Подробнее — в [объяснении TDD Мартина Фаулера](https://martinfowler.com/bliki/TestDrivenDevelopment.html).

Например, билет стоит 350 рублей. Напишем тест, который ожидает от `BookingTotal(3)` стоимость `1050`. С временной реализацией, возвращающей ноль, тест упадет. Добавим расчет стоимости — тест пройдет. Затем вынесем цену в именованную константу и повторим проверку.

Следующим циклом добавим тест на недопустимое количество билетов и реализуем ограничение. Так требования добавляются небольшими шагами.

### Рефакторинг и исправление ошибок

Рефакторинг меняет структуру кода, сохраняя поведение. Например, расчет стоимости можно вынести из обработчика в отдельную функцию. Сначала зафиксируйте нужное поведение тестами, затем изменяйте код и запускайте проверки. Изменение цены билета уже относится к новой функциональности.

Для исправления бага сначала добавьте тест, который его воспроизводит. Например, если сервис разрешил купить 11 билетов при максимуме 10, проверьте, что такой запрос возвращает ошибку. Убедитесь, что тест падает, исправьте код и оставьте проверку в наборе. Такой тест называется регрессионным: он помогает обнаружить повторное появление ошибки.

## 6. Надежность тестов: параллельность, flaky и coverage

### Параллельный запуск

Метод `t.Parallel()` позволяет выполнять тест одновременно с другими параллельными тестами. Добавим его в подтесты для `ParseFilmID`:

```go
for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		t.Parallel()
		// Вызов ParseFilmID и проверки для tt.
	})
}
```

В этом примере каждый подтест получает собственную строку и проверяет результат ее разбора. Подтесты не меняют общие данные, поэтому их можно выполнять параллельно.

Перед добавлением `t.Parallel()` в другие тесты проверьте, не используют ли они одни и те же файлы, записи БД или глобальные настройки. Собственный мок изолирует ожидания подтеста, но общая база при этом остается общей.

```bash
go test -parallel=4 ./...       # лимит параллельных тестов внутри тестового бинарника
go test -p=2 ./...              # лимит параллельной работы с пакетами
```

После вызова `t.Parallel()` подтест приостанавливается и ждет возврата функции родительского теста. Затем он продолжает работу вместе с другими параллельными подтестами.

Если родитель создал для них общий ресурс, зарегистрируйте закрытие через `t.Cleanup`. Такой вызов выполнится после подтестов. Обычный `defer` родителя сработает раньше, и ресурс окажется закрыт к моменту продолжения их работы.

### Flaky-тесты

Тест, который при одном и том же коде то проходит, то падает, называется flaky-тестом. Причина может быть во времени, порядке запуска, случайных данных или внешнем окружении. flaky-тесты опасны тем, что при их наличии разработчик перестаёт доверять тестам, и следующее падение тестов из за ошибки может быть воспринято как проявление flaky-тестов.

Например, тест ожидает определённого порядка при итерации по мапе. Требуемый порядок может иногда соблюдаться, а иногда нет.

Для поиска нестабильности:

```bash
go test -count=100 -shuffle=on -timeout=2m ./internal/film
```

Флаг `-count=100` повторяет тесты 100 раз. `-shuffle=on` меняет порядок тестов, которые запускает тестовый раннер. Строки таблицы внутри `t.Run` он не перемешивает.

Если тест упал, сохраните seed из вывода и повторите команду с `-shuffle=<seed>`. Также сохраните версию Go, входные данные и параметры окружения.

### Покрытие кода

Coverage показывает, какие участки кода выполнились во время тестов. В стандартном отчете Go процент относится к операторам, а не к количеству осмысленных проверок или всех возможных ветвей поведения. Механизм описан в [статье о Go cover](https://go.dev/blog/cover).

```bash
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
go tool cover -html=coverage.out -o coverage.html
go test -race -covermode=atomic -coverprofile=coverage.out ./...
```

HTML-отчет подсвечивает выполненный и невыполненный код. Последняя команда измеряет покрытие вместе с детектором гонок, используя совместимый режим счетчиков `atomic`.

Откройте HTML-отчет и найдите невыполненные участки. Например, непокрытый `if err != nil` подсказывает добавить тест на ошибку зависимости.

Обратите внимание: вызов функции увеличивает coverage даже без проверки результата. Поэтому 100% покрытия еще не означают, что проверены все границы, конкурентные операции и сами требования.

## 7. Поиск гонок данных

Если несколько горутин обращаются к одной области памяти и хотя бы одна записывает данные, их доступ нужно синхронизировать. Иначе возникает гонка данных (data race).

Рассмотрим счетчик, который увеличивают две горутины. Каждая выполняет тысячу прибавлений, поэтому после завершения ожидается `2000`.

Учебный пример с ошибкой; запускайте его отдельно от набора исправных тестов:

```go
package raceexample

import (
	"sync"
	"testing"

	"github.com/stretchr/testify/assert"
)

func TestCounterRace(t *testing.T) {
	var counter int
	var wg sync.WaitGroup
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 1000; j++ {
				counter++ // Ошибка: несинхронизированные чтение и запись.
			}
		}()
	}
	wg.Wait()
	assert.Equal(t, 2000, counter)
}
```

`WaitGroup` здесь позволяет дождаться завершения, но не защищает `counter++` от одновременного выполнения. Инкремент включает чтение, изменение и запись; обновления могут потеряться. Даже если тест случайно получил `2000`, гонка осталась.

```bash
go test -race ./...
go test -race -run '^TestCounterRace$' -count=10 ./...
```

При обнаружении гонки в выводе появится `WARNING: DATA RACE`. Ниже будут стеки конфликтующих обращений и места создания горутин. По ним можно найти переменную, к которой обращаются без синхронизации.

Для исправления можно использовать мьютекс, атомарную операцию или передачу владения через канал.

## 8. Поиск потерянных горутин

Предположим, горутина отправляет результат в канал, но запрос уже отменен и результат никто не читает. Отправка остается заблокированной. Такая горутина удерживает стек и связанные данные, хотя ее работа больше не нужна. Это называется утечкой горутины.

Ошибочный фрагмент:

```go
func leakySend() {
	results := make(chan int)
	go func() {
		results <- 42 // Получателя нет, отправка никогда не завершится.
	}()
}
```

Сборщик мусора не отменяет работу такой горутины. Буфер канала размером один поможет конкретной единственной отправке, но не решит общий случай producer, который продолжает выдавать значения.

### `goleak`

`goleak` ищет неожиданные горутины, оставшиеся после тестов:

```bash
go get go.uber.org/goleak@v1.3.0
```

Чтобы проверить один последовательный изолированный тест, добавьте `defer goleak.VerifyNone(t)`. Перед выходом из теста библиотека проверит оставшиеся горутины.

Если ресурсы освобождаются через `t.Cleanup`, зарегистрируйте там и проверку утечек — до создания ресурсов. Функции cleanup выполняются в обратном порядке: сначала закроются ресурсы, затем пройдет проверка. Обычный `defer` выполнился бы до этой очистки.

Для пакета с параллельными тестами удобнее один файл `internal/film/main_test.go`:

```go
package film

import (
	"testing"

	"go.uber.org/goleak"
)

func TestMain(m *testing.M) {
	goleak.VerifyTestMain(m)
}
```

В этом варианте `goleak` проверит горутины после всех тестов пакета. Это удобно при параллельном запуске: горутина соседнего работающего теста не попадет в проверку как утечка.

Метод `VerifyTestMain` сам вызывает `m.Run`. Повторно запускать его не нужно. Подробнее — в [документации `goleak`](https://github.com/uber-go/goleak).

Если в пакете уже есть `TestMain`, объедините подготовку, завершение общих ресурсов и проверку в одном месте. Общие серверы и workers должны остановиться до проверки утечек. Не добавляйте широкие исключения только для того, чтобы тест стал зеленым.



## 9. Интеграционное тестирование

Интеграционный тест проверяет, как несколько компонентов работают вместе. Например, репозиторий отправляет SQL-запрос в PostgreSQL и получает данные. Такой тест помогает найти ошибки во взаимодействии кода с базой.

### Чем отличается от unit-теста

В unit-тесте сервиса мы подменяли репозиторий моком и задавали его ответ. Так можно проверить, что сервис возвращает название фильма или обрабатывает ошибку. Сам SQL при этом не выполняется.

В интеграционном тесте репозитория используется настоящий PostgreSQL. Если в запросе неверно указано имя столбца или данные неправильно считываются в структуру, тест обнаружит проблему.

| | Unit-тест | Интеграционный тест |
|---|---|---|
| Что проверяет | Логику отдельного компонента | Взаимодействие компонентов |
| Зависимости | При необходимости подменяются моками или заглушками | Проверяемые компоненты взаимодействуют по-настоящему |
| Подготовка | Обычно достаточно входных данных и настройки подмен | Может потребоваться база, миграции и тестовые данные |
| Скорость | Обычно выполняется быстро | Часто медленнее из-за окружения и ввода-вывода |
| Причина провала | Ошибка в логике проверяемого компонента | Также ошибка запроса, схемы или настройки взаимодействия |

База данных — один из примеров. Интеграционный тест также может проверять взаимодействие нескольких слоев приложения, работу с очередью сообщений или внешним API.

### Как устроена проверка

Для проверки поиска фильма через PostgreSQL выполним следующие шаги:

1. Подготовим отдельную тестовую базу и применим миграции приложения.
2. Добавим фильм и получим его ID.
3. Вызовем метод репозитория и сравним результат с добавленными данными.
4. Очистим данные и закроем соединения, в том числе при провале теста.

Отдельными сценариями можно проверить отсутствие фильма, ограничения `UNIQUE` и откат изменений при ошибке. Каждый тест должен готовить свои данные и не зависеть от порядка запуска других тестов.

В Go для таких проверок используются те же функции `TestXxx`, пакет `testing` и команда `go test`. Отличие заключается в составе проверяемых компонентов и подготовке окружения. Интеграционные тесты часто запускают отдельным этапом, чтобы сначала выполнить быстрые unit-тесты, затем подготовить нужные сервисы.

### Отдельный запуск через build tags

Интеграционные тесты можно отделить от быстрых unit-тестов тегом сборки. Директива должна находиться в начале файла, перед строкой `package`:

```go
//go:build integration

package film_test
```

Обычный `go test ./...` такой файл не включает. Для запуска интеграционных тестов явно передайте тег:

```bash
go test -tags=integration ./...
```

Тег отделяет набор тестов, но не поднимает окружение сам. PostgreSQL, миграции и переменные подключения нужно подготовить до запуска команды.

### Организация интеграционных тестов через Test Suite

Пакет `github.com/stretchr/testify/suite` позволяет объединить связанные тесты и общую подготовку окружения. Методы `SetupSuite` и `TearDownSuite` выполняются один раз для всего набора, а `SetupTest` и `TearDownTest` — для каждого тестового метода.

```go
type RepositorySuite struct {
	suite.Suite
	db   *sql.DB
	repo *PostgresRepository
}

func (s *RepositorySuite) SetupSuite() {
	db, err := openTestDB()
	s.Require().NoError(err)
	s.db = db
	s.repo = NewPostgresRepository(db)
}

func (s *RepositorySuite) SetupTest() {
	_, err := s.db.Exec("TRUNCATE films RESTART IDENTITY")
	s.Require().NoError(err)
}

func (s *RepositorySuite) TearDownSuite() {
	s.Require().NoError(s.db.Close())
}

func (s *RepositorySuite) TestFindByID() {
	// Подготовка фильма, вызов s.repo.FindByID и проверки через s.Require().
}

func TestRepositorySuite(t *testing.T) {
	suite.Run(t, new(RepositorySuite))
}
```

Метод тестового набора должен начинаться с `Test`. Общие ресурсы удобно создавать один раз в `SetupSuite`, однако данные каждого теста должны оставаться изолированными. Не используйте suite только ради группировки: если общей подготовки нет, обычные `t.Run` проще.

## 10. Нагрузочное тестирование

Нагрузочное тестирование - это метод проверки производительности. Оно показывает, как работающий сервис ведет себя при потоке запросов. Специальная программа, генератор нагрузки, отправляет запросы и собирает результаты.

Например, один пользователь быстро получает список фильмов. Теперь предположим, что каталог одновременно открывают сотни пользователей. Запросы могут начать ждать свободное соединение с БД, время ответа увеличится, а часть пользователей получит ошибку.

### Зачем это нужно

С помощью нагрузочного теста можно проверить, выдерживает ли сервис ожидаемый поток запросов, найти ограничивающий его ресурс и сравнить поведение до и после изменения кода или настроек.

Также можно постепенно увеличивать нагрузку, чтобы найти предел сервиса, резко поднять ее для проверки скачка посещаемости или оставить тест работать надолго, чтобы заметить накопление проблем. После снижения нагрузки проверяют, восстановилась ли нормальная работа.

### Что измеряют

Результаты запросов собирает генератор нагрузки. Показатели самого сервиса и базы данных смотрят в мониторинге.

| Показатель                         | Что показывает                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| Запросы в секунду, RPS             | Какой поток запросов фактически создается; отдельно полезно считать успешные ответы в секунду |
| Время ответа                       | Сколько клиент ждет результат запроса                                                         |
| p95 и p99 времени ответа           | За какое время завершаются примерно 95% и 99% запросов                                        |
| Ошибки и тайм-ауты                 | Какая доля запросов не получила ожидаемый результат                                           |
| CPU и память                       | Как меняется потребление ресурсов под нагрузкой                                               |
| Горутины, соединения и ожидание БД | Где может накапливаться незавершенная работа                                                  |

Например, `p95 = 200 мс` означает, что примерно 95% запросов завершились не дольше 200 мс. Оставшиеся запросы могли выполняться значительно дольше. Поэтому одного среднего времени для оценки недостаточно. Примеры метрик генератора приведены в [документации k6](https://grafana.com/docs/k6/latest/using-k6/metrics/).

Обратите внимание: 100 одновременных пользователей и 100 запросов в секунду — разные условия. Пользователь может ждать ответ или делать паузу перед следующим действием. В описании теста нужно указать, какую нагрузку мы задаем.

### Как оценить результат

До запуска задайте нагрузку и критерии успеха. Например: 100 запросов в секунду в течение пяти минут, p95 ниже 200 мс, ошибок меньше 1%. Значения выбираются из требований к сервису.

После запуска проверьте фактическую нагрузку, корректность ответов и выполнение критериев. Рост задержек и ошибок сопоставьте с потреблением ресурсов. Сравнивайте прогоны при одинаковых данных и ресурсах стенда.

### Какие инструменты используют для Go-сервисов

Для HTTP-сервиса инструмент выбирают по сценарию тестирования независимо от языка приложения:

- [hey](https://github.com/rakyll/hey) — простая нагрузка на один HTTP-адрес.
- [Vegeta](https://github.com/tsenart/vegeta) — заданная частота запросов; есть Go-библиотека.
- [k6](https://github.com/grafana/k6) — сценарии из нескольких действий и проверки ответов на JavaScript.

## 11. Линтинг и код стайл

Для поиска проблем в коде используются инструменты линтеры. Они могут обнаружить пропущенную ошибку, неверный формат `Printf`, копирование mutex или неиспользуемое присваивание. Запускать код для такой проверки не требуется.

Чтобы привести отступы, пробелы и переносы строк к единому виду, используются форматтеры. После форматирования в diff остается меньше различий в оформлении, и изменения проще читать.

### `golangci-lint`

`golangci-lint` объединяет линтеры и форматтеры и позволяет хранить их настройки в одном файле. Установите подходящий для вашей версии Go выпуск по [официальной инструкции](https://golangci-lint.run/docs/welcome/install/).

Начальный файл `.golangci.yml` для версии 2:

```yaml
version: "2"

run:
  timeout: 3m

linters:
  default: none
  enable:
    - govet
    - staticcheck
    - errcheck
    - ineffassign
    - unused
    - bodyclose
  exclusions:
    generated: strict

formatters:
  enable:
    - goimports
  exclusions:
    generated: strict
```

В поле `version` указана версия схемы конфигурации. Секция `linters` задает анализаторы, а `formatters` — форматтеры.

Настройка `generated: strict` распознает файлы со стандартным заголовком сгенерированного Go-кода, включая вывод mockgen. Подробнее — в [описании конфигурации](https://golangci-lint.run/docs/configuration/file/).

Популярные анализаторы решают разные задачи:

| Анализатор | Пример того, что он ищет |
|---|---|
| `govet` | Неверные аргументы форматирования, копирование блокировок |
| `staticcheck` | Подозрительную логику, ненужные операции и устаревшие API |
| `errcheck` | Игнорирование возвращаемых ошибок |
| `ineffassign` | Присваивание, результат которого не используется |
| `unused` | Неиспользуемые объявления |
| `gosimple` | Конструкции, которые можно упростить без изменения поведения; в актуальном golangci-lint входит в `staticcheck` |
| `revive` | Нарушения стилевых правил и распространенных практик Go |
| `gocognit` | Высокую когнитивную сложность функций |
| `dupl` | Похожие и дублирующиеся фрагменты кода |
| `funcorder` | Нарушение выбранного порядка функций и методов в файле |
| `bodyclose` | Незакрытое тело HTTP-ответа |
| `goconst` | Повторяющиеся литералы, которые можно вынести в константы |
| `godoclint` | Ошибки и несогласованность GoDoc-комментариев |
| `gosec` | Потенциально небезопасные конструкции |
| `makezero` | Добавление элементов в слайс, созданный сразу с ненулевой длиной вместо нужной емкости |
| `wsl_v5` | Расположение выражений и пустых строк, влияющее на читаемость |
| `paralleltest` | Отсутствие ожидаемого `t.Parallel()` в тестах и подтестах |
| `unparam` | Параметры функций, которые фактически не используются |

Включать все анализаторы сразу необязательно. Полный список и статус каждого анализатора приведены в [документации golangci-lint](https://golangci-lint.run/docs/linters/).

Форматтеры отвечают за механическое оформление исходного кода:

| Форматтер | Назначение |
|---|---|
| `gofmt` | Стандартное форматирование Go-кода |
| `gofumpt` | Более строгий набор правил поверх `gofmt` |
| `gci` | Сортировка и группировка импортов по заданным правилам |
| `golines` | Перенос слишком длинных строк |
| `goimports` | Форматирование и автоматическое добавление или удаление импортов |

Команды проверки и форматирования:

```bash
golangci-lint run ./...
golangci-lint fmt
```

`run` запускает анализаторы, `fmt` применяет форматирование.

### Как вводить правила в проект

Начните с небольшого набора проверок, которые команда понимает и готова исправлять. Затем добавляйте правила по обнаруженным проблемам.

В большом существующем проекте можно сначала запрещать новые нарушения относительно базовой ветки:

```bash
golangci-lint run --new-from-merge-base=origin/main ./...
```

Такой режим помогает перестать добавлять плохой код в проект, при этом не переписывая уже имеющийся.

Чтобы отключить конкретную проверку в отдельном месте, укажите имя линтера и причину. Например: `//nolint:gocyclo // функция отражает неделимый бизнес-процесс`.

Такое исключение относится к `gocyclo`. Комментарий без имени линтера — `//nolint` — отключает больше проверок и может скрыть другие ошибки.

### Стиль, который помогает читать код

Стиль шире форматирования: не все решения можно проверить автоматически. В проекте стоит договориться об именовании, размещении интерфейсов и обработке ошибок. За основу можно взять [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md) — набор соглашений, которые помогают писать более единообразный и безопасный Go-код.

Несколько применимых правил:

- Описывайте небольшой интерфейс в пакете-потребителе, которому он нужен, а не рядом с конкретной реализацией «на будущее».
- Оборачивайте ошибку через `%w`, когда вызывающий код должен сохранить возможность проверить исходную ошибку с помощью `errors.Is` или `errors.As`.
- Проверяйте ошибку сразу и выходите из функции. Ранний возврат уменьшает вложенность и делает основной сценарий заметнее.
- Если итоговый размер слайса известен, заранее задавайте емкость: `make([]T, 0, n)`. Если нужны `n` уже существующих нулевых элементов, задавайте длину: `make([]T, n)`.
- Для частых преобразований простых типов используйте `strconv`, а не более общий и тяжелый `fmt`.
- Избегайте naked returns в длинных функциях: явный список возвращаемых значений легче читать. Именованные результаты остаются полезны, когда делают короткую функцию понятнее.
- Не используйте `panic` для ожидаемых ошибок в библиотечном коде. Возвращайте `error`; панику оставляйте для действительно невосстановимых нарушений инварианта.
- Не логируйте одну и ту же ошибку на каждом слое: добавляйте контекст при возврате, а записывайте ошибку там, где она окончательно обрабатывается.
- При необходимости проверяйте реализацию интерфейса во время компиляции: `var _ http.Handler = (*Handler)(nil)`.
- Сокращайте область видимости переменных и объявляйте их рядом с использованием.
