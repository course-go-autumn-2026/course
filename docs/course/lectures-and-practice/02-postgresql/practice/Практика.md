# Практика: PostgreSQL из Go

Вы доработаете сервис кинотеатра: добавите таблицу бронирований через миграцию, создадите индекс, соберёте гибкий поиск с помощью Squirrel и реализуете атомарное бронирование.

## Формат занятия

Работайте группами по 3–4 человека за одним компьютером. На каждом задании выберите разработчика и спикера (который будет представлять результат). На следующем задании по возможности поменяйтесь ролями.

После каждого задания спикер одной из команд показывает результат за 1–2 минуты. Если решение неполное, преподаватель показывает недостающую часть, а остальные команды получают 5 минут, чтобы исправить свой код.

## Что уже есть в репозитории

В подготовленном Go-проекте уже есть:
- `compose.yaml` с PostgreSQL;
- подключение через `pgxpool`;
- Squirrel в зависимостях и команды `Makefile` для работы с goose;
- миграция `00001_init_screenings.sql`, которая создаёт и заполняет таблицу `screenings`;
- простой метод получения списка сеансов;
- готовый HTTP-обработчик, каркас сервиса и менеджер транзакций;
- точка входа для проверки бронирования без HTTP.

В практике используются две прикладные таблицы: готовая `screenings` и `bookings`, которую вы добавите.

Структура таблицы `screenings`:

| Поле | Тип и ограничения |
|---|---|
| `id` | `bigint`, identity, первичный ключ |
| `film_title` | `text`, `NOT NULL` |
| `starts_at` | `timestamptz`, `NOT NULL` |
| `available_seats` | `integer`, `NOT NULL`, не меньше нуля |

## Подготовка

Нужны Go, Docker с плагином Compose, make, curl и goose. Установка goose описана в [README](./README.md).

Склонируйте выданный репозиторий, запустите PostgreSQL и примените готовую миграцию:

```bash
git clone <адрес-репозитория>
cd <каталог-репозитория>
docker compose up -d --wait

make migrate-up
```

Адрес учебной БД уже задан в `Makefile`, настраивать `DATABASE_URL` в окружении не нужно.
Команды ниже рассчитаны на настройки выданного `compose.yaml`. Если вы меняете реквизиты или подключаетесь к другой БД, следуйте [инструкции в README](./README.md#другая-база-данных).

## Задание 1. Добавить таблицу через миграцию

**Время: 10 минут.**

Создайте миграцию:

```bash
goose -s -dir ./migrations create add_bookings sql
```

В секции `-- +goose Up` создайте таблицу `bookings`:

| Поле           | Тип и ограничения                                           |
| -------------- | ----------------------------------------------------------- |
| `id`           | `bigint`, identity, первичный ключ                          |
| `screening_id` | `bigint`, `NOT NULL`, внешний ключ на `screenings(id)`      |
| `user_id`      | `bigint`, `NOT NULL`                                        |
| `created_at`   | `timestamptz`, `NOT NULL`, по умолчанию `CURRENT_TIMESTAMP` |

Пара `(screening_id, user_id)` должна быть уникальной: один пользователь может забронировать конкретный сеанс только один раз. Назовите ограничение `bookings_screening_user_unique`, чтобы код мог надёжно распознать его нарушение. В секции `-- +goose Down` удалите таблицу.

Примените миграцию, затем проверьте откат и повторное применение:

```bash
make migrate-up
make bookings-schema

make migrate-down
make migrate-up
make migrate-status
docker compose exec postgres psql -U app -d cinema -c '\dt'
```

Перед переходом дальше миграция должна остаться применённой.

Покажите файл миграции, успешные `up → down → up` и обе прикладные таблицы.

## Задание 2. Добавить индекс и сравнить планы запроса

**Время: 10 минут.**

Ближайшие сеансы запрашиваются так:

```sql
SELECT id, film_title, starts_at, available_seats
FROM screenings
WHERE starts_at >= $1
ORDER BY starts_at
LIMIT 20;
```

### 1. Снять план без индекса

В исходной таблице всего четыре строки. Для такой таблицы PostgreSQL может выбрать `Seq Scan` даже при наличии индекса: прочитать её целиком дешевле. Чтобы увидеть разницу в планах, добавьте 100 000 тестовых строк.

Если миграция индекса уже применена и она последняя, сначала откатите её командой `make migrate-down`.

Откройте psql в отдельном терминале:

```bash
docker compose exec postgres psql -U app -d cinema
```

Все SQL-блоки ниже выполняйте в psql, а команды goose, make и Docker Compose в обычном терминале из каталога проекта.

```sql
INSERT INTO screenings (film_title, starts_at, available_seats)
SELECT
    'EXPLAIN demo ' || n,
    TIMESTAMPTZ '2026-09-01 00:00:00+00' + n * INTERVAL '1 minute',
    100
FROM generate_series(1, 100000) AS s(n);

ANALYZE screenings;
```

`ANALYZE screenings` обновляет статистику, которую использует планировщик.

Выполните запрос с `EXPLAIN` и сохраните вывод. Ниже `$1` заменён датой из диапазона тестовых данных:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, film_title, starts_at, available_seats
FROM screenings
WHERE starts_at >= TIMESTAMPTZ '2026-09-10 18:00:00+00'
ORDER BY starts_at
LIMIT 20;
```

`EXPLAIN ANALYZE` действительно выполняет запрос и показывает фактические показатели. `BUFFERS` добавляет сведения об обращениях к страницам таблиц и индексов.

### 2. Создать и применить индекс

Создайте отдельную миграцию с индексом `screenings_starts_at_idx` по `starts_at`:

```bash
goose -s -dir ./migrations create add_screenings_starts_at_index sql
```

В `Up` создайте индекс, а в `Down` удалите его. Примените миграцию и найдите индекс:

```bash
make migrate-up
docker compose exec postgres psql -U app -d cinema -c \
  "SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'screenings';"
```

### 3. Сравнить планы и проверить откат

Повторите в psql тот же запрос с `EXPLAIN (ANALYZE, BUFFERS)` и сохраните новый план. На подготовленных данных ожидаем такие узлы:

```text
Без индекса: Limit → Sort → Seq Scan
С индексом:  Limit → Index Scan using screenings_starts_at_idx
```

Найдите `Index Cond`, сравните наличие `Sort`, показатели `Buffers` и `Execution Time`. Повторите запрос несколько раз: время зависит от кэша и машины, поэтому конкретного ускорения не требуется. Поле `cost` содержит оценку в условных единицах, не в миллисекундах.

Проверьте откат миграции индекса и повторное применение. Выполните в обычном терминале:

```bash
make migrate-down
docker compose exec postgres psql -U app -d cinema -c \
  "SELECT to_regclass('public.screenings_starts_at_idx') AS index_name;"

make migrate-up
docker compose exec postgres psql -U app -d cinema -c \
  "SELECT to_regclass('public.screenings_starts_at_idx') AS index_name;"
```

После отката первый запрос должен вернуть `NULL` (пустое поле в psql), а после повторного применения второй запрос должен вернуть `screenings_starts_at_idx`.

### 4. Удалить тестовые данные

После сравнения удалите только строки с префиксом `EXPLAIN demo ` и обновите статистику:

```sql
DELETE FROM screenings WHERE film_title LIKE 'EXPLAIN demo %';
ANALYZE screenings;
```

Исходные сеансы нужны для следующих заданий. Индекс оставьте применённым.

## Задание 3. Собрать запрос с гибкими фильтрами

**Время: 10 минут.**

Тип фильтра, разбор HTTP-параметров и сигнатура метода уже есть в стартовом проекте:

```go
type ScreeningFilter struct {
	Search     string
	StartsFrom *time.Time
	MinSeats   *int
	Limit      uint64
}

func (r *ScreeningRepository) Search(
	ctx context.Context,
	filter ScreeningFilter,
) ([]Screening, error)
```

К моменту вызова репозитория параметры уже подготовлены:

- HTTP-обработчик преобразовал строки в нужные типы;
- у `Search` удалены краевые пробелы; строка только из пробелов означает отсутствие фильтра;
- `MinSeats`, если указан, содержит неотрицательное целое число;
- некорректные значения отклонены;
- `Limit` получил значение по умолчанию 20 и ограничен диапазоном от 1 до 100.

Код выполнения запроса и чтения строк также написан. Заполните `TODO` между созданием `query` и вызовом `ToSql()`. При необходимости добавьте импорты; готовый код выполнения запроса и чтения строк не меняйте.

Общая часть запроса уже написана:

```go
query := sq.StatementBuilder.
	PlaceholderFormat(sq.Dollar).
	Select("id", "film_title", "starts_at", "available_seats").
	From("screenings")
```

Добавляйте условие только для заполненного фильтра:

- `Search` — название фильма содержит буквальную подстроку без учёта регистра;
- `StartsFrom` — сеанс начинается не раньше указанного времени;
- `MinSeats` — свободных мест не меньше указанного числа.

В `Search` символы `%`, `_` и `\` считаются обычными символами; при использовании `ILIKE` их нужно экранировать.

Завершите запрос сортировкой `starts_at, id` и вызовом `Limit(filter.Limit)`. Значения фильтров должны оставаться аргументами: не добавляйте их в SQL через `fmt.Sprintf` или конкатенацию. После `ToSql()` готовый код передаст SQL и аргументы в `pool.Query`.

## Задание 4. Собрать бронирование в транзакции

**Время: 10 минут.**

HTTP API уже подготовлен:

```text
POST /screenings/{screening_id}/bookings
Content-Type: application/json

{
  "user_id": 101
}
```

HTTP-обработчик разбирает запрос. Методы репозиториев также уже реализованы:

```go
func (r *ScreeningRepository) TakeSeat(
	ctx context.Context,
	db DBTX,
	screeningID int64,
) error

func (r *BookingRepository) Create(
	ctx context.Context,
	db DBTX,
	screeningID int64,
	userID int64,
) (Booking, error)
```

`TakeSeat` атомарно уменьшает число мест и возвращает `ErrNoSeats`, если свободных мест нет. `Create` добавляет бронирование и возвращает `ErrAlreadyBooked`, если пользователь уже бронировал этот сеанс.

В сервисе проверка мест идёт первой. Если мест уже нет, повторное бронирование завершится с `ErrNoSeats`, а не `ErrAlreadyBooked`: до вызова `Create` выполнение не дойдёт.

Допишите только `BookingService.Book`:

```go
func (s *BookingService) Book(
	ctx context.Context,
	screeningID int64,
	userID int64,
) (Booking, error)
```

В методе нужно:

1. Вызвать `txManager.WithinTransaction`.
2. Внутри callback сначала вызвать `TakeSeat`.
3. Если место удалось занять, вызвать `Create`.
4. Передать обоим методам один и тот же `pgx.Tx`, полученный callback-ом.
5. Вернуть ошибку любого из методов, чтобы менеджер выполнил `Rollback`.
6. После успешной транзакции вернуть созданное бронирование.

Не обращайтесь к `pool` напрямую и не вызывайте `BeginTx`, `Commit` или `Rollback`: этим занимается готовый менеджер транзакций.

После изменения кода остановите сервер из задания 3 сочетанием `Ctrl+C` и снова выполните `make run`. Автоматической перезагрузки нет; после следующих изменений сервер также нужно перезапускать.

Перед проверками выполните в psql блок ниже. Он удаляет все бронирования сеансов № 1 и № 2 и восстанавливает число мест только у них. Используйте его только в учебной БД и не отправляйте запросы на бронирование во время сброса.

```sql
BEGIN;
DELETE FROM bookings WHERE screening_id IN (1, 2);
UPDATE screenings SET available_seats = 1 WHERE id = 1;
UPDATE screenings SET available_seats = 3 WHERE id = 2;
COMMIT;
```

Проверьте API:

```bash
curl -i -X POST 'http://localhost:8080/screenings/1/bookings' \
  -H 'Content-Type: application/json' \
  -d '{"user_id": 101}'
```

Ожидается `HTTP 201 Created`: пользователь 101 занимает последнее место сеанса № 1.

Тот же сервис можно вызвать без HTTP:

```bash
make run ARGS='--demo-booking --screening-id 1 --user-id 102'
```

Здесь ожидается `ErrNoSeats`: предыдущий запрос уже занял последнее место. С флагом `--demo-booking` программа вызывает `BookingService.Book` и завершает работу. При успехе она печатает бронирование, а при ошибке выводит сообщение и завершается с ненулевым кодом.

Проверьте два сценария:

1. У сеанса № 1 одно свободное место. Первый пользователь получает бронирование, второй — `ErrNoSeats`. У этого сеанса одно бронирование и ноль мест. Команды выше проверяют этот сценарий.
2. У сеанса № 2 три места. Пользователь 101 бронирует его дважды. Второй вызов возвращает `ErrAlreadyBooked`, а число мест после отката остаётся равным двум.

Для второго сценария выполните следующий запрос дважды. Ожидается `HTTP 201 Created` при первом вызове и `HTTP 409 Conflict` с сообщением `user has already booked this screening` при повторном.

```bash
curl -i -X POST 'http://localhost:8080/screenings/2/bookings' \
  -H 'Content-Type: application/json' \
  -d '{"user_id": 101}'
```

После обоих сценариев проверьте состояние БД в psql:

```sql
SELECT s.id, s.available_seats, COUNT(b.id) AS bookings
FROM screenings AS s
LEFT JOIN bookings AS b ON b.screening_id = s.id
WHERE s.id IN (1, 2)
GROUP BY s.id, s.available_seats
ORDER BY s.id;
```

Ожидаемый результат:

| id | available_seats | bookings |
|---|---|---|
| 1 | 0 | 1 |
| 2 | 2 | 1 |

Второй сценарий доказывает, что уменьшение числа мест откатывается, если создание бронирования завершается ошибкой.

Оба сценария можно повторить целиком через API или через `--demo-booking`, используя те же идентификаторы сеансов и пользователей. Перед каждым полным прогоном выполните блок сброса выше. Не сбрасывайте данные между двумя вызовами внутри одного сценария.
