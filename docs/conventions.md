# Сквозные требования к коду

Это дополнение к заданиям, а не замена: в `tasks/` написано, что делать в
конкретной работе, здесь — требования, одинаковые для всех пяти.

Эти требования проверяются в каждой работе начиная с указанной. Они не привязаны
к одному пункту чек-листа: если что-то из этого списка нарушено, это видно в той
работе, где нарушено, и обсуждается на ревью.

## 1. Конфигурация — с лабораторной работы 1

- Всё, что различается между окружениями, приходит **только из переменных
  окружения**. Никаких хардкоженных адресов, портов, таймаутов и паролей.
- В репозитории лежит актуальный `.env.example` со всеми переменными и
  безопасными значениями по умолчанию.
- Если обязательная переменная не задана, сервис падает на старте с понятной
  ошибкой. Стартовать молча с нулевым таймаутом нельзя.
- Секретов в git нет. Ни в коде, ни в конфигах, ни в истории.

Базовый набор переменных — `config/trip-service.env.example`. Добавлять свои
можно, переименовывать существующие — нет.

## 2. Контекст и таймауты — с лабораторной работы 1

- Каждая функция, которая делает I/O, первым аргументом принимает
  `ctx context.Context`.
- `context.Background()` и `context.TODO()` допустимы только в `main` и в тестах.
- У любого исходящего вызова (БД, HTTP, gRPC, брокер) есть таймаут.
- Контекст запроса не используется для фоновой работы, которая должна пережить
  ответ клиенту. Для неё заводится собственный контекст жизни приложения.

## 3. Graceful shutdown — с лабораторной работы 1

- Сервис слушает `SIGINT` и `SIGTERM`.
- По сигналу: перестаём принимать новые запросы → дожидаемся текущих →
  останавливаем фоновые компоненты → закрываем пул БД и клиентов.
- Общий бюджет — `SHUTDOWN_TIMEOUT`. По его истечении выходим принудительно и
  пишем об этом в лог.
- После остановки не должно оставаться работающих горутин (с лабораторной работы 3 проверяется
  `goleak`).

## 4. Ошибки — с лабораторной работы 1, строго с лабораторной работы 2

- HTTP-ошибки отдаём по RFC 9457 в `application/problem+json`, схема `Problem`
  лежит в `contracts/openapi/trip-service.openapi.yaml`.
- Поле `code` — машиночитаемое, стабильное. Клиенты разбирают именно его.
- Внутренние детали наружу не отдаём: текст ошибки бд, стектрейс и SQL-запрос в
  ответ клиенту не попадают. В лог попадают.
- Ошибки оборачиваются с контекстом (`fmt.Errorf("...: %w", err)`), а не
  подменяются.
- С лабораторной работы 2: доменные ошибки объявлены в домене, а перевод «доменная ошибка → HTTP
  или gRPC код» собран в одном месте на транспортном слое.

## 5. Логи — с лабораторной работы 2

- `log/slog`, JSON-handler, вывод в stdout.
- Уровень пишется из `LOG_LEVEL`.
- Обязательные поля каждой записи: `time`, `level`, `msg`, `service`, `trace_id`,
  `span_id`. По `trace_id` находим и логи запроса, и его трейс в Jaeger.
- Персональные данные и секреты в логи не пишем.
- Уровни: `Error` — сломалось и нужно внимание человека; `Warn` — деградация, с
  которой сервис справился сам (сработал ретрай, отвалился необязательный вызов);
  `Info` — значимые бизнес-события (создана поездка, завершена поездка); `Debug` —
  детали для отладки, в проде выключены.
- Одна ошибка логируется один раз, там где её обработали, а не на каждом уровне
  стека.

## 6. Тесты — с лабораторной работы 2

- `make test` запускает всё и завершается успешно.
- Все тесты гоняются с `-race`.
- Тесты не зависят от порядка запуска и проходят при `-count=2`.
- Никаких `time.Sleep` для синхронизации: используем каналы, `sync.WaitGroup`,
  подменяемое время.
- Внешние зависимости в unit-тестах — только моки (gomock), сгенерированные
  через `go:generate`.

## 7. Работа с БД — с лабораторной работы 1

- Только параметризованные запросы. Конкатенация пользовательских данных в SQL
  запрещена.
- Схема меняется только миграциями. `up` и `down` обязаны применяться.
- Миграции неизменяемы: применённый файл не редактируем, выпускаем новый.
- Индексы, добавляемые к непустым таблицам, создаются `CONCURRENTLY` (и в этом
  случае миграция не должна быть внутри транзакции).

## 8. Структура репозитория — с лабораторной работы 1

Ориентир — golang-standards/project-layout, адаптированный под наш сервис:

```
cmd/trip-service/        composition root, единственный main
internal/                весь код сервиса, наружу не экспортируется
migrations/              SQL-миграции goose
api/                     сгенерированный по OpenAPI код
contracts/               копия контрактов курса (не редактируется)
deploy/                  Dockerfile, манифесты, docker-compose при необходимости
Makefile
.env.example
README.md
```

Внутренняя раскладка `internal/` фиксируется в лабораторной работе 2.

## 9. Makefile — с лабораторной работы 1

Обязательный минимум целей, работающих «из чистого клона»:

| Цель | Что делает |
|---|---|
| `tripgoctl environment start` / `stop` | поднять/остановить локальное окружение; эти команды не обязаны быть целями Makefile |
| `make migrate` | накатить миграции |
| `make run` | запустить сервис локально |
| `make test` | все тесты с `-race` |
| `make lint` | golangci-lint (с лабораторной работы 2) |
| `make generate` | вся кодогенерация: OpenAPI, mocks, protobuf |

## 10. README сервиса — с лабораторной работы 1

В корне репозитория лежит README, по которому проверяющий поднимает сервис ни о
чём не спрашивая: требования, команды запуска, переменные окружения, как прогнать
тесты, что сделано в текущей работе и какие приняты решения.
