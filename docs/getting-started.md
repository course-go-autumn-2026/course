# С чего начать

Здесь то, что нужно сделать до первой работы: завести репозиторий, поднять
окружение, поставить инструменты. В заданиях это уже не повторяется.

## 1. Репозиторий

Работы делаются в вашем личном репозитории, все пять — в одном. Каждая
следующая продолжает предыдущую, переписывать с нуля не нужно.

Заводим модуль:

```bash
mkdir trip-service && cd trip-service
git init
go mod init github.com/<ваш-логин>/trip-service
```

Аргумент `go mod init` — это module path, по нему ваши пакеты импортируются
внутри проекта: `github.com/<ваш-логин>/trip-service/internal/usecase/...`.
Обычно берут адрес репозитория, но требование одно — путь должен быть
уникальным и не меняться потом, иначе придётся править все импорты.

`go.mod` хранит зависимости и версию Go, `go.sum` — контрольные суммы всего, что
скачано. Оба файла коммитятся: без `go.sum` сборка не воспроизводится.

В `.gitignore` кладём собранный бинарь, `.env` и `.tripgo/` — это локальные
файлы конкретной машины.

## 2. Окружение

Всё, к чему обращается сервис, поднимает `tripgoctl`. В каждой работе лежит
`environment.toml` со списком нужных компонентов: копируем его в корень своего
репозитория и запускаем.

```bash
tripgoctl cluster start          # один раз на машине
tripgoctl environment start      # поднять компоненты этой работы
tripgoctl connect                # адреса и ссылки на веб-интерфейсы
```

Адреса берём из `.env`, который создаёт `environment start`. В коде и в командах
хосты и порты не хардкодим: у каждой работы своё окружение и свои порты.

Что внутри и что делать, если не поднялось — [`environment.md`](environment.md).

## 3. Инструменты

Начиная с Go 1.24 инструменты ставятся в сам модуль: `go get -tool` пишет их в
`go.mod`, а `go tool` запускает. Так у всех в команде одна и та же версия, и
ничего не надо ставить глобально.

```bash
go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen
go get -tool github.com/pressly/goose/v3/cmd/goose
go get -tool go.uber.org/mock/mockgen

go tool oapi-codegen --version
```

| Инструмент | Зачем | С какой работы |
|---|---|---|
| `oapi-codegen` | генерирует типы и серверные интерфейсы из OpenAPI | 1 |
| `goose` | накатывает и откатывает миграции | 1 |
| `mockgen` | генерирует моки по интерфейсам | 2 |
| `golangci-lint` | линтер, конфиг лежит в `config/golangci.yml` | 2 |
| `protoc` или `buf` | генерирует код по protobuf | 4 |

`golangci-lint` ставится отдельным бинарём — так рекомендуют авторы, и так он
работает быстрее. Команду установки смотрите в его документации.

Все команды генерации кладём в `Makefile` под цель `generate` или в
`//go:generate`. Сгенерированный код коммитим, но руками не правим: он
перезаписывается.

## 4. Миграции

Схему бд меняем только миграциями — никаких `psql` руками и правок таблиц на
живой базе. Каждая миграция состоит из двух частей: `up` накатывает изменение,
`down` его откатывает. Обе должны работать: без рабочего `down` вы не сможете
откатиться, если что-то пошло не так.

Применённую миграцию не редактируют. Если ошиблись — выпускают новую, которая
чинит. Иначе у вас и у проверяющего окажутся разные схемы при одинаковом коде.

Готовых миграций в комплекте нет: что должно быть в схеме, описано в заданиях,
писать её вам.

## 5. Как выглядит сданная работа

- ветка `homework/01` … `homework/05` от актуального `main`, Pull Request в
  `main`, до проверки не мержим;
- в описании PR: что сделано, какие решения приняты и почему, что не успели;
- в корне репозитория README, по которому проверяющий поднимает сервис ни о чём
  не спрашивая: требования, команды запуска, переменные окружения, как прогнать
  тесты;
- `make test` и `make lint` проходят.

Проверяющий смотрит по чек-листу — он лежит в конце каждой работы, там же
написано, сколько стоит каждый пункт. Плюс защита: 10–15 минут разговора по
вашему коду.

## 6. Как устроены задания

Все пять работ написаны по одной структуре: контекст, цель, что нужно сделать,
контракты, бизнес-правила, требования к реализации, как проверить себя, что
сдавать, критерии оценки, задания со звёздочкой.

Кроме самого задания действуют сквозные требования из
[`conventions.md`](conventions.md) — конфигурация, контекст и таймауты,
graceful shutdown, ошибки, логи, тесты, работа с бд, структура репозитория,
Makefile, README сервиса. Они одинаковы для всех работ, поэтому вынесены в
отдельный файл, а не продублированы пять раз.

Домен, сущности и жизненный цикл поездки — [`domain.md`](domain.md).
Шкала оценки и дедлайны — [`grading.md`](grading.md).
