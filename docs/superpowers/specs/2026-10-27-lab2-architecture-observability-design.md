# Лабораторная работа 2: архитектура и observability

## Цель

Сохранить внешний HTTP-контракт сервиса поездок из первой лабораторной и
перестроить внутренний код так, чтобы бизнес-правила не зависели от транспорта
и PostgreSQL. Сервис должен быть покрыт тестами, проходить линтер и отдавать
логи, метрики и трейсы через OpenTelemetry.

Новые ручки, изменения OpenAPI-контракта и миграции в этой работе не вводятся.

## Границы слоёв

```text
HTTP handler -> usecase -> domain -> repository interface
                                     |
                                     v
                              PostgreSQL implementation
```

Зависимости направлены внутрь. Пакет домена не импортирует HTTP, chi, pgx,
squirrel, OpenTelemetry или сгенерированный API. Usecase также не зависит от
транспорта и SQL-библиотек. HTTP-пакеты не создают и не импортируют конкретные
реализации репозиториев или инфраструктуры.

Целевая раскладка:

```text
cmd/trip-service/main.go
internal/config/
internal/container/
internal/domain/trip/
internal/model/
internal/usecase/trip/{create,get,finish}/
internal/http/trip/{create,get,finish}/
internal/http/domainerror/
internal/http/middleware/
internal/repository/trip/
internal/infra/postgres/
internal/infra/postgres/transaction/
internal/infra/telemetry/
internal/generated/
```

`main` отвечает только за чтение конфигурации, запуск приложения и graceful
shutdown. `container` создаёт конкретные зависимости и связывает их между
собой. Именно там разрешены конструкторы пула, репозитория и телеметрии.

Каждый usecase и HTTP-ручка располагаются в отдельном пакете. Интерфейсы
репозитория, транзакций и usecase объявляются неэкспортируемыми в `contract.go`
пакета-потребителя. Благодаря этому каждый потребитель запрашивает только
нужные ему методы, а реализация PostgreSQL остаётся заменяемой.

## Домен и ошибки

`internal/domain/trip` содержит сущность поездки, статус, переход `Finish` и
ошибки предметной области: поездка не найдена, поездка уже завершена, водитель
занят. Переход статуса выполняется методом доменной модели, который не требует
контекста, базы данных или HTTP.

Для ошибок валидации используется отдельный тип с названием поля и описанием
нарушения. HTTP-слой не выполняет `switch` по доменным ошибкам в хендлерах:
этим занимается единственный маппер `internal/http/domainerror`. Он возвращает
`application/problem+json` со статусами 400, 404 и 409 для ожидаемых ошибок.
Неожиданные ошибки превращаются в `500 internal_error`; текст ошибки базы или
внутренние детали клиенту не передаются.

## Выполнение операций

Хендлер декодирует и валидирует HTTP-запрос, преобразует его во входные данные
usecase и преобразует результат usecase в сгенерированный OpenAPI-ответ.

Usecase создания открывает транзакцию, сохраняет поездку и запись истории
статуса атомарно. Usecase завершения получает активную поездку, применяет
доменный переход `Finish`, сохраняет новое состояние и историю. Репозиторий
работает с pgx и squirrel, а преобразования между строкой PostgreSQL и доменной
моделью держит рядом с SQL-кодом.

Сгенерированные типы и серверные интерфейсы находятся в `internal/generated`.
Цель `make generate` воспроизводимо перезаписывает эти файлы; вручную они не
редактируются.

## Логи, метрики и трейсы

`infra/telemetry` создаёт JSON-логгер `slog` и OpenTelemetry SDK. Настройки
экспорта берутся из окружения. Неработающий коллектор не должен мешать запуску
HTTP-сервиса.

Порядок middleware:

```text
Recover -> Tracing -> Logging -> Metrics -> router
```

Tracing создаёт корневой спан с именем метода и шаблона маршрута. Пул PostgreSQL
инструментируется `otelpgx`, поэтому SQL-вызовы становятся вложенными спанами.
При ошибке спан получает статус Error и атрибут типа ошибки.

Logging записывает одну строку после ответа: метод, шаблон маршрута, статус,
длительность, `trace_id` и `span_id`. Для 2xx и 4xx используется Info, для 5xx
— Error. Отдельно логируются события создания и завершения поездки. Тела
запросов и ответов не записываются.

Metrics публикует HTTP-гистограмму длительности и число активных запросов.
Usecase создания и завершения увеличивают счётчики `tripgo.trips.created` и
`tripgo.trips.completed`. В атрибуте маршрута используется только шаблон, без
идентификаторов поездок.

## Тестирование и качество

* Домен: table-driven тесты переходов статуса и валидации.
* Usecase: unit-тесты с gomock для репозитория и менеджера транзакций.
* Маппер ошибок: table-driven тесты для ожидаемых и внутренних ошибок.
* Хендлеры: `httptest` с моками usecase для успеха, ошибок валидации и
  безопасного 500-ответа.
* Репозиторий: интеграционные тесты с PostgreSQL из `tripgoctl`, помеченные
  `integration`. Каждый тест использует собственные идентификаторы, очищает
  данные и может быть запущен повторно. Отдельный сценарий проверяет откат
  транзакции.

Моки генерируются `mockgen` рядом с контрактами. `make test` запускает тесты с
race detector и печатает покрытие пакетов домена и usecase; целевой минимум —
50%. `make test-integration` запускает только интеграционные сценарии.

В корне репозитория лежит `.golangci.yml` из курса. `make lint` запускает
golangci-lint и форматтеры из его конфигурации. Точечные `nolint` допустимы
только если без них нельзя и рядом есть причина.

## Проверка перед PR

1. `make generate`, `make lint`, `make test` и `make test-integration` проходят.
2. Сервис запускается в окружении `tripgoctl` и сохраняет прежнее поведение
   трёх ручек.
3. В Jaeger виден HTTP-спан с вложенным обращением к PostgreSQL.
4. В Grafana доступны HTTP-метрики и счётчики созданных и завершённых поездок.
5. `trace_id` из лога находит соответствующий трейс в Jaeger.
6. README содержит раздел об архитектуре, а описание PR — схему слоёв, решения
   и скриншоты Jaeger и Grafana.
