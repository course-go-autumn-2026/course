## 1. Контекст

Сервис ведёт поездки и маршруты. Теперь его хотят использовать соседние команды,
а мобильному приложению нужен более экономный протокол, чем JSON по HTTP. Плюс
продукту нужно, чтобы о завершённых поездках узнавали другие сервисы: начисление
бонусов, аналитика, расчёт чаевых.

Добавляем второй транспорт (gRPC) и асинхронное взаимодействие (Kafka).

Эта работа заодно проверяет, насколько честно сделана лабораторная работа 2. Если
слои выделены правильно, второй транспорт и консьюмер подключаются к готовым
usecase и бизнес-логика не дублируется. Если нет, придётся переписывать.

## 2. Цель

**Что будет уметь сервис.** Отдавать те же операции двумя транспортами — HTTP и
gRPC. При завершении поездки публиковать событие, а поездки уметь создавать не
только по запросу, но и по команде из брокера — идемпотентно, а то, что
обработать не удалось, складывать в DLQ (dead letter queue) — отдельный топик
для сообщений, которые сервис не смог обработать.

**Что на этом отрабатываем:**

- описывать контракт в protobuf и генерировать сервер и клиент;
- отдавать одну и ту же функциональность двумя транспортами без дублирования
  логики;
- заменять реализацию исходящего вызова, не трогая бизнес-код;
- публиковать и потреблять события, понимая гарантии доставки;
- делать обработчик идемпотентным и не блокировать партицию битым сообщением;
- пробрасывать контекст трассировки через gRPC и брокер.

## 3. Что нужно сделать

1. **Описать proto** сервиса поездок и сгенерировать код (п. 4.1).

   Ставим инструменты в модуль и генерируем:

   ```bash
   go get -tool google.golang.org/protobuf/cmd/protoc-gen-go
   go get -tool google.golang.org/grpc/cmd/protoc-gen-go-grpc

   protoc \
     --go_out=internal/generated --go_opt=paths=source_relative \
     --go-grpc_out=internal/generated --go-grpc_opt=paths=source_relative \
     -I contracts/proto \
     contracts/proto/trip/v1/trip_service.proto
   ```

   `protoc` — внешний бинарь, ставится отдельно (`brew install protobuf` или
   пакетом в вашей системе). Можно вместо него взять `buf` — он сам подтягивает
   плагины и не требует `protoc`; тогда команда генерации будет своя, опишите её
   в README сервиса. Команду кладём в `make generate`, результат коммитим.
2. **Поднять gRPC-сервер** рядом с HTTP: оба транспорта над одними usecase (п. 5.1).
3. **Перевести гейтвей Push Service с HTTP на gRPC** (п. 5.2).
4. **Публиковать `TripCompletedEvent`** в `trip.events.v1` при завершении
   поездки (п. 5.3).
5. **Потреблять `CreateTripCommand`** из `trip.commands.v1` и создавать по нему
   поездку — идемпотентно (п. 5.4).
6. **Сделать DLQ** для необрабатываемых сообщений (п. 5.5).

Куда класть новое, по раскладке из работы 2: gRPC-сервер — в
`internal/grpc/trip/<метод>/`, обработчик сообщений из брокера — в
`internal/consumer/tripcommands/`, клиент брокера — в `internal/infra/kafka/`.

## 4. Контракты

### 4.1. gRPC сервиса поездок

Файл `contracts/proto/trip/v1/trip_service.proto` — вы его дополняете и
коммитите в свой репозиторий; это **ваш** контракт, в отличие от опубликованного
`push.proto`.

```protobuf
service TripService {
  rpc CreateTrip(CreateTripRequest) returns (Trip);
  rpc GetTrip(GetTripRequest) returns (Trip);
  rpc FinishTrip(FinishTripRequest) returns (Trip);
  rpc AddPosition(AddPositionRequest) returns (Position);
  rpc ListPositions(ListPositionsRequest) returns (ListPositionsResponse);
}
```

Требования к контракту:

- поля нумеруются осмысленно, зарезервированных номеров не переиспользуем;
- временные метки — `google.protobuf.Timestamp`;
- `status` — `enum` с обязательным `TRIP_STATUS_UNSPECIFIED = 0`;
- деньги — `int64`, как в HTTP-контракте;
- никаких `optional bool` в качестве «трёхзначной логики» без причины.

Маппинг доменных ошибок в gRPC-коды фиксирован:

| Доменная ошибка | gRPC | HTTP (для сравнения) |
|---|---|---|
| валидация | `INVALID_ARGUMENT` | `400` |
| `ErrTripNotFound` | `NOT_FOUND` | `404` |
| `ErrTripCompleted` | `FAILED_PRECONDITION` | `409` |
| `ErrDriverBusy` | `ALREADY_EXISTS` | `409` |
| прочее | `INTERNAL` | `500` |

Маппинг собран в одном месте gRPC-слоя, как `problemFrom` в HTTP-слое из
лабораторной работы 2.

### 4.2. События

Оба топика — JSON, схемы и примеры лежат в
[`contracts/events/README.md`](../../contracts/events/README.md).

gRPC-ручки описаны в proto, а события — в JSON, и это осознанно: сообщение видно
глазами в Redpanda Console и туда же его можно положить руками, без утилит и
кодогенерации. Плата — нет строгой схемы, потребитель обязан сам проверять, что
пришло.

| | `trip.events.v1` | `trip.commands.v1` |
|---|---|---|
| Кто пишет | ваш сервис | вы руками через Console |
| Кто читает | внешние потребители | ваш сервис |
| Сообщение | `TripCompletedEvent` | `CreateTripCommand` |
| Ключ | `trip_id` | `driver_id` |
| DLQ | — | `trip.commands.v1.dlq` |
| Consumer-группа | — | `trip-service` |

Ключ `driver_id` выбран намеренно: команды по одному водителю попадают в одну
партицию и обрабатываются по порядку. На защите спросим, зачем это нужно именно
здесь.

Зачем сервису принимать команды на создание поездки, если есть API? Для учебной
задачи — чтобы поработать с консьюмером. В реальности такая схема тоже
встречается, она позволяет пережить недоступность сервиса, не теряя запросы.

### 4.4. Схема данных

Новая таблица `processed_commands`, состав полей — в
[`contracts/schema.md`](../../contracts/schema.md).

Зачем она нужна. Consumer работает at-least-once: оффсет коммитится после
обработки, поэтому при ребалансировке группы или рестарте пода между обработкой
и коммитом сообщение придёт второй раз. Это штатная работа Kafka, а не сбой.

Без этой таблицы повтор выглядит так: пытаемся создать вторую поездку тому же
водителю, срабатывает уникальный индекс `trips_active_driver_uniq`, получаем
`23505` и доменную ошибку `driver_busy`. Обработать сообщение не удалось —
значит, по п. 5.4 оно уедет в DLQ. Получится, что обычный дубль поднимает алерт
и требует разбора человеком.

С таблицей эти два случая различаются:

| Что пришло | Что делаем |
|---|---|
| `command_id` уже есть | это повтор: поездку не создаём, оффсет коммитим, метрика `result=duplicate` |
| `command_id` новый, но водитель занят | это конфликт: сообщение в DLQ |

Вставка `command_id` идёт в одной транзакции с созданием поездки. Если сделать
это двумя отдельными запросами, между ними может случиться сбой — и повтор
создаст вторую поездку.

Вставка идентификатора команды и создание поездки идут в одной транзакции, а
повторная доставка не должна превращаться в ошибку: по тому, вставилась строка
или нет, и понимаем, обрабатывали мы эту команду раньше.

Такую таблицу называют inbox: она хранит идентификаторы уже обработанных
входящих сообщений. Тот же приём подойдёт для любых команд, которые появятся
позже, и не заставляет добавлять в `trips` поле, которое заполнено только у
поездок, приехавших из Kafka.

## 5. Требования к реализации

### 5.1. gRPC-сервер

- Слушает `GRPC_ADDR`, поднимается параллельно с HTTP; оба сервера
  останавливаются в общем graceful shutdown (`GracefulStop`, а не `Stop`).
- HTTP и gRPC вызывают одни и те же usecase. Бизнес-логика, валидация
  бизнес-правил и доступ к репозиториям между транспортами не дублируются.
- Конвертация proto ↔ доменная модель лежит в gRPC-слое. Доменные структуры не
  получают protobuf-тегов, сгенерированные типы не протекают в usecase.
- Обязательные interceptor'ы: `recover`, логирование, трассировка, метрики.
- Включён `grpc_health_v1` health check и reflection (чтобы можно было ходить
  `grpcurl`'ом).

HTTP-транспорт остаётся и продолжает работать. Ручки не удаляем.

### 5.2. Перевод Push Service на gRPC

Меняется **только** реализация гейтвея: интерфейс, объявленный в лабораторной работе 3, остаётся
прежним, usecase и пул воркеров не правятся.

- клиент создаётся один раз при старте, соединение переиспользуется;
- таймаут на вызов — `PUSH_REQUEST_TIMEOUT`, через `context.WithTimeout`;
- коды `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED` различаются в
  логах и метриках;
- HTTP-реализация гейтвея либо удаляется, либо остаётся и выбирается по env —
  на ваше усмотрение, но выбор описывается в README.

Если лабораторная работа 2 сделана правильно, диффа в `internal/usecase` в этом
пункте не будет вообще. Проверяющий на это посмотрит.

### 5.3. Producer

- Публикация происходит при успешном завершении поездки.
- Формат — JSON, ключ — `trip_id`.
- `event_id` — UUID, генерируется один раз на событие.
- Ошибка публикации логируется уровнем `Error` и учитывается в
  `tripgo.events.published{result="error"}`, но **не** приводит к откату уже
  завершённой поездки: HTTP-клиент должен получить `200`.
- Из этого следует, что событие может потеряться. Это известная проблема, её
  закрывает вариант A в лабораторной работе 5 (transactional outbox). В README
  опишите, где теряется событие.

### 5.4. Consumer

- Consumer-группа `trip-service`, топик `trip.commands.v1`.
- Оффсеты коммитим вручную и только после успешной обработки, автокоммит не
  используем.
- Идемпотентность: создание поездки и вставка `command_id` в `processed_commands`
  идут в одной транзакции через `TxManager`. Повторная доставка того же
  `command_id` не создаёт вторую поездку и учитывается как
  `tripgo.commands.consumed{result="duplicate"}`.
- Не смогли обработать — сообщение уезжает в DLQ, оффсет коммитим. Ретраев в
  этой работе нет: причины ошибки не разбираем, повторов не делаем, см. п. 5.7.
- Обработка идёт с ограниченным параллелизмом: партиции обрабатываются
  независимо, внутри одной партиции — по порядку.
- Consumer останавливается по общему shutdown, дорабатывая текущее сообщение.

### 5.5. DLQ

- Топик `trip.commands.v1.dlq`.
- Сообщение уезжает как есть, плюс заголовки: `dlq.reason`, `dlq.error`,
  `dlq.original_topic`, `dlq.original_partition`, `dlq.original_offset`,
  `dlq.occurred_at`.
- Отправка в DLQ логируется уровнем `Error`.
- Сообщение, которое не удалось обработать, нельзя оставлять в партиции и
  пытаться снова и снова: оффсет не двинется, и вся партиция встанет.

### 5.6. Как класть команды в топик

Отдельную утилиту писать не надо. Сообщения в `trip.commands.v1` кладём руками
через Redpanda Console — веб-интерфейс по URL из `tripgoctl connect`, он умеет
публиковать в топик. Там же смотрим, что уехало в `trip.events.v1` и в DLQ.

Понадобится три сценария:

- валидная команда — по ней создаётся поездка;
- та же команда с тем же `command_id` ещё раз — второй поездки быть не должно;
- заведомо битое сообщение — уезжает в DLQ и не блокирует партицию.

### 5.7. Упрощения

1. **Ретраев нет.** В DLQ уезжает любая необработанная команда, в том числе та,
   что не прошла из-за моргнувшей бд: валидное сообщение теряется, хотя со второй
   попытки прошло бы. В проде сначала ретраят с backoff и только потом сдаются.
   Механизм backoff вы напишете в лабораторной работе 5 и сможете вернуться сюда
   и доделать.
2. **События в JSON, без схемы с проверкой совместимости.** Продюсер может
   поменять тип поля, и узнает об этом потребитель в рантайме. Поэтому входящее
   сообщение обязательно валидируем.

### 5.8. Конфигурация

```
GRPC_ADDR=:9091
PUSH_GRPC_ADDR=<генерируется tripgoctl в .env>
PUSH_REQUEST_TIMEOUT=1s
BROKER_BROKERS=<генерируется tripgoctl в .env>
TRIP_EVENTS_TOPIC=trip.events.v1
TRIP_COMMANDS_TOPIC=trip.commands.v1
TRIP_COMMANDS_DLQ_TOPIC=trip.commands.v1.dlq
CONSUMER_GROUP=trip-service
```

## 7. Тесты

Обязательные сценарии:

1. каждый gRPC-метод: успех и все коды ошибок из таблицы п. 4.1;
2. конвертация proto ↔ домен в обе стороны, включая `nil` и нулевые времена;
3. usecase не изменился при переводе push-гейтвея на gRPC — старые тесты
   проходят без правок;
4. producer формирует событие с правильными ключом, заголовками и телом;
5. consumer создаёт поездку по валидной команде;
6. повторная доставка того же `command_id` не создаёт вторую поездку;
7. битое сообщение уезжает в DLQ с заполненными заголовками и не блокирует
   обработку следующих;
8. интеграционный: команда, отправленная в реальный топик, приводит к появлению
   поездки в БД.

Для интеграционных тестов поднимайте брокер через `testcontainers-go` либо
используйте окружение из `tripgoctl environment start` под билд-тегом.

## 8. Как проверить себя

```bash
make generate && make lint && make test && tripgoctl environment start && make run

grpcurl -plaintext localhost:9091 list          # grpcurl: brew install grpcurl
grpcurl -plaintext -d '{"trip_id":"'$TRIP_ID'"}' localhost:9091 tripgo.trip.v1.TripService/GetTrip

# событие о завершении
curl -sS -X POST localhost:8080/api/v1/trips/$TRIP_ID/finish
# rpk идёт с Redpanda, готовые команды печатает tripgoctl connect
rpk topic consume trip.events.v1 --num 1 --brokers "$BROKER_BROKERS"

# команду в trip.commands.v1 кладём через Redpanda Console: URL из `tripgoctl connect`
# 1) валидная — появилась поездка
# 2) та же с тем же command_id — второй поездки быть не должно
# 3) битая — уехала в DLQ:
rpk topic consume trip.commands.v1.dlq --num 1 --brokers "$BROKER_BROKERS"

rpk group describe trip-service --brokers "$BROKER_BROKERS" # лаг должен уходить в ноль
```

Проверьте также:

- gRPC и HTTP на одной поездке возвращают одинаковые данные;
- остановка брокера не роняет сервис: HTTP-ручки продолжают отвечать, consumer
  переподключается после возврата брокера;
- лаг consumer-группы уходит в ноль после обработки.

### Сквозная трассировка

В лабораторной работе 2 трейс живёт внутри одного HTTP-запроса. Здесь вызовов
несколько и они разнесены во времени: публикация события и его обработка
происходят в разных горутинах, а то и в разных процессах. Задание — связать их в
один трейс.

Что нужно сделать:

- пробросить контекст через `W3C TraceContext`: в gRPC метаданными, в Kafka
  заголовками сообщения;
- producer создаёт спан `publish` с атрибутом `messaging.destination.name` и
  записывает в заголовки текущий контекст;
- consumer достаёт контекст из заголовков и продолжает трейс, а не начинает
  новый.

Результат: в Jaeger по одному `trace_id` видна цепочка
`publish → consume → создание поездки в бд`. Ручной проброс `trace_id` строкой в
теле сообщения не засчитывается, при нём теряется связь со спанами.

Метод-заготовка закомментирован в `contracts/proto/trip/v1/trip_service.proto`.
Клиент подписывается на поездку и получает координаты по мере их сохранения, а не
опрашивает ручку в цикле.

Что нужно сделать:

1. Раскомментировать метод в proto и сгенерировать код.
2. Связать сохранение координаты и открытые потоки: сохранили точку — она ушла
   подписчикам.
3. Закрывать поток при завершении поездки, при отвале клиента и при остановке
   сервиса.

Требования:

- подписчиков у одной поездки может быть несколько, и координату получают все;
- медленный клиент не тормозит остальных и не копит память бесконечно: у каждого
  подписчика свой буфер, при переполнении соединение закрывается;
- после `finish` поток закрывается, а не висит;
- `goleak` чистый: на каждого отвалившегося клиента не остаётся горутины;
- есть тесты на подписку, на закрытие по завершении поездки и на медленного
  клиента.

Это тот же механизм, что в варианте C лабораторной работы 5, только по gRPC
вместо WebSocket.
