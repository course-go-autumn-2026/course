## 1. Контекст

Функционально сервис готов. Осталось сделать так, чтобы он нормально переживал
проблемы у соседей.

Push Service в нашем окружении умеет отвечать медленно, отдавать `503` и
ограничивать нагрузку. Настройте его через поддерживаемый admin API, посмотрите,
что станет с worker pool, а после проверки сбросьте настройки:

```bash
curl -fsS -X POST "$PUSH_ADMIN_URL/admin/behaviour" \
  -H 'content-type: application/json' -d '{"fail_rate":0.5}'
# проверка сервиса
curl -fsS -X POST "$PUSH_ADMIN_URL/admin/behaviour" \
  -H 'content-type: application/json' -d '{"fail_rate":0,"latency_ms":0}'
```

Сейчас каждая неудача — это просто потерянная команда, а если добавить ретраи
без ограничений, четыре воркера добьют и без того лежащий сервис.

Работа состоит из обязательной части, её делают все, и одного варианта на
выбор.

**Что будет уметь сервис.** Переживать медленного и падающего соседа: повторять
вызовы с растущей задержкой, не превышать заданную частоту обращений и не
занимать воркеров бессмысленным ожиданием. Плюс то, что даёт выбранный вариант —
гарантированную доставку событий, кеш или обновления клиенту по WebSocket.

## 2. Обязательная часть — устойчивость исходящих вызовов

### 2.1. Retry с экспоненциальным backoff

Применяется к вызовам Push Service и к публикации в Kafka.

Требования:

- задержка растёт экспоненциально: `initial × multiplier^attempt`, но не выше
  `max`;
- обязателен jitter, то есть случайная составляющая задержки. Без него все
  воркеры ретраятся синхронно и бьют по сервису волнами;
- число попыток ограничено `max_attempts`;
- ожидание учитывает контекст: отмена или дедлайн прекращают ретраи сразу,
  поэтому ждём через `select` по `ctx.Done()`, а не `time.Sleep`;
- ретраим только те ошибки, которые имеет смысл повторять: таймауты, `5xx` /
  `UNAVAILABLE`, `429` / `RESOURCE_EXHAUSTED`. `4xx` и `INVALID_ARGUMENT` не
  ретраим никогда, на защите спросим почему;
- при `429` с заголовком `Retry-After` используется указанная в нём задержка,
  а не своя;
- механизм оформлен переиспользуемым, а не скопирован в двух местах.

Конфигурация:

```
PUSH_RETRY_MAX_ATTEMPTS=3
PUSH_BACKOFF_INITIAL=100ms
PUSH_BACKOFF_MAX=2s
PUSH_BACKOFF_MULTIPLIER=2.0
PUSH_BACKOFF_JITTER=0.2
```

Суммарное время всех попыток не должно превышать бюджет задачи. Если
`PUSH_REQUEST_TIMEOUT=1s`, а три ретрая занимают 5 секунд, то воркер занят 5
секунд и пул из четырёх воркеров перестаёт справляться. Поэтому заводим общий
дедлайн на задачу.

### 2.2. Rate limiter на исходящие вызовы

Ограничивает частоту обращений **вашего** сервиса к Push Service.

Требования:

- алгоритм token bucket, реализованный вами. `golang.org/x/time/rate`
  использовать нельзя, лимитер надо написать самим и уметь объяснить, как он
  работает. Библиотечную реализацию можно взять как эталон для сравнения в
  тестах;
- параметры из env: `PUSH_RATE_LIMIT_RPS`, `PUSH_RATE_LIMIT_BURST`;
- лимитер потокобезопасен: его дёргают все воркеры одновременно;
- ожидание токена уважает контекст и не превращается в вечную блокировку;
- что делать при исчерпании лимита, выбираете вы: ждать в пределах дедлайна
  задачи или сразу отклонять. Выбор описываем в README с обоснованием;
- решения считаются в `tripgo.ratelimit.decisions{result}`.

### 2.3. Тесты обязательной части

- backoff: последовательность задержек соответствует формуле, jitter попадает в
  заданный коридор, отмена контекста прерывает ожидание, неретраибельная ошибка
  не ретраится;
- limiter: при `rps=10` за секунду проходит ~10 запросов; burst работает;
  конкурентные вызовы не ломают счётчик (проверяется с `-race`);
- тесты **детерминированные**: время подменяемо, реальных задержек тесты не
  ждут.

## 3. Вариант на выбор

### Вариант A. Transactional Outbox

**Что чиним:** в лабораторной работе 4 событие `TripCompletedEvent` теряется,
если бд зафиксировала завершение поездки, а публикация упала. Outbox закрывает
эту проблему.

**Что сделать:**

1. Миграция с таблицей `outbox_events` — состав полей в
   [`contracts/schema.md`](../../contracts/schema.md).
2. Завершение поездки пишет событие в `outbox_events` **в той же транзакции**,
   что и обновление `trips`. Прямая публикация в брокер из usecase убирается.
3. Фоновый publisher — в `internal/worker/outbox/`. Раз в `OUTBOX_POLL_INTERVAL`
   выбирает неопубликованные
   события пачками по `OUTBOX_BATCH_SIZE`, публикует, проставляет
   `published_at`.
4. Выборка идёт `FOR UPDATE SKIP LOCKED` — несколько реплик не берут одно
   событие дважды. Как это выглядит в запросе —
   [`contracts/sql/queries.md`](../../contracts/sql/queries.md).
5. Ошибка публикации увеличивает `attempts`, пишет `last_error` и откладывает
   следующую попытку через `next_attempt_at` по тому же backoff, что и в п. 2.1.
6. Порядок событий по одной поездке сохраняется.
7. Метрики: `tripgo.outbox.pending`, `tripgo.outbox.published{result}`,
   `tripgo.outbox.age`.

**Тесты:** событие появляется в outbox в одной транзакции с завершением;
падение брокера не теряет событие; после возврата брокера событие уезжает;
две параллельные реплики publisher'а не публикуют одно событие дважды.

**Проверка:** завершить поездку при остановленном брокере — в `outbox_events`
запись с `published_at IS NULL`; поднять брокер — событие уехало,
`published_at` проставлен.

### Вариант B. In-memory cache

**Что чиним:** `GET /api/v1/trips/{tripId}` дёргают на каждый экран приложения, и
каждый вызов идёт в бд.

**Что сделать:**

1. Кеш поездок в памяти — в `internal/infra/cache/`, шардированный на
   `CACHE_SHARDS` бакетов по хешу ключа.
   Один мьютекс на весь кеш не подходит, на защите спросим почему.
2. TTL на запись (`CACHE_TTL`) и ограничение размера (`CACHE_MAX_ENTRIES`) с
   вытеснением по LRU.
3. Явная инвалидация при любом изменении поездки: завершение, сохранение
   координаты, создание по команде из Kafka. Только TTL не засчитывается.
4. Защита от cache stampede: при промахе по одному ключу в базу идёт **один**
   запрос, остальные ждут его результата (single-flight, написанный вами).
5. Фоновая очистка протухших записей — без утечки памяти и без горутины на
   запись.
6. Метрики: `tripgo.cache.requests{result}`, `tripgo.cache.size`,
   `tripgo.cache.evictions{reason}`.

**Тесты:** попадание и промах; инвалидация при изменении; истечение TTL;
вытеснение по размеру; single-flight — 100 конкурентных промахов по одному
ключу дают один вызов репозитория (с `-race`).

**Проверка:** обстрелять `GET` одной поездки, посмотреть hit rate и падение
`db.client.operation.duration`; завершить поездку и убедиться, что следующий
`GET` отдаёт `completed`, а не устаревшие данные.

### Вариант C. WebSocket для водителя

**Что делаем:** приложение водителя сейчас не знает о событиях поездки, пока само
не сходит в API. Добавляем канал, по которому сервис шлёт обновления сам.

**Что сделать:**

1. Эндпоинт `GET /ws/v1/drivers/{driverId}` — контракт в
   `contracts/asyncapi/driver-updates.asyncapi.yaml`. Хаб соединений кладём в
   `internal/ws/`.
2. Сообщения `trip.created` и `trip.completed` доставляются подписанным
   водителям.
3. Hub соединений: регистрация, отписка, рассылка. Соединение, закрытое
   клиентом, гарантированно убирается.
4. У каждого соединения свой буфер исходящих сообщений на
   `WS_CLIENT_BUFFER_SIZE` сообщений. Медленный клиент не должен блокировать
   остальных: при переполнении буфера соединение закрываем и инкрементим
   `tripgo.ws.slow_clients`.
5. Ping/pong раз в `WS_PING_INTERVAL` и таймаут записи `WS_WRITE_TIMEOUT` —
   мёртвые соединения отваливаются, а не висят вечно.
6. При остановке сервиса все соединения закрываются корректным close-фреймом.
7. Метрики: `tripgo.ws.connections`, `tripgo.ws.messages.sent{result}`,
   `tripgo.ws.slow_clients`.

**Тесты:** подключение и получение события; отключение убирает соединение из
hub'а; медленный клиент отваливается и не влияет на остальных; остановка
сервиса закрывает соединения; `-race` и `goleak` чистые.

**Проверка:** консольным клиентом WebSocket — например `websocat`
(`brew install websocat`): `websocat ws://localhost:8080/ws/v1/drivers/$DRIVER_ID`, затем
создать и завершить поездку этого водителя — сообщения приходят.

## 6. Со звёздочкой

| Задание | Баллы |
|---|---|
| Circuit breaker на вызовах Push Service | +1 |

Backoff и rate limiter ограничивают темп, но всё равно продолжают ходить к
лежащему соседу: каждый вызов занимает воркера на таймаут и заканчивается
ошибкой. Circuit breaker даёт быстрый отказ — пока сосед не отвечает, вызовы
отклоняются сразу, не занимая ни воркера, ни сети.

Три состояния и переходы между ними:

| Состояние | Поведение |
|---|---|
| `closed` | вызовы идут, считаем ошибки |
| `open` | вызовы отклоняются сразу, сеть не трогаем |
| `half-open` | пропускаем несколько пробных вызовов |

Что проверяем:

- пороги настраиваются через env: сколько ошибок нужно для открытия, пауза до
  `half-open`, сколько успехов нужно, чтобы закрыться;
- состояние общее для всех воркеров и защищено от гонок;
- переходы видны в метрике, по ней понятно, когда брейкер открывался;
- в `open` воркер освобождается сразу, а задача учитывается как неуспешная;
- есть тест на полный цикл `closed → open → half-open → closed` и на то, что
  неудачная проба в `half-open` возвращает брейкер в `open`;
- тест детерминированный, время подменяемо.

Проверить руками: через `POST $PUSH_ADMIN_URL/admin/behaviour` задайте
`{"fail_rate":1.0}` и убедитесь, что после нескольких неудач вызовы перестают
уходить в сеть. Затем отправьте `{"fail_rate":0,"latency_ms":0}` и убедитесь,
что брейкер сам закрывается.
