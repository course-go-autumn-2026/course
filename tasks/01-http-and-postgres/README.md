## Окружение

Скопируйте [`environment.toml`](environment.toml) в корень своего репозитория и

Что внутри окружения и что делать, если не поднялось —

## 1. Контекст

Репозиторий пустой. Контракт первых трёх ручек уже согласован с мобильной
командой, схема данных тоже согласована, всё лежит в `contracts/` и меняться не
будет.

Надо сделать работающий сервис: поднять веб-сервер, накатить миграции, научиться
писать и читать данные через `pgx` и реализовать свой менеджер транзакций.

## 2. Цель

**Что будет уметь сервис.** Принимать HTTP-запросы по контракту, создавать
поездку, отдавать её и завершать. Данные лежат в PostgreSQL, схема накатывается
миграциями, создание поездки атомарно пишет в две таблицы. Сервис читает
конфигурацию из окружения и корректно останавливается по сигналу.

**Что на этом отрабатываем:**

- собирать сервис по структуре из `conventions.md` и конфигурировать его через
  окружение;
- поднимать HTTP-сервер, роутить запросы и корректно его останавливать;
- работать по подходу API-first: контракт первичен, код генерируется из него;
- выполнять запросы и транзакции в PostgreSQL через `pgx`;
- строить SQL безопасно, через билдер, а не конкатенацией;
- управлять транзакцией так, чтобы бизнес-код о ней не знал.

## 3. Что нужно сделать

1. **Создать структуру репозитория** по разделу 8 [`conventions.md`](../../docs/conventions.md).
   Инициализировать модуль через `go mod init`, добавить `.gitignore`,
   `.env.example`, `Makefile`. `go.mod` и `go.sum` коммитим. Подробнее про
   module path и что класть в `.gitignore` —
   [`getting-started.md`](../../docs/getting-started.md), п. 1.

2. **Сделать конфигурацию из окружения.** Все параметры — из env, обязательные
   проверяются на старте. За основу возьмите `config/trip-service.env.example`;
   для этой работы нужны `HTTP_ADDR`, `DATABASE_URL`, `LOG_LEVEL`,
   `SHUTDOWN_TIMEOUT` и параметры пула.

3. **Поднять HTTP-сервер** на `net/http` с роутером `chi`. Реализовать
   `/health` и `/ready`, настроить таймауты сервера (`ReadTimeout`,
   `ReadHeaderTimeout`, `WriteTimeout`, `IdleTimeout`) и graceful shutdown по
   `SIGINT` / `SIGTERM`. Без таймаутов одно зависшее соединение держит
   горутину и файловый дескриптор бесконечно.

4. **Сгенерировать код по OpenAPI.** Взять
   `contracts/openapi/trip-service.openapi.yaml`, ограничиться операциями
   `createTrip`, `getTrip`, `finishTrip`, `health`, `ready` и сгенерировать
   типы и серверные интерфейсы. Кодогенерация обязательна, писать структуры
   запросов и ответов руками нельзя: иначе код и контракт разъезжаются — поле
   переименовали в yaml, а в структуре забыли, и об этом узнает клиент.

   Ставим инструмент в модуль и генерируем:

   ```bash
   go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen

   go tool oapi-codegen \
     -generate types,chi-server \
     -package api \
     -o internal/generated/api.gen.go \
     contracts/openapi/trip-service.openapi.yaml
   ```

   Команду кладём в `Makefile` под цель `generate` или в `//go:generate`.
   Сгенерированный код коммитим, но руками не правим: он перезаписывается.

5. **Написать миграции**: таблицы `trips` и `trip_status_history` по
   требованиям п. 4.2. Обе миграции обязаны применяться и откатываться.

6. **Подключить PostgreSQL** через `pgxpool`. Из env берём `DATABASE_URL`,
   размер пула (`DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS`), таймауты
   (`DATABASE_CONNECT_TIMEOUT`, `DATABASE_QUERY_TIMEOUT`) и время жизни
   соединения (`DATABASE_MAX_CONN_LIFETIME`). На старте выполняется `Ping`, при
   недоступности бд сервис не стартует.

7. **Реализовать репозитории** на `pgx` + `squirrel`.

8. **Реализовать менеджер транзакций** — см. п. 6.3. Создание поездки должно
   писать в `trips` и `trip_status_history` **атомарно**.

9. **Реализовать три ручки** по контракту, включая коды ошибок и формат
   `application/problem+json`.

### 4.1. HTTP

Источник истины — `contracts/openapi/trip-service.openapi.yaml`. В этой работе
реализуются:

| Метод | Путь | Ответы |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, `400`, `409`, `500` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, `400`, `404`, `500` |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, `400`, `404`, `409`, `500` |
| `GET` | `/health` | `200` |
| `GET` | `/ready` | `200`, `503` |

Создание поездки:

```http
POST /api/v1/trips
Content-Type: application/json

{
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": { "latitude": 59.9398, "longitude": 30.3146 },
  "end_point":   { "latitude": 59.9290, "longitude": 30.3626 },
  "price": 1450
}
```

```http
HTTP/1.1 201 Created
Location: /api/v1/trips/1f0a9c62-4a1c-4f2e-9d33-2a4bb0f0b111
Content-Type: application/json

{
  "id": "1f0a9c62-4a1c-4f2e-9d33-2a4bb0f0b111",
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": { "latitude": 59.9398, "longitude": 30.3146 },
  "end_point":   { "latitude": 59.9290, "longitude": 30.3626 },
  "price": 1450,
  "status": "active",
  "started_at": "2026-08-24T12:00:00Z",
  "finished_at": null,
  "last_position_at": null
}
```

Цену передаём и храним в целых рублях: `"price": 1450` — это 1450 ₽. В проде так
делать не стоит, деньги обычно хранят в минимальных единицах, то есть в копейках
целым числом (`145000`), либо оборачивают в отдельный тип вроде
`model.Money{ pennies int64 }`. Тогда не теряется копеечная часть и не надо
округлять при пересчётах. Для MVP копейки нам не нужны, поэтому храним рубли, а в
бд это `bigint`. Float для денег не используем ни в каком виде.

Ошибки отдаём по RFC 9457 в `application/problem+json` — это стандарт на тело
ошибки для HTTP API, пришедший на смену RFC 7807. Схема `Problem` лежит в
контракте, поля такие:

| Поле | Что в нём |
|---|---|
| `type` | URI, обозначающий вид ошибки. По ссылке ничего открывать не нужно, это идентификатор |
| `title` | короткое имя вида ошибки, одинаковое для всех случаев одного `type` |
| `status` | HTTP-код, дублирует статус ответа |
| `detail` | что случилось в этом конкретном запросе, текст для человека |
| `instance` | путь запроса, на котором ошибка произошла |
| `code` | наше расширение стандарта: стабильный машиночитаемый код |

RFC разрешает добавлять свои поля, `code` — одно из них. Клиенты принимают
решения по нему, а не по `title` или `detail`: те могут поменяться, `code` нет.

Коды этой работы:

| HTTP | `code` | Когда |
|---|---|---|
| `400` | `invalid_request` | не прошла валидация тела или `tripId` не UUID |
| `404` | `trip_not_found` | поездки с таким `id` нет |
| `409` | `trip_completed` | попытка завершить уже завершённую поездку |
| `409` | `driver_busy` | у водителя уже есть активная поездка |
| `409` | `idempotency_conflict` | только для задания со звёздочкой, см. п. 10 |
| `500` | `internal_error` | всё остальное |

```json
{
  "type": "https://tripgo.example/problems/driver-busy",
  "title": "Driver busy",
  "status": 409,
  "detail": "Driver already has an active trip",
  "code": "driver_busy",
  "instance": "/api/v1/trips"
}
```

Получение поездки:

```http

```

```http

{
  "id": "1f0a9c62-4a1c-4f2e-9d33-2a4bb0f0b111",
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": { "latitude": 59.9398, "longitude": 30.3146 },
  "end_point":   { "latitude": 59.9290, "longitude": 30.3626 },
  "price": 1450,
  "status": "active",
  "started_at": "2026-08-24T12:00:00Z",
  "finished_at": null,

}
```

Завершение поездки — тело запроса пустое, в ответе та же поездка со статусом


### 4.2. Схема данных

В этой работе нужны две таблицы: `trips` и `trip_status_history`. Состав полей,
типы и ограничения — в [`contracts/schema.md`](../../contracts/schema.md).
Миграции пишете сами, `CREATE TABLE` оттуда можно перенести как есть.

Журнал `trip_status_history` заполняется при каждом изменении статуса, включая
создание поездки, и в той же транзакции, что и сама поездка.

Одно ограничение в `schema.md` намеренно не дано и его надо придумать: у одного
водителя не может быть двух активных поездок. Оно должно держаться при
одновременных запросах — два параллельных создания на одного водителя дают одну
поездку и одну ошибку.

Всё, что можно закрепить ограничением бд, закрепляем в ней: код можно обойти,
ограничение нет.

## 5. Бизнес-правила

1. `POST /api/v1/trips` создаёт поездку в статусе `active`, `started_at = now()`
   на стороне сервиса, `finished_at = NULL`. `id` генерирует сервис, из запроса
   он не принимается: клиент не может задать `id` поездки.
2. Валидация запроса: `user_id` и `driver_id` — непустые UUID, координаты в
   допустимых диапазонах, `price >= 0`. Неизвестные поля в теле запрещены
   (`additionalProperties: false` в контракте).
3. У одного водителя не может быть двух активных поездок, иначе `409`
   `driver_busy`. Правило должно держаться под конкурентной нагрузкой: два
   одновременных запроса на одного водителя дают одну поездку и одну ошибку.
4. `POST /finish` переводит `active → completed` и проставляет
   `finished_at = now()`. Повторный вызов — `409` `trip_completed`. Поездки
   нет — `404` `trip_not_found`.
5. Завершение должно быть безопасным при конкурентном вызове: два одновременных
   `finish` дают один `200` и один `409`, `finished_at` не перезаписывается.
6. `GET /trips/{tripId}` возвращает поездку целиком.
7. `/health` отвечает `200`, пока процесс жив, и **не** ходит в бд. `/ready`
   проверяет доступность бд и отвечает `503`, если она недоступна. Обе ручки
   отдают `application/json` со схемой `HealthResponse` из контракта — и в
   успешном случае, и в ошибочном. `problem+json` для них не используется:
   их читает оркестратор, ему хватает статуса.

## 6. Требования к реализации

### 6.1. HTTP

- Роутинг — `chi`, пути как в контракте.
- Валидация входных данных до бизнес-логики.
- Ответ всегда имеет корректный `Content-Type`: `application/json` для успеха,
  `application/problem+json` для ошибок.

### 6.2. Работа с БД

- Только `pgxpool`, никаких глобальных переменных с пулом.
- SQL собирается `squirrel` с плейсхолдерами `$N`.
- Нарушение уникального индекса распознаётся по коду ошибки PostgreSQL `23505`
  и превращается в доменную ошибку, а не в `500`.
- Завершение поездки — одним запросом с условием в `WHERE`, а не «прочитали,
  проверили в Go, записали»:

```sql
UPDATE trips
SET status = 'completed', finished_at = $2, updated_at = now()
WHERE id = $1 AND status = 'active'
RETURNING *;
```

Ноль затронутых строк означает, что поездки нет или она уже завершена. Эти
случаи надо различить дополнительным чтением, чтобы отдать правильный код.

### 6.3. Менеджер транзакций

Бизнес-код не должен знать про `pgx`, транзакции и пулы. Делаем менеджер с таким
интерфейсом:

```go
type TxManager interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}
```

Требования:

- `Do` открывает транзакцию, кладёт её в `context` и вызывает `fn` с уже
  обогащённым контекстом;
- `fn` вернула `nil` → `COMMIT`; вернула ошибку или паникнула → `ROLLBACK`
  и проброс наружу;
- репозиторий достаёт исполнителя из контекста: есть транзакция — работает
  через неё, нет — через пул. **Транзакция не передаётся аргументом метода
  репозитория**;
- вложенный `Do` внутри `Do` переиспользует ту же транзакцию, а не открывает
  вторую;
- уровень изоляции задаётся при старте транзакции в `Do`. Какой выбрали по
  умолчанию и почему — опишите в README своего сервиса.

Создание поездки выполняется внутри одного `Do`: `INSERT` в `trips` и `INSERT` в
`trip_status_history`. Чтобы проверить атомарность, уроните вторую вставку и
убедитесь, что в `trips` ничего не осталось.

## 7. Как проверить себя

```bash
tripgoctl environment start && make migrate && make run

# создание
curl -sS -X POST localhost:8080/api/v1/trips \
  -H 'content-type: application/json' \
  -d '{"user_id":"5cb72c04-7650-45c9-a79b-bcdba0631e0c",
       "driver_id":"8860b315-ec86-42eb-a17c-7c163d721ff5",
       "start_point":{"latitude":59.9398,"longitude":30.3146},
       "end_point":{"latitude":59.9290,"longitude":30.3626},
       "price":1450}' | jq

# повтор на том же водителе — ожидаем 409 driver_busy
# получение
curl -sS localhost:8080/api/v1/trips/$TRIP_ID | jq
# завершение и повторное завершение — 200, затем 409 trip_completed
curl -sS -X POST localhost:8080/api/v1/trips/$TRIP_ID/finish -i
```

Обязательно проверьте:

- `goose down` откатывает обе миграции;
- `/ready` отдаёт `503`, если остановить PostgreSQL, и снова `200` после старта;
- по `SIGTERM` сервис дожидается текущего запроса и выходит за
  `SHUTDOWN_TIMEOUT`;
- в БД после падения второй вставки не остаётся «висящей» поездки;
- конкурентная гонка:

```bash
# 20 одновременных попыток создать поездку одному водителю: ровно один 201
seq 20 | xargs -P20 -I{} curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST localhost:8080/api/v1/trips -H 'content-type: application/json' \
  -d @trip.json | sort | uniq -c
```

## 10. Со звёздочкой

Бонусные баллы сверх шестидесяти. Делать только после того, как основная часть
готова.

| Задание | Баллы |
|---|---|
| Идемпотентность `POST /api/v1/trips` по заголовку `Idempotency-Key`: повторный запрос с тем же ключом и телом возвращает ту же поездку и `200`, с тем же ключом и другим телом — `409 idempotency_conflict` | +1 |
| `Dockerfile` с многостадийной сборкой (итоговый образ на `distroless` или `scratch`, без исходников и тулчейна) и запуск сервиса в окружении рядом с PostgreSQL | +1 |

Запрос для первого задания — тот же `POST /api/v1/trips`, но с заголовком:

```http
POST /api/v1/trips
Content-Type: application/json
Idempotency-Key: 7f1c2a54-6d0e-4a3b-9f21-0c8e5b3a77d1

{
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": { "latitude": 59.9398, "longitude": 30.3146 },
  "end_point":   { "latitude": 59.9290, "longitude": 30.3626 },
  "price": 1450
}
```

Поведение:

| Запрос | Ответ |
|---|---|
| первый с этим ключом | `201`, поездка создана |
| повтор с тем же ключом и тем же телом | `200` и та же поездка, вторая не создаётся |
| тот же ключ, другое тело | `409`, `code = idempotency_conflict` |
| без заголовка | как обычно, `201` |

Ключ генерирует клиент, сервис его не придумывает.

Требования:

- повтор не создаёт вторую поездку;
- ответ на повтор содержит ту же поездку, что и первый, с тем же `id`;
- ключ живёт не вечно: договоритесь, сколько он хранится, и напишите это в
  README сервиса;
- работает при конкурентных запросах: два одновременных запроса с одним ключом
  дают одну поездку, а не две.

Где хранить ключ и как отличать повтор от конфликта — решаете сами.

### Многостадийная сборка

- процесс запускается не от root;
- есть `.dockerignore`, в образ не утекают `.git`, тесты и локальные конфиги;
- сервис поднимается в локальном окружении рядом с PostgreSQL и отвечает на
  `/ready`;
- в README сервиса указан размер итогового образа.
