# Работа с PostgreSQL из Go

Веб-сервис без постоянного хранилища забывает все после перезапуска. Подключение базы данных решает эту проблему, но добавляет новые: соединения надо переиспользовать, ошибки чтения нельзя терять, несколько изменений иногда требуется выполнять атомарно, а схему базы нужно одинаково обновлять на ноутбуках разработчиков и в production.

В этой главе разберем путь SQL-запроса от Go-кода до PostgreSQL. В примерах используется PostgreSQL, нативный драйвер `pgx` пятой версии, его пул `pgxpool`, билдер Squirrel и инструмент миграций goose.

После чтения вы сможете:

- выбрать между `database/sql` и нативным API `pgx`;
- выполнить запрос, который возвращает ноль, одну или несколько строк;
- правильно завершить транзакцию при успехе и при ошибке;
- вынести управление транзакцией из бизнес-кода;
- настроить и оценить размер пула соединений;
- найти по метрикам нехватку соединений и медленные запросы;
- построить динамический запрос без SQL-инъекции;
- объяснить место PgBouncer в инфраструктуре;
- создать, применить и откатить миграцию goose.

## 1. Как Go-приложение общается с PostgreSQL

PostgreSQL обслуживает клиентов через соединения. Установка соединения состоит не только из открытия TCP-сокета: клиент и сервер договариваются о параметрах протокола, выполняют аутентификацию, иногда устанавливают TLS. На сервере соединению соответствует отдельный backend-процесс. Поэтому открывать новое соединение для каждого HTTP-запроса дорого, а держать сколько угодно соединений нельзя.

В обычном сервисе путь выглядит так:

```text
HTTP-запрос -> handler -> service -> repository -> пул -> PostgreSQL
```

Handler разбирает транспортный запрос, service выполняет бизнес-сценарий, repository содержит SQL, а пул выдает физическое соединение на время обращения к базе. Такое разделение не обязательно для маленькой учебной программы, но полезно понимать, где заканчивается бизнес-логика и начинается код хранения данных.

## 2. `database/sql` и `pgx`: это не конкурирующие драйверы

Названия часто смешивают, поэтому сначала разберемся с терминами.

`database/sql` входит в стандартную библиотеку Go. Это общий интерфейс для реляционных баз данных и менеджер пула соединений. Сам пакет не знает протокол PostgreSQL и не может подключиться к серверу без драйвера.

`pgx` — драйвер и набор инструментов именно для PostgreSQL. Его можно использовать двумя способами:

1. Через нативный API `pgx` и пул `pgxpool`.
2. Как драйвер под `database/sql` через пакет `github.com/jackc/pgx/v5/stdlib`.

| Вопрос | `database/sql` + драйвер pgx | Нативный `pgx` |
|---|---|---|
| Какой пул используется | `*sql.DB` | `*pgxpool.Pool` |
| Насколько API привязан к PostgreSQL | Слабо | Явно привязан |
| PostgreSQL-специфичные возможности | Часть доступна через адаптеры | Доступны напрямую: `COPY`, `LISTEN/NOTIFY`, богатая система типов и другие |
| Когда выбирать | Библиотека требует `*sql.DB` или проект поддерживает разные СУБД | Сервис работает только с PostgreSQL |

Универсальный интерфейс сам по себе редко делает смену СУБД простой: SQL-диалекты, типы, DDL и поведение транзакций все равно различаются. Если приложение заведомо работает с PostgreSQL и сторонние библиотеки не требуют `*sql.DB`, разумный выбор — нативный `pgx`.

### Подключение через `database/sql`

```go
import (
	"context"
	"database/sql"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func openDB(ctx context.Context, dsn string) (*sql.DB, error) {
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		return nil, err
	}

	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(5)

	if err := db.PingContext(ctx); err != nil {
		db.Close()
		return nil, err
	}
	return db, nil
}
```

Несмотря на имя, `sql.Open` обычно не устанавливает соединение немедленно. Он создает `*sql.DB`, то есть конкурентно-безопасный объект с пулом внутри. Реальную доступность базы проверяет `PingContext`.

### Подключение через `pgxpool`

```go
import (
	"context"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func newPool(ctx context.Context, dsn string) (*pgxpool.Pool, error) {
	config, err := pgxpool.ParseConfig(dsn)
	if err != nil {
		return nil, fmt.Errorf("parse database config: %w", err)
	}

	config.MaxConns = 20
	config.MinConns = 2
	config.MaxConnLifetime = time.Hour
	config.MaxConnIdleTime = 30 * time.Minute
	config.HealthCheckPeriod = time.Minute

	pool, err := pgxpool.NewWithConfig(ctx, config)
	if err != nil {
		return nil, fmt.Errorf("create database pool: %w", err)
	}

	pingCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
	defer cancel()
	if err := pool.Ping(pingCtx); err != nil {
		pool.Close()
		return nil, fmt.Errorf("ping database: %w", err)
	}

	return pool, nil
}
```

DSN обычно приходит из конфигурации, например `postgres://app:password@localhost:5432/cinema?sslmode=disable`. Пароль нельзя хранить в исходном коде или коммитить в репозиторий. `sslmode=disable` годится для локального контейнера, но не как бездумный production-дефолт.

Пул создают один раз при запуске приложения, передают в репозитории и закрывают во время graceful shutdown:

```go
pool, err := newPool(ctx, dsn)
if err != nil {
	return err
}
defer pool.Close()
```

Нативный `*pgx.Conn` — одно соединение, которое нельзя одновременно использовать из нескольких горутин. Для серверного приложения почти всегда нужен конкурентно-безопасный `*pgxpool.Pool`.

## 3. `Exec`, `QueryRow` и `Query`

Метод выбирают по форме результата, а не только по первому слову SQL-запроса.

| Метод      | Когда использовать          | Что не забыть                                         |
| ---------- | --------------------------- | ----------------------------------------------------- |
| `Exec`     | Запрос не возвращает строки | Проверить ошибку и при необходимости `RowsAffected()` |
| `QueryRow` | Ожидается одна строка       | Обязательно вызвать `Scan`; именно он вернет ошибку   |
| `Query`    | Ожидается несколько строк   | Закрыть `rows`, проверить `Scan` и `rows.Err()`       |

У нативного pgx эти методы сразу принимают контекст. В `database/sql` используйте варианты `ExecContext`, `QueryRowContext` и `QueryContext`. Методы без суффикса `Context` остались в API для совместимости, но серверному коду обычно нужна возможность отмены.

Пусть в базе есть таблица фильмов:

```sql
CREATE TABLE films (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title       text NOT NULL,
    release_date date NOT NULL,
    rating      numeric(3, 1) NOT NULL CHECK (rating BETWEEN 0 AND 10)
);
```

И соответствующая структура:

```go
type Film struct {
	ID          int64
	Title       string
	ReleaseDate time.Time
	Rating      float64
}
```

### `Exec`: строки результата не нужны

`Exec` подходит для `UPDATE`, `DELETE`, DDL и для `INSERT` без `RETURNING`.

```go
func updateRating(
	ctx context.Context,
	pool *pgxpool.Pool,
	filmID int64,
	rating float64,
) error {
	tag, err := pool.Exec(ctx, `
		UPDATE films
		SET rating = $1
		WHERE id = $2
	`, rating, filmID)
	if err != nil {
		return fmt.Errorf("update film rating: %w", err)
	}
	if tag.RowsAffected() == 0 {
		return ErrFilmNotFound
	}
	return nil
}
```

Успешное выполнение SQL еще не означает, что строка существовала. `UPDATE ... WHERE id = $1` может завершиться без ошибки и изменить ноль строк. Если для бизнес-сценария это важно, проверяйте `RowsAffected()`.

Первое слово запроса не определяет метод. `INSERT` с секцией `RETURNING` уже возвращает строку, поэтому для него нужен `QueryRow`:

```go
var filmID int64
err := pool.QueryRow(ctx, `
	INSERT INTO films (title, release_date, rating)
	VALUES ($1, $2, $3)
	RETURNING id
`, title, releaseDate, rating).Scan(&filmID)
if err != nil {
	return 0, fmt.Errorf("insert film: %w", err)
}
```

### `QueryRow`: ожидается одна строка

```go
var ErrFilmNotFound = errors.New("film not found")

func filmByID(
	ctx context.Context,
	pool *pgxpool.Pool,
	filmID int64,
) (Film, error) {
	var film Film
	err := pool.QueryRow(ctx, `
		SELECT id, title, release_date, rating
		FROM films
		WHERE id = $1
	`, filmID).Scan(
		&film.ID,
		&film.Title,
		&film.ReleaseDate,
		&film.Rating,
	)
	if errors.Is(err, pgx.ErrNoRows) {
		return Film{}, ErrFilmNotFound
	}
	if err != nil {
		return Film{}, fmt.Errorf("select film: %w", err)
	}
	return film, nil
}
```

`QueryRow` всегда возвращает объект строки. Ошибка выполнения и отсутствие результата проявятся при `Scan`. Поэтому вызов `QueryRow(...)` без `Scan(...)` почти наверняка является ошибкой программы.

Если запрос случайно вернул несколько строк, `QueryRow` прочитает первую. Запрос должен сам выражать ожидание одной строки, например через уникальный ключ или подходящую агрегацию. `LIMIT 1` не заменяет корректное условие уникальности.

Для `database/sql` код почти такой же, но используются `QueryRowContext` и `sql.ErrNoRows`:

```go
err := db.QueryRowContext(ctx, query, filmID).Scan(&film.ID, &film.Title)
if errors.Is(err, sql.ErrNoRows) {
	return Film{}, ErrFilmNotFound
}
```

### `Query`: ожидается набор строк

```go
func recentFilms(
	ctx context.Context,
	pool *pgxpool.Pool,
	from time.Time,
) ([]Film, error) {
	rows, err := pool.Query(ctx, `
		SELECT id, title, release_date, rating
		FROM films
		WHERE release_date >= $1
		ORDER BY release_date DESC, id DESC
	`, from)
	if err != nil {
		return nil, fmt.Errorf("query recent films: %w", err)
	}
	defer rows.Close()

	films := make([]Film, 0)
	for rows.Next() {
		var film Film
		if err := rows.Scan(
			&film.ID,
			&film.Title,
			&film.ReleaseDate,
			&film.Rating,
		); err != nil {
			return nil, fmt.Errorf("scan film: %w", err)
		}
		films = append(films, film)
	}
	if err := rows.Err(); err != nil {
		return nil, fmt.Errorf("iterate films: %w", err)
	}
	return films, nil
}
```

Здесь три независимые точки отказа:

1. `Query` может не отправить или не начать выполнять запрос.
2. `Scan` может обнаружить несовместимые типы или неожиданное число столбцов.
3. Ошибка сети или сервера может возникнуть посреди чтения; ее вернет `rows.Err()`.

Пока строки не дочитаны и не закрыты, соединение обычно занято. `defer rows.Close()` защищает ранние выходы из функции. После полного прохода `pgx` закрывает `Rows` автоматически, но явный `defer` делает код устойчивее к будущим изменениям.

### Порядок полей и `NULL`

Аргументы `Scan` соответствуют столбцам по позиции. При изменении `SELECT` компилятор не предупредит о забытом поле. Хорошая привычка — перечислять столбцы явно и держать SQL рядом с кодом сканирования. `SELECT *` делает такой контракт хрупким.

Если столбец допускает `NULL`, обычного `string`, `int64` или `time.Time` может быть недостаточно. В `database/sql` есть типы `sql.NullString`, `sql.NullInt64` и другие. В нативном pgx можно использовать указатели или типы пакета `pgtype`. Выбор зависит от смысла: иногда `NULL` лучше превратить в отдельное состояние доменной модели, а не протаскивать тип драйвера до HTTP-слоя.

### Контекст и тайм-аут

Передавайте `context.Context` от входящего запроса до базы. Тогда отмена HTTP-запроса сможет остановить ненужную работу. Для операций с понятным бюджетом времени можно добавить локальный тайм-аут:

```go
queryCtx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
defer cancel()

film, err := filmByID(queryCtx, pool, filmID)
```

Тайм-аут приложения не отменяет необходимости настраивать ограничения на стороне PostgreSQL, например `statement_timeout`. Клиент может потерять сеть как раз в момент отмены, а серверу все равно нужна собственная граница.

### Ошибки запросов и SQLSTATE

Не все ошибки запроса означают одно и то же. Их удобно разделить на несколько групп:

- `pgx.ErrNoRows` означает, что `QueryRow` не нашел строку;
- `context.Canceled` и `context.DeadlineExceeded` говорят об отмене или тайм-ауте;
- `*pgconn.PgError` содержит ошибку, которую вернул PostgreSQL;
- сетевые ошибки, разрыв соединения и ошибки драйвера не относятся к предыдущим группам и обычно остаются внутренними ошибками сервиса.

PostgreSQL присваивает серверным ошибкам пятисимвольный код SQLSTATE. Код стабилен, а текст сообщения может измениться между версиями или зависеть от локализации. Поэтому разбирать `err.Error()` и искать в нем фразу `duplicate key` не следует.

Например, уникальность email задается в схеме:

```sql
CREATE TABLE users (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL,
    CONSTRAINT users_email_unique UNIQUE (email)
);
```

Код репозитория может превратить конкретное нарушение ограничения в понятную прикладную ошибку:

```go
var ErrEmailAlreadyExists = errors.New("email already exists")

func createUser(
	ctx context.Context,
	pool *pgxpool.Pool,
	email string,
) (int64, error) {
	var userID int64
	err := pool.QueryRow(ctx, `
		INSERT INTO users (email)
		VALUES ($1)
		RETURNING id
	`, email).Scan(&userID)
	if err == nil {
		return userID, nil
	}

	if errors.Is(err, context.Canceled) ||
		errors.Is(err, context.DeadlineExceeded) {
		return 0, err
	}

	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) &&
		pgErr.Code == "23505" &&
		pgErr.ConstraintName == "users_email_unique" {
		return 0, ErrEmailAlreadyExists
	}

	return 0, fmt.Errorf("create user: %w", err)
}
```

Проверки одного кода `23505` недостаточно: в таблице может быть несколько уникальных ограничений с разным бизнес-смыслом. `ConstraintName` позволяет понять, какое именно правило было нарушено.

Часто встречаются такие SQLSTATE:

| Код | Условие PostgreSQL | Возможная реакция приложения |
|---|---|---|
| `23502` | `not_null_violation` | Ошибка данных или ошибка программы |
| `23503` | `foreign_key_violation` | Связанный объект не существует либо еще используется |
| `23505` | `unique_violation` | Конфликт с уже существующим объектом |
| `23514` | `check_violation` | Нарушен инвариант из `CHECK` |
| `40001` | `serialization_failure` | Повторить всю транзакцию, если операция допускает повтор |
| `40P01` | `deadlock_detected` | PostgreSQL прервал одну транзакцию; иногда ее можно повторить целиком |

Ограничения базы нужны даже при предварительной проверке в Go. Между запросом «свободен ли email?» и последующим `INSERT` другой обработчик может вставить такой же email. Только `UNIQUE` закроет эту гонку, а приложение обработает полученный `23505`.

Если PostgreSQL вернул ошибку во время транзакции, она обычно переходит в состояние `aborted`: следующие команды будут отклоняться до `Rollback`. Не проглатывайте такую ошибку с намерением продолжить транзакцию. Верните ее из callback менеджера транзакций, чтобы он выполнил rollback. `pgx.ErrNoRows` ведет себя иначе: отсутствие результата у корректного `SELECT` не является ошибкой PostgreSQL и не ломает транзакцию.

Не отправляйте клиенту `pgErr.Message`, `Detail`, SQL и аргументы запроса. Эти данные полезны в закрытых логах, но могут раскрыть схему или пользовательские значения. Внешний слой должен вернуть собственное сообщение и подходящий статус протокола.

## 4. Зачем нужен пул соединений

Один `*pgx.Conn` последовательно обслуживает запросы. Если один запрос ждет диск 100 мс, остальные пользователи того же соединения тоже ждут. Открывать соединение на каждый запрос еще хуже: сервис тратит время на подключение, а PostgreSQL получает постоянный поток новых backend-процессов.

Пул держит несколько соединений и выдает свободное вызывающей горутине. Когда операция завершилась, соединение возвращается в пул. Это дает параллелизм, переиспользует уже установленные соединения и ставит верхнюю границу нагрузки со стороны одного процесса.

Пул не делает медленный SQL быстрым. Если все соединения заняты тяжелыми запросами, следующие горутины будут ждать. Увеличение `MaxConns` иногда лишь переносит очередь из приложения внутрь PostgreSQL и ухудшает ситуацию.

### Как выбрать размер

Число `20` в примере выше не является универсальной настройкой. Начать оценку можно с ограничения:

```text
число экземпляров сервиса × MaxConns
    + соединения фоновых задач
    + соединения администраторов
    < допустимого числа соединений PostgreSQL
```

Дальше настройку проверяют нагрузочным тестом и метриками. Для `pgxpool` полезны число занятых и свободных соединений, длительность ожидания выдачи соединения и количество отмененных ожиданий. Если пул постоянно исчерпан, причина может быть в маленьком лимите, медленных запросах, долгих транзакциях или забытых `Rows`.

Основные параметры `pgxpool.Config`:

- `MaxConns` ограничивает общее число соединений пула;
- `MinConns` поддерживает минимальное число соединений;
- `MaxConnLifetime` периодически заменяет старые соединения;
- `MaxConnIdleTime` закрывает долго простаивающие соединения;
- `HealthCheckPeriod` задает период фоновой проверки.

Не вызывайте `Acquire` без причины. `pool.Query`, `pool.QueryRow` и `pool.Exec` сами берут и возвращают соединение. Явный `Acquire` нужен для работы, привязанной к конкретной сессии, и требует обязательного `Release`:

```go
conn, err := pool.Acquire(ctx)
if err != nil {
	return err
}
defer conn.Release()
```

Транзакция тоже удерживает одно соединение до `Commit` или `Rollback`. Поэтому внутри нее не стоит выполнять сетевые вызовы, ждать пользовательский ввод или запускать долгие вычисления.

## 5. Метрики пула и запросов

Без метрик настройка пула сводится к угадыванию. Когда запрос пользователя занял 700 мс, нужно различать по крайней мере две ситуации: запрос действительно выполнялся в PostgreSQL 700 мс или он 650 мс ждал свободное соединение и выполнился за оставшиеся 50 мс.

`pool.Stat()` возвращает снимок состояния `pgxpool`. Для локальной диагностики его можно вывести в структурированный лог:

```go
func logPoolStats(logger *slog.Logger, pool *pgxpool.Pool) {
	stat := pool.Stat()

	logger.Info("database pool stats",
		"acquired", stat.AcquiredConns(),
		"idle", stat.IdleConns(),
		"total", stat.TotalConns(),
		"max", stat.MaxConns(),
		"acquire_duration", stat.AcquireDuration(),
		"empty_acquire_count", stat.EmptyAcquireCount(),
		"empty_acquire_wait", stat.EmptyAcquireWaitTime(),
		"canceled_acquire_count", stat.CanceledAcquireCount(),
	)
}
```

В работающем сервисе эти значения обычно экспортируют в систему метрик и снимают через равные интервалы. `AcquiredConns`, `IdleConns` и `TotalConns` показывают текущее состояние. `AcquireDuration`, `EmptyAcquireCount`, `EmptyAcquireWaitTime` и `CanceledAcquireCount` накапливаются с момента создания пула, поэтому на графике полезна скорость их изменения или разница между соседними измерениями.

На что смотреть:

| Наблюдение | Вероятная причина |
|---|---|
| `AcquiredConns` долго держится около `MaxConns` | Пул работает на пределе |
| Растут `EmptyAcquireCount` и `EmptyAcquireWaitTime` | Запросы ждут свободное соединение |
| Растет `CanceledAcquireCount` | Контекст успевает завершиться еще во время ожидания пула |
| Соединений хватает, но запросы медленные | Причину надо искать в SQL, блокировках, плане запроса или состоянии PostgreSQL |
| Большая часть соединений постоянно простаивает | Возможно, пул завышен; решение зависит от ожидаемых всплесков нагрузки |

Одних метрик пула мало. Для каждой операции с базой полезно считать:

- количество запросов и ошибок;
- длительность выполнения;
- тип результата: успех, `not_found`, тайм-аут, отмена или ошибка PostgreSQL;
- SQLSTATE для серверных ошибок.

Используйте постоянное имя операции вроде `films.list` или `users.create`. Не помещайте в метки полный SQL, email, идентификатор пользователя или текст ошибки: число различных значений быстро раздует хранилище метрик, а пользовательские данные окажутся там, где их не должно быть.

Собирать длительность можно на границе метода репозитория. Для сквозной инструментализации у pgx есть интерфейс `QueryTracer`: его методы вызываются в начале и в конце `Query`, `QueryRow` и `Exec`. Tracer передается через `config.ConnConfig.Tracer` до создания пула. На этом уровне удобно подключить метрики и распределенную трассировку, не добавляя таймер вручную в каждый метод.

Логировать каждый успешный запрос на уровне `info` обычно слишком шумно. В логах полезнее оставлять ошибки и медленные операции, указывая стабильное имя операции, длительность и SQLSTATE. Аргументы запроса могут содержать пароль, токен или персональные данные, поэтому их автоматическое логирование должно быть отключено или отфильтровано.

Если между приложением и PostgreSQL стоит PgBouncer, появляется еще одна очередь. Метрики локального пула описывают путь только до PgBouncer. Для полной картины понадобятся `SHOW POOLS` и `SHOW STATS` самого PgBouncer, а также метрики PostgreSQL. Иначе свободное соединение в `pgxpool` может создать ложное впечатление, что ожидания нигде нет.

## 6. Транзакции в коде

Транзакция объединяет несколько SQL-команд в одну атомарную операцию: фиксируются все изменения либо ни одно. Типичный пример — перевод денег. Сумму нельзя списать с одного счета, если зачисление на другой не удалось.

В примере деньги хранятся целым числом минимальных денежных единиц. `amount = 1250` означает 12 рублей 50 копеек. Для денег не следует использовать `float64`.

```go
var (
	ErrInvalidAmount   = errors.New("amount must be positive")
	ErrDebitRejected   = errors.New("source account not found or insufficient funds")
	ErrAccountNotFound = errors.New("account not found")
)

func transfer(
	ctx context.Context,
	pool *pgxpool.Pool,
	fromID int64,
	toID int64,
	amount int64,
) error {
	if amount <= 0 {
		return ErrInvalidAmount
	}

	tx, err := pool.BeginTx(ctx, pgx.TxOptions{})
	if err != nil {
		return fmt.Errorf("begin transaction: %w", err)
	}
	defer func() { _ = tx.Rollback(ctx) }()

	tag, err := tx.Exec(ctx, `
		UPDATE accounts
		SET balance = balance - $1
		WHERE id = $2 AND balance >= $1
	`, amount, fromID)
	if err != nil {
		return fmt.Errorf("withdraw: %w", err)
	}
	if tag.RowsAffected() != 1 {
		return ErrDebitRejected
	}

	tag, err = tx.Exec(ctx, `
		UPDATE accounts
		SET balance = balance + $1
		WHERE id = $2
	`, amount, toID)
	if err != nil {
		return fmt.Errorf("deposit: %w", err)
	}
	if tag.RowsAffected() != 1 {
		return ErrAccountNotFound
	}

	if err := tx.Commit(ctx); err != nil {
		return fmt.Errorf("commit transaction: %w", err)
	}
	return nil
}
```

Отложенный `Rollback` нужен на всех ветках с ранним `return` и при panic. После успешного `Commit` повторный `Rollback` вернет ошибку закрытой транзакции, которую здесь можно проигнорировать. Ошибку `Commit` игнорировать нельзя: до успешного ответа от `Commit` приложение не знает, что операция зафиксирована.

Одна команда списания намеренно не различает отсутствующий исходный счет и недостаточный баланс: в обоих случаях изменено ноль строк. Если продукту нужны разные ответы, придется безопасно получить дополнительную информацию, не возвращаясь к схеме «прочитали баланс, затем безусловно записали новый».

Все запросы между `BeginTx` и `Commit` выполняются через `tx`. Такой код неверен:

```go
tx, _ := pool.Begin(ctx)
_, _ = tx.Exec(ctx, firstQuery)
_, _ = pool.Exec(ctx, secondQuery) // вне транзакции, возможно на другом соединении
```

Пул может выдать второму запросу другое соединение. В лучшем случае атомарность будет потеряна, в худшем код упрется в собственные блокировки.

У `database/sql` схема та же: `db.BeginTx`, запросы через `*sql.Tx`, затем `Commit` или `Rollback`. Не отправляйте `BEGIN`, `COMMIT` и `ROLLBACK` строками через `Exec`: библиотека тогда не сможет правильно управлять закрепленным соединением.

Есть одно различие в поведении контекста. В нативном pgx отмена контекста, переданного в `Begin` или `BeginTx`, влияет на команду начала транзакции, но не запускает автоматический rollback позже. Транзакцию все равно необходимо завершить. `BeginFunc` и `BeginTxFunc`, которые используются ниже, берут этот протокол на себя.

### Изоляция и конкурентные изменения

Атомарность не решает все гонки. Два конкурентных обработчика могут прочитать одно значение и затем перезаписать изменения друг друга. В примере выше списание выражено одной атомарной SQL-командой с условием `balance >= $1`, поэтому отдельного чтения баланса нет.

Для других сценариев используют блокировки (`SELECT ... FOR UPDATE`), ограничения базы, версионирование строк или более строгий уровень изоляции. `pgx.TxOptions` позволяет выбрать `ReadCommitted`, `RepeatableRead` или `Serializable`. На строгих уровнях PostgreSQL может отклонить одну из конфликтующих транзакций. Тогда приложение повторяет всю транзакцию, а не отдельный запрос.

Автоматический retry требует осторожности. Callback транзакции может успеть отправить письмо или вызвать другой сервис, а затем получить ошибку сериализации. Повтор такого callback продублирует внешний эффект. Внутри повторяемой транзакции лучше оставлять только работу с базой, а интеграционные события сохранять, например, через transactional outbox.

## 7. Менеджер транзакций

Ручной `Begin` уместен в одной функции. В большом сервисе он быстро начинает повторяться, а бизнес-операция часто затрагивает несколько репозиториев. Если каждый репозиторий сам открывает транзакцию, объединить их действия атомарно не получится.

Менеджер транзакций задает границу на уровне use case и отвечает за технический протокол: начать транзакцию, вызвать функцию, сделать commit или rollback. В `pgx` уже есть надежные функции `BeginFunc` и `BeginTxFunc`, на которых можно построить такой менеджер:

```go
type TxManager struct {
	pool *pgxpool.Pool
}

func NewTxManager(pool *pgxpool.Pool) *TxManager {
	return &TxManager{pool: pool}
}

func (m *TxManager) WithinTransaction(
	ctx context.Context,
	fn func(pgx.Tx) error,
) error {
	err := pgx.BeginTxFunc(ctx, m.pool, pgx.TxOptions{}, fn)
	if err != nil {
		return fmt.Errorf("run in transaction: %w", err)
	}
	return nil
}
```

Чтобы один метод репозитория работал и с пулом, и с транзакцией, ему достаточно узкого интерфейса:

```go
type DBTX interface {
	Exec(
		context.Context,
		string,
		...any,
	) (pgconn.CommandTag, error)
	Query(context.Context, string, ...any) (pgx.Rows, error)
	QueryRow(context.Context, string, ...any) pgx.Row
}

type AccountRepository struct{}

func (r *AccountRepository) Withdraw(
	ctx context.Context,
	db DBTX,
	accountID int64,
	amount int64,
) error {
	tag, err := db.Exec(ctx, `
		UPDATE accounts
		SET balance = balance - $1
		WHERE id = $2 AND balance >= $1
	`, amount, accountID)
	if err != nil {
		return fmt.Errorf("withdraw: %w", err)
	}
	if tag.RowsAffected() != 1 {
		return ErrDebitRejected
	}
	return nil
}
```

Вне транзакции вызывающий код передаст `*pgxpool.Pool`, а внутри — `pgx.Tx`:

```go
func (s *TransferService) Transfer(
	ctx context.Context,
	fromID int64,
	toID int64,
	amount int64,
) error {
	return s.txManager.WithinTransaction(ctx, func(tx pgx.Tx) error {
		if err := s.accounts.Withdraw(ctx, tx, fromID, amount); err != nil {
			return err
		}
		if err := s.accounts.Deposit(ctx, tx, toID, amount); err != nil {
			return err
		}
		return nil
	})
}
```

Так service определяет бизнес-границу транзакции, репозитории не знают, кто ее начал, а менеджер остается местом для метрик, трассировки и явных вариантов `ReadOnly` или `Serializable`.

Есть и другие реализации. Например, текущую транзакцию иногда кладут в `context.Context`, чтобы не добавлять параметр `DBTX`. Это сокращает сигнатуры, но делает зависимость скрытой: по коду метода уже не видно, какой исполнитель запросов используется. Для учебного проекта явный параметр проще читать и тестировать.

Вложенные вызовы требуют отдельного решения. Нельзя бездумно начать независимую внутреннюю транзакцию и ожидать общей атомарности. Нативный pgx умеет псевдовложенные транзакции через savepoint, но менеджер должен явно определить семантику: присоединяться к текущей транзакции, создавать savepoint или запрещать вложение.

## 8. Squirrel: построение динамического SQL

Статический SQL обычно понятнее писать строкой. Билдер полезен, когда части запроса зависят от входных параметров: фильтры, пагинация, набор обновляемых полей.

Squirrel строит SQL и список аргументов. Он не выполняет запрос сам, если ему не передан runner. Для PostgreSQL важно выбрать долларовые плейсхолдеры:

```go
import sq "github.com/Masterminds/squirrel"

var psql = sq.StatementBuilder.PlaceholderFormat(sq.Dollar)
```

Пример динамического запроса с точным сравнением названия. Метод `Where` добавляет условие, а оператор `=` задаёт полное совпадение с учётом регистра:

```go
type FilmFilter struct {
	MinRating *float64
	Search    string
	Sort      string
	Limit     uint64
}

func buildFilmQuery(filter FilmFilter) (string, []any, error) {
	query := psql.
		Select("id", "title", "release_date", "rating").
		From("films")

	if filter.MinRating != nil {
		query = query.Where(sq.GtOrEq{"rating": *filter.MinRating})
	}
	if filter.Search != "" {
		query = query.Where("title = ?", filter.Search)
	}

	orderBy := map[string]string{
		"date":   "release_date DESC, id DESC",
		"rating": "rating DESC, id DESC",
		"title":  "title ASC, id ASC",
	}
	order, ok := orderBy[filter.Sort]
	if !ok {
		order = orderBy["date"]
	}

	limit := filter.Limit
	if limit == 0 || limit > 100 {
		limit = 20
	}

	return query.OrderBy(order).Limit(limit).ToSql()
}
```

При `Search = "matrix"` получится запрос примерно такой формы:

```sql
SELECT id, title, release_date, rating
FROM films
WHERE title = $1
ORDER BY release_date DESC, id DESC
LIMIT 20
```

А отдельный слайс аргументов будет содержать `"matrix"`. При сравнении через `=` символы `%`, `_` и `\` не имеют специального значения, поэтому экранирование шаблона не нужно. Значения всё равно передаются параметрами, а не вставляются в SQL. Выполнение ничем не отличается от обычного запроса:

```go
sqlText, args, err := buildFilmQuery(filter)
if err != nil {
	return nil, fmt.Errorf("build film query: %w", err)
}

rows, err := pool.Query(ctx, sqlText, args...)
```

Билдер не проверяет смысл SQL, наличие таблиц и индексов и не гарантирует хороший план. Сгенерированный запрос по-прежнему нужно читать, тестировать и при проблемах исследовать через `EXPLAIN (ANALYZE, BUFFERS)`.

## 9. SQL-инъекции и границы параметризации

Инъекция появляется, когда данные пользователя становятся частью SQL-кода. Уязвимый вариант:

```go
query := fmt.Sprintf(
	"SELECT id, email FROM users WHERE email = '%s'",
	inputEmail,
)
row := pool.QueryRow(ctx, query)
```

Строка ввода `' OR true --` меняет условие запроса. Возможность выполнить несколько выражений зависит от протокола и настроек драйвера, но защита не должна строиться на этом ограничении: для обхода авторизации достаточно изменить одно условие.

Правильный вариант передает значение отдельно:

```go
row := pool.QueryRow(ctx, `
	SELECT id, email
	FROM users
	WHERE email = $1
`, inputEmail)
```

Драйвер кодирует аргумент как значение протокола. Содержимое `inputEmail` больше не разбирается как SQL-синтаксис.

Параметры работают только для значений. Ими нельзя заменить имя таблицы, столбца, направление сортировки или SQL-оператор:

```sql
ORDER BY $1  -- сортировки по указанному пользователем столбцу не получится
```

Такие части выбирают по белому списку, как `orderBy` в примере Squirrel. Никогда не вставляйте произвольный `sort` из query string в `OrderBy` или `fmt.Sprintf`.

Squirrel помогает не потерять плейсхолдеры в динамическом запросе, но не является автоматической защитой. Эти вызовы все еще опасны, если строка пришла от пользователя:

```go
query.OrderBy(userInput)
query.Where(userInput)
sq.Expr(userInput)
```

Практический минимум защиты:

- все значения передаются параметрами;
- динамические идентификаторы выбираются из белого списка или корректно экранируются средствами драйвера;
- учетная запись приложения имеет только нужные права;
- секреты не попадают в код и логи;
- у запросов есть контекст и разумные тайм-ауты;
- сообщение клиенту не раскрывает внутренний SQL, хотя полная ошибка остается в закрытых логах.

Валидация ввода нужна для бизнес-правил и понятных ошибок, но не заменяет параметры. Адрес электронной почты, прошедший строгую валидацию сегодня, завтра может использоваться в новом запросе без нее. Безопасность должна сохраняться на уровне самого обращения к базе.

## 10. Что такое PgBouncer

`pgxpool` и `sql.DB` находятся внутри одного процесса Go. Если запущено 30 реплик сервиса и у каждой `MaxConns = 20`, они теоретически откроют 600 соединений к PostgreSQL. При большом числе приложений и коротких запросах полезен внешний пулер PgBouncer.

```text
Go-сервисы -> локальные пулы -> PgBouncer -> меньшее число соединений -> PostgreSQL
```

Для приложения PgBouncer выглядит как PostgreSQL: в DSN меняются адрес и порт. Он принимает много клиентских соединений и переиспользует меньший набор серверных соединений.

У PgBouncer есть три режима.

| Режим | Когда серверное соединение возвращается в пул | Ограничения |
|---|---|---|
| `session` | После отключения клиента | Почти полностью сохраняет семантику обычного соединения, но экономия меньше |
| `transaction` | После `COMMIT` или `ROLLBACK` | Между транзакциями клиент может попасть на другой backend; нельзя полагаться на состояние сессии |
| `statement` | После каждого выражения | Многооператорные транзакции запрещены |

Чаще всего интересен `transaction` pooling. Обычные транзакции работают: PgBouncer удерживает одно серверное соединение от `BEGIN` до завершения. Ломается то, что должно жить дольше транзакции: `LISTEN`, session-level advisory locks, некоторые временные таблицы и произвольное состояние через `SET`.

С prepared statements нужна проверка конфигурации, а не старое правило «они никогда не работают». Современный PgBouncer умеет отслеживать protocol-level prepared statements в transaction mode, если `max_prepared_statements` имеет ненулевое значение. SQL-команды `PREPARE` и `DEALLOCATE` в этом режиме по-прежнему несовместимы. Настройки кэша запросов pgx и PgBouncer надо проверять вместе на той версии, которая используется в инфраструктуре.

PgBouncer не отменяет локальный пул. Локальный пул ограничивает конкурентность конкретного процесса и позволяет не держать клиентское соединение к PgBouncer для каждой горутины. Но появляется два уровня лимитов, которые нужно настраивать совместно. PgBouncer также не ускоряет плохой запрос и не заменяет репликацию, резервные копии или failover.

## 11. Миграции схемы

Схема базы меняется вместе с кодом: появляются таблицы и индексы, столбцы получают ограничения, иногда меняется формат данных. Если выполнять эти изменения вручную, окружения быстро расходятся. У одного разработчика столбец уже есть, в CI его нет, а в production команда была выполнена частично и никто не помнит когда.

Миграция — версионированный файл с изменением схемы или данных. Файлы лежат в репозитории рядом с кодом и применяются в определенном порядке. Инструмент хранит в самой базе список уже выполненных версий.

Миграции дают:

- воспроизводимую схему на локальной машине, в тестах и production;
- историю изменений, доступную на code review;
- автоматическое применение только новых версий;
- понятный способ развернуть чистую базу;
- возможность описать откат там, где он действительно безопасен.

### Goose

[goose](https://github.com/pressly/goose) — CLI и Go-библиотека для миграций. Для большинства изменений схемы достаточно SQL-файлов: они видны DBA, не требуют компиляции и не прячут SQL за кодом. Стандартный CLI выполняет SQL-миграции. Для миграций, написанных функциями Go, собирают собственный бинарник goose и регистрируют эти функции в нем.

Установка CLI:

```bash
go install github.com/pressly/goose/v3/cmd/goose@latest
```

Для воспроизводимого CI вместо `@latest` фиксируют конкретную проверенную версию.

Настройка для локального окружения:

```bash
export GOOSE_DRIVER=postgres
export GOOSE_DBSTRING='postgres://app:password@localhost:5432/cinema?sslmode=disable'
export GOOSE_MIGRATION_DIR=./migrations
```

Не добавляйте файл с настоящим `GOOSE_DBSTRING` в Git.

Создание миграции:

```bash
mkdir -p migrations
goose create create_films sql
```

По умолчанию goose создаст один файл с временной меткой, например `20260823120000_create_films.sql`. В отличие от некоторых других инструментов, стандартный формат goose хранит секции up и down в одном SQL-файле:

```sql
-- +goose Up
CREATE TABLE films (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title        text NOT NULL,
    release_date date NOT NULL,
    rating       numeric(3, 1) NOT NULL CHECK (rating BETWEEN 0 AND 10)
);

CREATE INDEX films_release_date_idx ON films (release_date);

-- +goose Down
DROP TABLE films;
```

Аннотация `-- +goose Up` обязательна и должна стоять без отступа. `-- +goose Down` необязательна. По умолчанию SQL-миграция выполняется в транзакции, поэтому при ошибке посередине изменения откатятся вместе.

Основные команды:

```bash
goose validate          # проверить формат файлов
goose status            # показать примененные и ожидающие миграции
goose up                # применить все новые миграции
goose up-by-one         # применить одну следующую миграцию
goose up-to 20260823120000
goose down              # откатить последнюю версию
goose down-to 20260823120000
goose version           # показать версию схемы в базе
```

Команда `goose fix` не применяет указанную миграцию. Она перенумеровывает timestamp-миграции последовательно, сохраняя их порядок. Для применения до конкретной версии служит `up-to`.

### Правила работы с миграциями

Миграция, которая уже попала в общее окружение, считается неизменяемой. Исправление оформляют новым файлом. Если переписать старый файл, база, где он уже применен, не выполнит новую версию содержимого.

Откат не всегда возможен без потери данных. `DROP COLUMN` в down-секции не восстановит удаленные значения. Поэтому наличие `Down` не равно гарантии безопасного rollback. Перед опасным изменением нужны резервная копия, проверенный план восстановления или новая исправляющая миграция.

При rolling deployment старая и новая версии приложения некоторое время работают одновременно. Изменение схемы делают совместимыми шагами:

1. Добавляют новый nullable-столбец или таблицу, не ломая старый код.
2. Выкатывают код, который умеет работать с новой схемой, и при необходимости заполняют данные.
3. После перехода всех реплик добавляют строгие ограничения и удаляют старую структуру отдельной миграцией.

Такой подход часто называют expand/contract. Он важнее красивого `Down`, потому что позволяет выпускать код без одновременной остановки всех реплик.

Некоторые команды PostgreSQL нельзя выполнять внутри транзакции. Для них goose поддерживает аннотацию `-- +goose NO TRANSACTION` в начале файла. Используйте ее только когда это действительно требуется: при ошибке инструмент уже не сможет атомарно отменить выполненную часть файла. Например, `CREATE INDEX CONCURRENTLY` запускают вне транзакции, когда обычное создание индекса слишком надолго блокирует запись в большую таблицу.

Миграции лучше применять отдельным шагом deployment pipeline и только из одного контролируемого процесса. Если каждая реплика сервиса пытается мигрировать базу при старте, управление порядком развертывания и диагностика ошибок становятся сложнее.

Goose можно вызвать и как Go-библиотеку, в том числе встроить SQL-файлы через `embed`. Это удобно для самостоятельной утилиты миграций. Для основного приложения все равно стоит отделять готовность схемы от обычного запуска HTTP-сервера.
