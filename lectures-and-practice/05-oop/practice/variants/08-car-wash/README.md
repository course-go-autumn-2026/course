# Практикум: автомойка на Go

Автомойка принимает заказы на мойку автомобилей.
Три задания независимы: каждое работает с отдельной учебной моделью.
Цены в заданиях 1, 2 и 3 заданы отдельно и не обязаны совпадать.

## Начало работы

Откройте терминал в этой папке, рядом с её `go.mod`, и выполните:

```sh
go test ./student/...
go run ./cmd/demo
```

Нужен Go 1.22 или новее. Внешние библиотеки, база данных и доступ к сети не нужны.
Можно работать парами. Незавершённое первое задание не мешает второму и третьему.
Все исходные тесты проходят: они проверяют базовые сценарии, но не все требования.
Стартовый код намеренно содержит проблемы для разбора и исправления.

Результат работы: изменённый код, тесты и короткое объяснение принятых решений.
Если меняете конструктор или публичный API учебных пакетов, обновите вызовы
в тестах и `cmd/demo`. Ожидаемые цены, чеки и ошибки исходных сценариев сохраняйте.
Пакет `student/task03interface/clients` менять нельзя.

## Задание 1. Разобраться в SOLID

Исходный код: `student/task01solid/service.go`.

Метод `Service.PlaceOrder` принимает `Order`, рассчитывает стоимость,
сохраняет запись и сообщает о принятии. Каждая позиция стоит `Price` рублей
за единицу; её количество задаётся в `Quantity`.

Поле `FinishKind` выбирает дополнительную опцию:

| Значение | Реализация | Опция | Доплата, руб. |
|---|---|---|---:|
| `none` | `NoFinish` | без покрытия | 0 |
| `wax` | `WaxFinish` | воск | 200 |
| `ceramic` | `CeramicFinish` | керамическое покрытие | 500 |

Доплата начисляется **один раз на всю запись**, а не на каждую позицию.
Для `NoFinish` поле `Box` не используется.
Для `WaxFinish` поле `Box` должно быть непустым, других ограничений нет.
Для `CeramicFinish` допустимо только значение `Бокс 1`.
Это упрощённые правила учебного примера.

Планируемые изменения:

1. Отправлять уведомления через SMS вместо консоли.
2. Изменить формат чека, сохранив правила расчёта.
3. Добавить покрытие «антидождь» за 150 рублей: значение `rain`,
   тип `RainFinish`. Для этой опции поле `Box` не используется.
4. Подключить хранилище, которое умеет только сохранять `Order`.
5. Возвращать обычную ошибку при недоступной опции, не прерывая программу.

Что сделать:

1. Найдите минимум три места, которые затрудняют эти изменения или уже нарушают
   обещанное поведение. Для каждого укажите принцип SOLID и объясните последствия.
2. Выберите одну проблему и исправьте её в коде.
3. Добавьте тест, который проверяет выбранное изменение или выявленную ошибку.
4. Сохраните успешные сценарии и проверку некорректного количества.

Используйте таблицу в ответе:

| Место в коде | Принцип | Как проявляется проблема | Предложенное изменение |
|---|---|---|---|
| ... | ... | ... | ... |

Контракт `Finish`: метод `Cost` возвращает доплату в рублях.
Если опция недоступна для переданного значения, метод возвращает ошибку,
а не вызывает `panic`. Совпадение сигнатур ещё не гарантирует соблюдение контракта.
Попробуйте `(CeramicFinish{}).Cost("Бокс 3")`.

Контрольный успешный сценарий: позиция «Мойка кузова» с ценой 600 рублей и количеством 2
с опцией `wax` и `Box: "Бокс 2"` дают чек
`Заказ 42: 1400 руб.`

**Для продвинутых:** устраните все найденные проблемы, подключите новую опцию
через сборку зависимостей и проверьте, что ошибка сохранения предотвращает уведомление.

Критерии: объяснение связано с конкретным требованием; изменение проверяется тестом;
основной сценарий сохранён. Количество созданных интерфейсов не оценивается.

## Задание 2. Cohesion и coupling

Исходный код: `student/task02grasp/wash_package.go`.

Тип `WashPackage` описывает «Комплексная мойка» с фиксированным составом:
кузов — 300 руб., салон — 200 руб., коврики — 100 руб.
Цена одного набора равна сумме цен его составляющих — 600 рублей.
Чек показывает название, количество и итоговую стоимость.

Новые требования:

- Можно добавить воск за 150 рублей и далее любые другие составляющие.
- Текстовый и HTML-чеки должны показывать правильную стоимость при любом составе.
- Изменение оформления чека не должно требовать изменения типа `WashPackage`.

Что сделать:

1. Покажите, какие ответственности объединены в `WashPackage`.
2. Объясните, что `Receipt` знает о внутреннем устройстве набора и как это влияет на изменения.
3. Перераспределите расчёт цены и форматирование чека.
4. Добавьте воск без изменения алгоритмов формирования чеков.
5. Проверьте оба формата: два расширенных набора должны стоить 1500 рублей.
   Два исходных набора по-прежнему стоят 1200 рублей.

Допустимо менять представление составляющих, конструкторы и API учебного пакета.
Сохраните экранирование названия в HTML, в том числе символов `<`, `>` и `&`.
Интерфейсы вводите только при наличии причины.

В объяснении ответьте:

- Почему обязанности каждого получившегося типа связаны между собой?
- Какие сведения о наборе теперь нужны формирователю чека?
- Какие файлы потребуется изменить для добавления ещё одной составляющей?

**Для продвинутых:** проверьте, может ли внешний код изменить цену созданного набора,
изменив переданный в конструктор срез составляющих. При необходимости защитите состояние
и добавьте тест.

Критерии: оба формата используют один расчёт цены; оформление отделено от модели;
новая составляющая не требует изменения форматирования; исходные чеки сохранены.

## Задание 3. Выделить интерфейс из бизнес-кейса

Исходный код: `student/task03interface/quote.go`.
Готовые клиенты: `student/task03interface/clients/providers.go`.

Перед подтверждением заказа нужно узнать стоимость мойки в рублях и время выполнения в минутах.
Входные данные: класс автомобиля (`carClass`) и количество автомобилей
(`cars`, в штуках).
Автомойка выбирает исполнителя при запуске приложения.
Логика `Reception.QuoteWash` должна работать с любым выбранным клиентом.

Есть два готовых клиента с разными API:

```go
func (*ManualWash) Estimate(carClass string, cars int) (int, int, error)

func (*AutoWash) Calculate(request WashRequest) (WashResponse, error)
```

`ManualWash.Estimate` возвращает стоимость в рублях, время в минутах и ошибку.
`AutoWash.Calculate` принимает поля `VehicleClass` и `VehicleCount`
с теми же входными единицами, но возвращает `CostKopecks` в копейках
и `DurationSeconds` в секундах.
Дополнительные операции `ListWorkers` и `Start` для оценки не нужны.
Публичный API и реализацию пакета `clients` изменять нельзя.
Клиенты работают локально, без HTTP.

Правила общего поведения:

- Значения `Легковой` и `Кроссовер` обслуживаются обоими клиентами.
- Любое другое непустое значение недоступно. Бизнес-код должен различать этот случай
  и прочие ошибки, не разбирая текст ошибки.
- Пустая строка и неположительное значение `cars` приводят к ошибке.
- Стоимость и время показываются целыми числами; дробные рубли и минуты округляются вверх.
- Недоступная опция приводит к ошибке, а не к `panic`.
- Разные исполнители могут возвращать разные цены и время.

Контрольные значения для `carClass: "Легковой"`, `cars: 2`:

| Клиент | Рубли | Минуты |
|---|---:|---:|
| `ManualWash` | 900 | 40 |
| `AutoWash` | 901 | 30 |

Второй клиент возвращает 90050 копеек и 1755 секунд.
Это намеренно дробные рубли и минуты: простого целочисленного деления недостаточно.

Что сделать:

1. Сформулируйте, какая возможность нужна бизнес-коду от исполнителя.
2. Самостоятельно выберите название интерфейса, его методы и тип результата.
   Опишите единицы измерения и правила ошибок в объяснении решения.
3. Подключите клиентов к этому контракту, не меняя их API.
4. Передавайте зависимость бизнес-коду снаружи.
5. Напишите тест бизнес-кода с собственной простой заглушкой.

**Базовый объём:** общий контракт, один клиент, внедрение зависимости и тест с заглушкой.

**Для продвинутых:** оба клиента, перевод единиц измерения, общий способ распознать
недоступную опцию и одинаковый набор проверок контракта для обеих реализаций.
Проверьте поддерживаемые значения, недоступное значение, пустую строку,
нулевое и отрицательное число, а также округление второго клиента.

Критерии: бизнес-код зависит от нужной ему возможности; в нём нет выбора конкретного
клиента и пересчёта копеек или секунд; заглушка не требует настоящего клиента;
выбранные реализации соблюдают один контракт.
