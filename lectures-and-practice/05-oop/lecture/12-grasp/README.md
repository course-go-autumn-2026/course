# GRASP: кому поручить ответственность

GRASP расшифровывается как General Responsibility Assignment Software Patterns - шаблоны распределения обязанностей в программном обеспечении. Они помогают решить, какой объект должен считать сумму, создавать позицию заказа или знать состав пиццы.

Здесь разобраны **четыре шаблона из презентации**, а не весь каталог GRASP. Каждый пример запускается отдельно и показывает варианты до и после изменения.

| Слайд | Каталог | Основной вопрос |
| --- | --- | --- |
| 30 | `01-high-cohesion` | Связаны ли обязанности типа между собой? |
| 31 | `02-low-coupling` | Сколько деталей другого типа должен знать потребитель? |
| 33 | `03-information-expert` | У кого есть данные для выполнения обязанности? |
| 34 | `04-creator` | Кто должен создавать позицию заказа? |

В каждом каталоге:

- `before.go` - исходная организация кода;
- `after.go` - вариант с применением шаблона;
- `main.go` - общий сценарий сравнения и вопрос для аудитории;
- `main_test.go` - ожидаемый вывод, который проверяется командой `go test`.

Команды из папки `lecture`:

```sh
go run ./12-grasp/01-high-cohesion
go run ./12-grasp/02-low-coupling
go run ./12-grasp/03-information-expert
go run ./12-grasp/04-creator
go test ./12-grasp/...
```

Запускайте весь каталог: `main.go` использует определения из соседних файлов.

## High Cohesion: связанные обязанности

В `before.go` тип `MixedPizza` хранит начинку, проверяет её наличие и формирует финансовый отчёт. Первые две обязанности работают с составом пиццы. Для отчёта состояние пиццы вообще не требуется.

В `after.go` у `Pizza` остаются `AddTopping` и `HasTopping`. Формирование отчёта вынесено в отдельную функцию `SalesReport`. Дополнительный интерфейс или тип здесь не нужен.

**Что показать:** вывод до и после одинаков по смыслу, но теперь изменение формата отчёта не требует менять код типа пиццы. Добавление метода `RemoveTopping` само по себе не ухудшило бы cohesion: он относится к той же задаче управления составом.

Высокая связность обязанностей не означает «мало методов». Десять методов, работающих с одной моделью, могут сочетаться лучше, чем два случайных метода. Это близко к SRP: SRP обсуждает причины изменения модуля, а High Cohesion - насколько его обязанности связаны между собой.

Вопрос студентам: «Если добавить в `Pizza` отправку отчёта по email, какие новые причины менять этот тип появятся?»

## Low Coupling: меньше знаний о чужом устройстве

В `before.go` функция чека сама складывает цены теста, сыра и соуса. Она знает внутреннее устройство `DetailedPizza`. Позже в пиццу добавили платную начинку `Topping`, но расчёт чека забыли обновить.

В `after.go` пицца хранит ингредиенты и считает цену в `Price()`. Чеку достаточно вызвать этот метод. Добавление ещё одного ингредиента через `NewPizza` не требует изменения функции чека.

**Что показать:** до изменения рецепта оба варианта дают **350**. После добавления начинки за 100 исходный расчёт ошибочно возвращает **350**, новый - **450**.

Ошибка в варианте «до» намеренная. Тест фиксирует её как часть демонстрации; в прикладном коде такой результат следовало бы исправить.

Слабая связанность не означает отсутствие зависимостей: чек всё ещё зависит от `Pizza` и метода `Price`. Он знает меньше деталей, которые могут измениться. Интерфейс для этого улучшения не потребовался. Если изменится сам смысл цены или контракт метода, код потребителя тоже может потребовать изменений.

Вопрос студентам: «Если завтра появятся оливки, где придётся править код в каждом варианте?»

## Information Expert: вычисляет тот, у кого есть нужные данные

В `before.go` внешний сценарий оформления заказа перебирает позиции, получает цены пицц и умножает их на количество. Ему приходится знать устройство заказа и правила расчёта позиции.

В `after.go` обязанности распределены так:

- `Pizza.Price()` сообщает цену пиццы;
- `OrderItem.Subtotal()` умножает цену на количество, которыми располагает позиция;
- `Order.Total()` складывает суммы позиций, которые находятся в заказе;
- внешний сценарий `CheckoutTotal` запрашивает итог у заказа.

**Что показать:** две пиццы по 600 дают **1200**, ещё одна за 750 даёт итог **1950**. Пустой заказ даёт **0**. Оба варианта считают правильно; меняется место размещения знания о расчёте.

Эксперт может делегировать часть работы другим экспертам. Заказу не нужно самому разбирать ингредиенты каждой пиццы.

Наличие данных - основание рассмотреть объект как исполнителя, но не безусловный приказ. Наличие email покупателя в заказе не означает, что заказ должен подключаться к почтовому серверу. Такое решение добавит инфраструктурные зависимости и смешает обязанности. Information Expert применяют вместе с High Cohesion и Low Coupling.

Вопрос студентам: «Если изменится формула суммы позиции, должен ли внешний сценарий оформления знать об этом?»

## Creator: создание поручаем подходящему владельцу

В `before.go` внешний сценарий `BeforeCheckoutAdd` проверяет количество, создаёт `BeforeOrderItem` и кладёт его в заказ. Он знает, из каких полей состоит позиция и как она хранится.

В `after.go` клиент вызывает `order.AddPizza(pizza, count)`. Заказ сам проверяет количество, создаёт внутренний `orderItem` и добавляет его в свои позиции. Он подходит для этой обязанности, потому что содержит позиции, использует их и получает данные для инициализации.

**Что показать:** оба варианта дают **1950** и отклоняют отрицательное количество. После отказа сумма остаётся прежней. Валидация присутствует в обоих вариантах: главное отличие здесь в том, кто знает детали создания позиции.

Creator не требует всегда создавать всё внутри родительского объекта. Если создание сложное, требует внешних ресурсов или выбора разных реализаций, отдельная фабрика может лучше сохранить связность обязанностей. В этом примере таких требований нет.

Вопрос студентам: «Если у позиции появится обязательное поле, сколько внешних сценариев должны будут знать, как его заполнить?»

## Что связать со слайдами 35–37

- Вызов `pizza.Price()` уменьшает знание клиента об ингредиентах. Спросите, какой вариант переживёт изменение состава без правки чека.
- Оценивайте связанность обязанностей по смыслу и используемым данным, а не по числу методов.
- Объект с нужными данными - кандидат на ответственность. Проверьте, не заставит ли назначение этой обязанности подключать к нему БД, сеть или другие несвязанные задачи.

Шаблоны пересекаются. Например, перенос расчёта в `Pizza.Price` одновременно использует Information Expert и уменьшает coupling. На лекции полезно назвать конкретную проблему, а затем показать, какие шаблоны помогли её решить.

## Границы учебных примеров

Цены заданы целыми рублями. Используются корректные цены и количества, кроме явно показанного отрицательного количества в Creator. Дробные суммы, переполнение и полный набор бизнес-проверок здесь не рассматриваются.

Все варианты находятся в `package main` для удобного сравнения. В Go неэкспортируемые поля скрыты от других пакетов, но доступны всему коду своего пакета. Поэтому этот пример сам по себе не запрещает соседней функции обойти методы и изменить поля. Настоящую границу пакета показывает [пример инкапсуляции](../09-oop-principles/04-encapsulation/main.go).
