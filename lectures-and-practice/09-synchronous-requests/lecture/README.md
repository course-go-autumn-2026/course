# Синхронные запросы на Go

[Практика](../practice/README.md)

Конспект студента · Лекция 9 · ITMO × Avito Start

Цель занятия: выбрать подход к синхронному взаимодействию и реализовать unary gRPC-вызов с контрактом, обработкой ошибок и ограничением ожидания. Для чтения нужны основы Go, HTTP и context.Context.

Примеры используют пиццерию и службу расчёта доставки. Практика запускается локально без базы данных и Docker. Код на страницах — отдельные фрагменты; рабочие файлы и точные команды находятся в README практики.

## Один заказ, два процесса

Пиццерия обращается к отдельной службе, потому что правила доставки принадлежат этой службе. Клиент отправляет адрес и вес и получает стоимость в копейках и время в минутах. Весь материал использует одну предметную область, но примеры REST, GraphQL и RPC показывают разные способы выразить API. Это учебный расчёт без записи заказа и резервирования.

- Пиццерия знает адрес и вес заказа
- Служба доставки рассчитывает цену и время
- Покупатель ждёт результат расчёта

## Что означает «синхронно»

Синхронность здесь описывает зависимость бизнес-операции от результата запроса. Она не означает запрет горутин, последовательную обработку всех клиентов или обязательное блокирование потока ОС. Go может обслуживать множество сетевых запросов одновременно, пока отдельная горутина ожидает ответ. Асинхронное взаимодействие через брокер подробно разбирается на следующем занятии.

- Текущая операция зависит от ответа другого сервиса
- Ожидание нужно ограничить по времени
- Другие запросы сервер может обрабатывать параллельно

## Удалённый вызов может не дать ответа

У локального вызова нет сетевого участка. У удалённого появляются независимый процесс, транспорт и ожидание. Отсутствие ответа не сообщает, на каком участке произошёл сбой. Для расчёта доставки повтор обычно не создаёт побочного эффекта. Для списания денег или создания заказа нельзя сделать тот же вывод. Гарантии повтора определяются контрактом операции, а не только кодом ошибки.

- Сервис недоступен до начала обработки
- Сервис принял запрос, но отвечает слишком долго
- Сервис завершил операцию, а ответ потерялся

## REST и HTTP

REST не является синонимом JSON поверх HTTP. В этой лекции повторяем ресурсный подход: клиент работает с ресурсами и их представлениями, а HTTP даёт общую семантику методов. Полное проектирование HTTP API уже было на лекции 1. Наличие POST само по себе не делает интерфейс ни REST, ни RPC.

- REST описывает архитектурный стиль API
- HTTP задаёт методы, заголовки и статусы
- JSON — один из форматов представления

## Ресурс расчёта доставки

Если расчёт представлен ресурсом, сервер может создать котировку с идентификатором и вернуть 201 и Location. В показанном примере создаётся ресурс котировки; в практическом gRPC-примере результат не сохраняется. Не нужно добавлять хранение только ради формы URL. Для существующей котировки чтение могло бы выглядеть как GET /delivery-quotes/q-42. Код 201 уместен именно при создании ресурса.

```
POST /delivery-quotes
Content-Type: application/json

{"address":"Центр","weightGrams":1500}

HTTP/1.1 201 Created
Location: /delivery-quotes/q-42

{"id":"q-42","priceKopecks":30000,"etaMinutes":30}
```

## Контракт HTTP-вызова

HTTP определяет поведение протокола, но не знает, что вес должен быть положительным и не превышать 20 килограммов. Эти правила описывает API. OpenAPI помогает формализовать интерфейс и генерировать код. Сгенерированный код не заменяет бизнес-валидацию. На уровне клиента по-прежнему нужны контекст, ограничение ожидания и проверка результата.

- Формат входа и единицы измерения
- Успешный ответ и ошибки
- Правила совместимости и повторов

## GraphQL: клиент выбирает поля

GraphQL задаёт язык запросов и правила их исполнения. Клиент может запросить только стоимость или стоимость вместе со временем. Сервер разрешает только поля, объявленные в схеме. GraphQL не даёт клиенту прямой доступ к SQL или внутренним таблицам. Обычно его используют через HTTP, но язык запросов и транспорт — отдельные части решения.

- Схема задаёт доступные типы и операции
- Запрос перечисляет нужные поля ответа
- Resolver получает данные для поля

## Схема GraphQL

Query описывает чтение, Mutation — операции изменения. В примере Quote содержит цену и время. Восклицательный знак означает non-null: сервер обещает значение вместо null. GraphQL Int — знаковое 32-битное число. Для больших денежных значений нужен согласованный scalar или иное представление; в учебном диапазоне значения помещаются в Int.

```
type Query {
  estimate(address: String!, weightGrams: Int!): Quote
}

type Quote {
  priceKopecks: Int!
  etaMinutes: Int!
}
```

## Запрос и ответ GraphQL

Клиент просит только priceKopecks, поэтому etaMinutes не входит в ответ. Чтобы получить время, клиент добавляет поле в selection set. Возможность выбрать поля уменьшает лишние данные в ответе, но сама по себе не гарантирует меньше запросов к базам или зависимостям. Это зависит от исполнения resolver-ов.

```
query {
  estimate(address: "Центр", weightGrams: 1500) {
    priceKopecks
  }
}

{"data":{"estimate":{"priceKopecks":30000}}}
```

## Resolver и стоимость запроса

Для estimate resolver может вызвать тот же расчёт, что использует gRPC-обработчик. Если для каждого элемента списка отдельно загружать связанный объект, появится N+1. Батчинг, кеширование внутри запроса и ограничение сложности помогают управлять нагрузкой. Свободный выбор полей требует контроля стоимости исполнения, а не только красивой схемы.

- Resolver вызывает бизнес-логику или источник данных
- Вложенный список может вызвать N+1 обращений
- Сервер ограничивает сложность и объём запроса

## Ошибки GraphQL

При ошибке выполнения части запроса GraphQL может вернуть доступные данные и массив errors. Поле path помогает понять, какая часть ответа пострадала. Для non-null поля null распространяется до ближайшего nullable родителя. HTTP-статус сам по себе не описывает весь результат GraphQL-операции. Ошибки синтаксиса или валидации запроса отличаются от ошибок выполнения.

```
{"data":{"estimate":null},
 "errors":[{
   "message":"Delivery is unavailable",
   "path":["estimate"]
 }]}
```

## Где GraphQL помогает

GraphQL полезен, когда форма ответа заметно меняется между потребителями. Для одного простого межсервисного вызова его гибкость может не окупить сложность сервера, контроля запросов и кеширования. GraphQL и gRPC могут сосуществовать: внешний API собирает данные через внутренние RPC. Это архитектурный выбор, а не соревнование форматов.

- Несколько экранов требуют разный набор данных
- Нужен единый типизированный интерфейс для клиентов
- Команда готова управлять resolver-ами и стоимостью запросов

## RPC: вызов именованного метода

RPC означает Remote Procedure Call. Клиент вызывает действие, например estimateDelivery. Похожая на локальную сигнатура удобна, но не отменяет задержки и ошибки сети. JSON-RPC и gRPC — разные реализации этой идеи. Brief также позволяет описывать RPC-контракты, но не является другим именем protobuf.

- Метод Estimate принимает request и возвращает response
- Клиент знает контракт операции
- Сеть остаётся частью вызова

## JSON-RPC 2.0

Спецификация JSON-RPC не привязана к одному транспорту. В обычном вызове клиент задаёт id, а сервер возвращает тот же id. Успешный ответ содержит result, неуспешный — error; оба поля вместе не используются. Notification не содержит id и не получает JSON-RPC-ответ. Отсутствие ответа на notification не означает подтверждённое выполнение.

```
{"jsonrpc":"2.0","method":"estimateDelivery",
 "params":{"address":"Центр","weightGrams":1500},
 "id":42}

{"jsonrpc":"2.0",
 "result":{"priceKopecks":30000,"etaMinutes":30},
 "id":42}
```

## Ошибка JSON-RPC

JSON-RPC определяет стандартные ошибки: например, -32601 — неизвестный метод, -32602 — некорректные параметры. Бизнес-ошибки нужно согласовать отдельно. Сообщение предназначено человеку; обработку строят по коду и контракту данных. Идентификатор id связывает ответ и запрос, но не является ключом идемпотентности.

```
{"jsonrpc":"2.0",
 "error":{"code":-32602,"message":"Invalid params"},
 "id":42}
```

## gRPC: контракт и сгенерированный код

В типичном gRPC-проекте одна схема определяет доступные методы и сообщения. Генератор создаёт код сериализации и инфраструктуру вызова. Бизнес-логику разработчик реализует сам. Другие языки могут использовать тот же контракт и свои генераторы. gRPC не даёт автоматического выигрыша во всех задачах: результат зависит от нагрузки и окружения.

- Описание сервиса и сообщений в .proto
- Клиентский stub и серверный интерфейс для Go
- Обычно Protobuf для сообщений и HTTP/2 для транспорта

## Путь unary-вызова

Клиент вызывает метод stub. Транспорт кодирует запрос и отправляет его серверу. Серверная инфраструктура декодирует сообщение и вызывает обработчик. Обработчик обращается к бизнес-логике и возвращает ответ либо статус ошибки. Слово unary описывает число сообщений в RPC, а не число одновременно обслуживаемых клиентов.

```
Код клиента
  → сгенерированный DeliveryServiceClient
    → HTTP/2 + Protobuf
      → серверный обработчик Estimate
        → расчёт доставки
      ← ответ или статус ошибки
```

## Четыре формы RPC

Сегодня подробно изучаем unary RPC. Streaming нужен для последовательностей сообщений внутри одного вызова. Двунаправленный поток не требует строгого чередования запрос-ответ. Потоки не превращают gRPC в брокер с долговременным хранением и гарантиями доставки событий. Практическое применение streaming относится к лекции о realtime.

- Unary: один запрос и один ответ
- Server streaming: один запрос и поток ответов
- Client streaming: поток запросов и один ответ
- Bidirectional streaming: два независимых потока

## Protobuf: сервис

В учебном примере используем proto3 и обычный Open Struct API Go. package задаёт protobuf-пространство имён, go_package — Go-путь импорта и имя пакета. Это разные назначения. Версия v1 в пакете помогает организовать развитие API, но сама по себе не обеспечивает совместимость. Имена и номера полей остаются частью контракта.

```
syntax = "proto3";
package delivery.v1;
option go_package =
  "example.com/sync-practice/api/delivery/v1;deliveryv1";

service DeliveryService {
  rpc Estimate(EstimateRequest) returns (EstimateResponse);
}
```

## Protobuf: сообщения

Номер используется в бинарном представлении и должен сохранять смысл. Копейки и граммы входят в имя, чтобы разные реализации не перепутали единицы. Цена — целое число, поэтому нет ошибки двоичного представления дробной денежной величины. Схема не ограничивает вес диапазоном 1–20000: это проверяет бизнес-логика.

```
message EstimateRequest {
  string address = 1;
  int64 weight_grams = 2;
}
message EstimateResponse {
  int64 price_kopecks = 1;
  int32 eta_minutes = 2;
}
```

## Значение по умолчанию и отсутствие

В proto3 у обычного скалярного поля без explicit presence ноль не отличим через getter от отсутствия. Если эта разница важна, используют optional. Для веса в нашем контракте и отсутствие, и ноль невалидны, поэтому optional не нужен. В другом API нулевая скидка и неуказанная скидка могут иметь разный смысл. Для enum первое значение равно нулю; удобно назвать его UNSPECIFIED и обработать явно.

```
message Preferences {
  optional int32 discount_percent = 1;
}

// В Go у optional-скаляра можно проверить наличие.
// Один GetDiscountPercent() различие не сохраняет.
```

## Изменение схемы

Добавление нового поля обычно совместимо для бинарного protobuf: старый код не начинает использовать неизвестное поле автоматически. Но если сервер внезапно требует новое поле от старого клиента, поведение сломается. Переименование поля может сохранить бинарную совместимость и одновременно сломать JSON-потребителей или исходный код. Изменение единиц с копеек на рубли при том же типе тоже нарушает контракт.

```
message EstimateResponse {
  reserved 3;
  reserved "legacy_label";
  int64 price_kopecks = 1;
  int32 eta_minutes = 2;
  string currency = 4;
}
```

- Новое поле получает новый номер
- Удалённые номера и имена резервируем
- Совместимость проверяем вместе с бизнес-смыслом

## Что создаёт генератор

Компилятор protoc читает схему и вызывает два плагина. protoc-gen-go создаёт protobuf-сообщения, protoc-gen-go-grpc — gRPC-код. Генерация интерфейса сервера не означает генерацию бизнес-реализации. Изменения вносят в proto и исходники обработчика, затем повторяют генерацию. Сгенерированные файлы можно хранить в репозитории, чтобы сборка не требовала protoc.

- delivery.pb.go: типы сообщений и сериализация
- delivery_grpc.pb.go: клиент, интерфейс и регистрация
- Обработчик и бизнес-правила пишем сами

## Команда генерации

На практике make tools устанавливает плагины в локальную .bin, а make generate обновляет только контракт первого задания. paths=source_relative размещает файлы рядом с исходной схемой. Для полного демонстрационного примера путь к proto отличается, но параметры те же. При проблемах генерации доступна подготовленная копия файлов; преподаватель отдельно проверяет понимание схемы.

```
protoc \
  --go_out=. --go_opt=paths=source_relative \
  --go-grpc_out=. --go-grpc_opt=paths=source_relative \
  api/delivery/v1/delivery.proto
```

## Обработчик вызывает бизнес-логику

Handler принимает транспортную модель, извлекает аргументы и передаёт их domain.Estimate. Домен не импортирует grpc или protobuf. После расчёта handler собирает ответ. Ниже показан сокращённый фрагмент: MapError и тип Server определены в полном примере. Такая граница помогает менять транспорт без переписывания расчёта.

```
func (s *Server) Estimate(ctx context.Context,
  in *pb.EstimateRequest) (*pb.EstimateResponse, error) {
  q, err := domain.Estimate(in.GetAddress(), in.GetWeightGrams())
  if err != nil { return nil, MapError(err) }
  return &pb.EstimateResponse{
    PriceKopecks: q.PriceKopecks, EtaMinutes: q.ETAMinutes,
  }, nil
}
```

## Запуск сервера

net.Listen открывает TCP-порт. grpc.NewServer создаёт серверную инфраструктуру, а RegisterDeliveryServiceServer связывает её с нашим обработчиком. Serve принимает соединения. В учебном запуске сервер слушает loopback и останавливается Ctrl+C. Graceful shutdown и настройка защищённого соединения требуют отдельной конфигурации в рабочем сервисе.

```
listener, err := net.Listen("tcp", "127.0.0.1:50051")
if err != nil { return err }

server := grpc.NewServer()
pb.RegisterDeliveryServiceServer(server, &Server{})
return server.Serve(listener)
```

## Создание клиента

grpc.NewClient создаёт канал клиента и не выполняет сетевой обмен немедленно. Успех конструктора не доказывает, что сервер доступен. Соединение устанавливается по мере необходимости. ClientConn и сгенерированный клиент допускают конкурентное использование. Не нужно создавать их заново на каждый запрос внутри долгоживущего сервиса. insecure в примере отключает TLS и подходит для локального учебного запуска.

```
conn, err := grpc.NewClient("127.0.0.1:50051",
  grpc.WithTransportCredentials(insecure.NewCredentials()))
if err != nil { return err }
defer conn.Close()

client := pb.NewDeliveryServiceClient(conn)
```

## Вызов метода

При создании контекста от входящего запроса сохраняются его отмена и ограничения. Если использовать Background внутри цепочки, можно потерять сигнал отмены от вызывающей стороны. Для CLI корневой контекст создаёт main. Пример намеренно показывает обработку ошибки до чтения ответа. Части кода на слайдах — фрагменты; целиком запускается пример преподавателя.

```
ctx, cancel := context.WithTimeout(parent, time.Second)
defer cancel()

quote, err := client.Estimate(ctx, &pb.EstimateRequest{
  Address: "Центр", WeightGrams: 1500,
})
if err != nil { return err }
fmt.Println(quote.GetPriceKopecks(), quote.GetEtaMinutes())
```

## Демонстрация успешного вызова

На демонстрации преподаватель запускает готовый сервер и клиент в разных терминалах. Для Центра и веса 1500 граммов ответ содержит 30000 копеек и 30 минут; для Севера — 40000 копеек и 45 минут. После выполнения задания 2 эти команды работают и в вашем репозитории. Сравните параметры запроса с полями ответа.

```
go run ./cmd/server -task=2

# В другом терминале
go run ./cmd/client -task=2
go run ./cmd/client -task=2 -address=Север
```

- Терминал 1: сервер задания 2
- Терминал 2: клиент задания 2
- Результат: 30000 копеек, 30 минут

## Доменная ошибка становится статусом

Выбор NotFound для необслуживаемой зоны — договорённость нашего API. В другом API этот случай может быть частью успешного ответа или иметь другой статус. Важно согласовать трактовку и использовать её на обеих сторонах. Исходный текст внутренних ошибок клиенту не отдаём. Для wrapped sentinel-ошибок используем errors.Is.

- Некорректный адрес или вес: InvalidArgument
- Зона доставки отсутствует: NotFound
- Временный отказ: Unavailable
- Неожиданный внутренний сбой: Internal

## Клиент обрабатывает код

status.Code извлекает gRPC-код. При переводе в прикладную ошибку важно сохранить нужную вызывающему коду семантику. В практике три статуса переводятся в sentinel-ошибки, распознаваемые errors.Is, а остальные возвращаются без изменения. Поэтому отмена и deadline сохраняют транспортный код. Логирование и политика повторов не должны зависеть от английского текста сообщения.

```
switch status.Code(err) {
case codes.InvalidArgument:
  return nil, ErrInput
case codes.NotFound:
  return nil, ErrNoDelivery
case codes.Unavailable:
  return nil, ErrDependency
default:
  return response, err
}
```

## Бюджет времени цепочки

Timeout — длительность ожидания, deadline — момент, после которого результат уже не нужен. WithTimeout создаёт deadline относительно текущего времени. Дочерний контекст наследует более ранний deadline родителя. Если родителю осталось 100 мс, новый timeout в одну секунду не выдаёт ещё секунду. По умолчанию gRPC не задаёт прикладной deadline: его нужно устанавливать явно. grpc-go передаёт ограничение времени через протокол; контекст нужно передавать в последующие вызовы.

```
Родителю осталось 100 мс
Дочерний WithTimeout(parent, 1*time.Second)
Фактический предел: не позже deadline родителя
```

- Общий deadline ограничивает всю операцию
- Дочерний вызов получает оставшееся время
- Локальный timeout может только сократить бюджет

## Отмена должна остановить работу

gRPC сообщает об отмене через контекст, но не может безопасно прервать произвольный код обработчика. Вместо Sleep используем таймер и select. Вызовы зависимостей также должны получать ctx. CPU-цикл проверяет ctx.Err в разумных точках. Таймер освобождается при выходе. Отмена кооперативная: между сигналом и прекращением работы есть небольшая задержка.

```
timer := time.NewTimer(delay)
defer timer.Stop()
select {
case <-ctx.Done():
  return ctx.Err()
case <-timer.C:
  return ctx.Err()
}
```

## Демонстрация deadline

На демонстрации сервер задания 3 работает с delay=2s, а клиент вызывает его с timeout=200ms. После выполнения задания 3 повторите эксперимент в своём репозитории. Клиент получает DeadlineExceeded. В логе сервера видно начало и завершение расчёта с отменой или превышением deadline. Эти стороны могут наблюдать разные контекстные ошибки в зависимости от порядка событий. Тест проверяет и ответ клиента, и завершение работы сервера.

```
go run ./cmd/server -task=3 -delay=2s

go run ./cmd/client -task=3 -timeout=200ms

# Явная отмена до deadline
go run ./cmd/client -task=3 -timeout=3s -cancel-after=100ms
```

- Расчёт занимает 2 секунды
- Клиент ждёт не более 200 миллисекунд
- Сервер фиксирует завершение работы по отмене

## Тайм-аут и неизвестный результат

Представьте: сервер сохранил заказ, но ответ не дошёл. Клиент видит тайм-аут, хотя заказ существует. Повтор без ключа идемпотентности может создать второй заказ. Для нашей чистой функции расчёта побочного эффекта нет, однако это не общее свойство RPC. Политику retries, backoff и circuit breaker разбираем на лекции 11.

- Клиент мог перестать ждать после выполнения операции
- Отмена не откатывает запись в БД или платёж
- Повтор требует договорённости об идемпотентности

## Brief в Авито

Brief — внутренний формат Авито, используемый для описания контрактов, в том числе RPC. Концептуально он решает знакомую задачу: описать методы и сообщения и получить код для взаимодействия. Brief имеет собственный синтаксис и инструменты; .brief нельзя просто передать protoc. Для практики достаточно открытого стека gRPC, доступа к платформе Авито не требуется.

- Формат описания контрактов между сервисами
- Генерация клиентского и серверного кода
- Проверка совместимости изменений

## Учебный контракт Brief

Показан специально придуманный учебный контракт доставки, без схем рабочих сервисов. service объявляет имя сервиса, rpc — метод, message — структуры входа и выхода. Поле *string является необязательным. В Brief нет protobuf-номеров полей в этом синтаксисе. Сходство DTO не означает тождество протоколов или правил совместимости.

```
service "delivery-example"
rpc estimate(EstimateIn) EstimateOut
message EstimateIn {
  address string
  weightGrams int
}
message EstimateOut {
  priceKopecks int
  etaMinutes int
}
```

## Контракт и кодогенерация

В Brief клиентская схема может включать только нужную часть серверного API с соблюдением требований к обязательным полям. Проверка совместимости помогает не удалить используемое потребителями поле или метод. Общая идея применима за пределами Авито: схема — соглашение сторон, генерация снимает механическую работу, бизнес-правила и безопасная эволюция остаются ответственностью разработчика.

- Сервер описывает свой API
- Клиент описывает используемую часть API
- Генератор создаёт код, разработчик пишет обработчик

## Выбор интерфейса

Сравнивайте потребителей, инструменты команды, транспортные ограничения и требования к эволюции. Для браузерного клиента gRPC обычно требует gRPC-Web или шлюз; обычный браузер не является прямой заменой grpc-go клиента. Для внутренних сервисов gRPC часто удобен контрактом и генерацией. Наличие JSON не делает API REST, а наличие схемы не гарантирует правильной бизнес-семантики.

- REST: ресурсное API и стандартная HTTP-семантика
- GraphQL: разные выборки данных для клиентов
- JSON-RPC: именованные методы в JSON-конверте
- gRPC: типизированные межсервисные вызовы и генерация

## Словарь

Контракт — согласованная структура данных и поведение операции. DTO — модель передачи данных. Stub — сгенерированный клиентский код. Unary RPC — один запрос и один ответ. Deadline — крайний момент ожидания. Cancellation — сигнал, что работа больше не нужна. Resolver — функция получения значения поля GraphQL. Идемпотентность — эквивалентность эффекта повторного вызова с теми же аргументами.

## Памятка перед сдачей практики

- Цена и вес имеют явно указанные единицы.
- Бизнес-логика не зависит от protobuf.
- Ошибки распознаются по коду или errors.Is.
- Каждый исходящий вызов использует контекст.
- Клиентский deadline и остановка серверной работы проверены отдельно.
- Сгенерированные файлы не редактировались вручную.
