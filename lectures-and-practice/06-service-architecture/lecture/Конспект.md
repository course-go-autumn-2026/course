## Что такое архитектура вообще

Если разложить код по папкам `handler/`, `service/`, `repository/` - это уже
архитектура? Нет, папки - это просто раскладка файлов по дискам. Архитектура
появляется там, где раскладка отражает направление зависимостей: кто от кого
имеет право знать.

Можно сделать красивые папки и свалить туда код, который зависит друг от друга
как попало - репозиторий знает про HTTP-статусы, хендлер делает SQL-запросы
напрямую - папки есть, архитектуры нет. И наоборот, можно жить в одном файле
без всякой структуры, но держать слои в голове и не путать их мысленно.

Рабочий критерий на всю лекцию: граница - это не папка, а то, какие импорты
разрешены пакету.

### Проблема на примере

`before/handler.go` - весь сценарий публикации объявления в одной функции:
разбор запроса, две бизнес-проверки, SQL-запрос, HTTP-вызов во внешний сервис
модерации и решение, что ответить клиенту - всё вперемешку, 107 строк.

```go
func PublishListingHandler(db *sql.DB, moderationURL string) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        var req PublishListingRequest
        json.NewDecoder(r.Body).Decode(&req)

        if req.Price <= 0 { /* 400 */ }
        if strings.TrimSpace(req.PhotoURL) == "" { /* 400 */ }

        // SQL прямо тут
        db.QueryRowContext(r.Context(), `INSERT INTO listings ...`)

        // HTTP-вызов в модерацию прямо тут
        resp, err := http.DefaultClient.Do(modReq)
        if err != nil {
            // модерация недоступна, но объявление уже создано в БД —
            // что с ним делать, решается неявно, по месту
        }
        // ...
    }
}
```

Пока ручка одна, это терпимо. Держите в голове вопрос до конца лекции: что
будет, если в сервисе появится 10 таких ручек? Ответ - в последнем блоке, про
оверинжиниринг.

## Слои, архитектурные стили, Clean Architecture

### Слои и границы ответственности

Классическое разделение: `handler` → `service` → `repository`, и отдельно
`domain` - модели предметной области, которые не зависят ни от одного из
остальных слоёв.

| Слой | Знает про | НЕ знает про |
|---|---|---|
| handler | HTTP, JSON, статусы ответа | SQL, структуру БД, как устроена модерация |
| service | бизнес-правила, порты (интерфейсы) | `*sql.DB`, HTTP-клиент, SQL-запросы |
| domain | свои инварианты и переходы состояний | вообще ничего из инфраструктуры |
| repository | SQL, схему таблиц | бизнес-правила, HTTP-статусы |

В `before/handler.go` код похож сразу на все четыре строки таблицы - и в этом
вся проблема: нельзя отдельно потрогать бизнес-правило, не задев при этом SQL
и HTTP.

### Какие бывают архитектуры

Разделение на `handler/service/repository` - конкретная реализация идеи слоёв,
не единственная:

| Стиль | Идея |
|---|---|
| Слоёная (N-tier) | Слои идут друг за другом линейно: UI → бизнес-логика → данные |
| Луковая (Onion) | Домен в центре, слои вокруг него концентрическими кольцами, зависимости - только внутрь |
| Чистая архитектура (Clean Architecture, Р. Мартин) | Разновидность луковой с конкретными названными кольцами - разбираем ниже |
| Гексагональная (порты и адаптеры) | Домен в центре, вокруг - порты (интерфейсы), к портам снаружи подключаются адаптеры |

Общее у всех - домен и бизнес-правила в центре, зависимости направлены к
центру, а не от него. Разное - в названиях колец и в том, насколько строго
формализованы правила.

Можно придумать свою архитектуру? Да, и это нормально. Важно не совпадение с
эталонным названием, а соблюдение правила направления зависимостей. Clean,
Onion, Hexagonal - это общий словарь для разговора с другими инженерами, а не
контракт, который нужно скопировать один в один.

### Чистая архитектура - картинка-круг

Классическая диаграмма Роберта Мартина - четыре концентрических кольца от
центра к краю:

1. **Entities** - модели предметной области и бизнес-правила, не зависят
   вообще ни от чего снаружи. У нас - `domain.Listing`.
2. **Use Cases** - сценарии приложения, оркестрируют Entities. У нас -
   `service.ListingService.Publish`.
3. **Interface Adapters** - переводчики между Use Cases и внешним миром:
   контроллеры, презентеры. У нас - `handler.ListingHandler` и
   `repository.PostgresListingRepository`.
4. **Frameworks & Drivers** - самый внешний слой: БД, веб-фреймворк. У нас -
   конкретный `*sql.DB` и `net/http`.

Главное правило - Dependency Rule: стрелки зависимостей смотрят только внутрь,
от внешних колец к внутренним, никогда наоборот. Внутреннее кольцо (Entities)
вообще не знает о существовании внешних.

Нарушение правила выглядит так:

```go
package domain

import "net/http" // domain импортирует HTTP — стрелка пошла наружу

type Listing struct {
    LastResponse *http.Response // домен держит у себя HTTP-тип
}
```

В нашем `domain/listing.go` импортируются только `errors`, `strings`, `time` -
правило соблюдено. Если в домене найдётся импорт `database/sql` или
`net/http` - вот и нарушение Dependency Rule.

## Живой рефакторинг: разносим код по слоям

Тот же сценарий публикации объявления, разложенный на четыре пакета:

```
after/
├── domain/      Listing — богатая модель, инварианты и переходы статусов
├── service/     ListingService.Publish — бизнес-сценарий + порты (интерфейсы)
├── repository/  адаптеры: Postgres для хранилища, HTTP для модерации
└── handler/     транспортный слой: JSON <-> доменные ошибки <-> HTTP-статусы
```

Направление зависимостей: `handler` → `service` → `domain`. `repository`
реализует интерфейсы из `service/ports.go`, но про `domain` не знает ничего,
кроме типов - `service` вообще не знает про `database/sql`.

### domain - богатая модель

```go
func NewListing(title string, price float64, photoURL string, sellerID int64) (*Listing, error) {
    if price <= 0 {
        return nil, ErrInvalidPrice
    }
    if strings.TrimSpace(photoURL) == "" {
        return nil, ErrPhotoMissing
    }
    return &Listing{Title: title, Price: price, PhotoURL: photoURL,
        SellerID: sellerID, Status: StatusPending, CreatedAt: time.Now()}, nil
}

func (l *Listing) Approve() error {
    if l.Status != StatusPending {
        return errors.New("only pending listing can be approved")
    }
    l.Status = StatusApproved
    return nil
}
```

`NewListing` - единственный способ получить `*Listing`: создать объект с
нарушенным инвариантом просто не получится. `Approve` сам проверяет, из какого
состояния можно перейти в approved - это поведение, а не просто смена поля.

### service - бизнес-сценарий

```go
func (s *ListingService) Publish(ctx context.Context, in PublishInput) (*domain.Listing, error) {
    listing, err := domain.NewListing(in.Title, in.Price, in.PhotoURL, in.SellerID)
    if err != nil {
        return nil, err
    }

    id, err := s.repo.Create(ctx, listing)
    if err != nil {
        return nil, err
    }
    listing.ID = id

    approved, err := s.moderator.Check(ctx, id)
    if err != nil {
        // Модерация недоступна. Явное решение сервисного слоя:
        // объявление остаётся pending, модерация подхватит его позже.
        return listing, nil
    }

    if approved {
        listing.Approve()
    } else {
        listing.Reject()
    }
    s.repo.UpdateStatus(ctx, id, listing.Status)
    return listing, nil
}
```

Ни одной строчки SQL или `net/http` - весь сценарий читается как
последовательность бизнес-шагов. Сравните с `before/handler.go`: там это была
одна функция на 80+ строк, здесь - явная цепочка вызовов.

Главное отличие от `before`: случай недоступной модерации теперь явное решение
с комментарием, а не случайно получившийся код-путь.

### repository - адаптер, где живёт SQL

```go
func (r *PostgresListingRepository) Get(ctx context.Context, id int64) (*domain.Listing, error) {
    var l domain.Listing
    err := r.db.QueryRowContext(ctx,
        `SELECT id, title, price, photo_url, seller_id, status, created_at
         FROM listings WHERE id = $1`, id,
    ).Scan(&l.ID, &l.Title, &l.Price, &l.PhotoURL, &l.SellerID, &l.Status, &l.CreatedAt)

    if errors.Is(err, sql.ErrNoRows) {
        return nil, domain.ErrNotFound
    }
    if err != nil {
        return nil, err
    }
    return &l, nil
}
```

Здесь и только здесь появляется SQL. Если завтра PostgreSQL сменится на другую
БД, поменяется этот пакет, а `domain` и `service` разницы не заметят - они
зависят от интерфейса `service.ListingRepository`, а не от конкретной
реализации.

### handler - тонкий транспортный слой

```go
func (h *ListingHandler) Publish(w http.ResponseWriter, r *http.Request) {
    var req publishRequest
    json.NewDecoder(r.Body).Decode(&req)

    listing, err := h.service.Publish(r.Context(), service.PublishInput{
        Title: req.Title, Price: req.Price, PhotoURL: req.PhotoURL, SellerID: req.SellerID,
    })
    if err != nil {
        writeError(w, err)
        return
    }
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(listing)
}
```

Весь хендлер - разбор запроса, вызов сервиса, запись ответа. Сравните размер
этого файла с `before/handler.go`.

## Модели: анемичные vs богатые

Анемичная модель - структура с публичными полями, которую можно менять откуда
угодно:

```go
type Listing struct {
    ID, Title, Price string
    Status           string // просто string, не отдельный тип
}
// где-то снаружи, в любом другом файле:
listing.Status = "approved" // никто не проверил, что было pending
```

Что будет, если кто-то забудет вызвать проверку перед сохранением? Ничего не
упадёт - объявление просто окажется в невозможном по бизнес-правилам
состоянии, и баг найдётся не сразу, а через несколько шагов, когда данные уже
разойдутся с реальностью.

Богатая модель (`domain.Listing` из `after/`) защищает свои инварианты сама:
`NewListing` не даст создать объект с нарушенным правилом, `Approve`/`Reject`
не дадут перейти в недопустимое состояние.

Второй аргумент - на уровне типов. `Status string` в анемичной версии
позволяет записать туда любую строку, опечатка `"aproved"` скомпилируется без
проблем. `domain.Status` - именованный тип с константами (`StatusPending`,
`StatusApproved`, `StatusRejected`), и опечатка в имени константы просто не
скомпилируется.

## Ошибки по слоям

Путь ошибки в примере: `sql.ErrNoRows` в репозитории переводится в
`domain.ErrNotFound`, а в хендлере классифицируется в HTTP-статус:

```go
func writeError(w http.ResponseWriter, err error) {
    switch {
    case errors.Is(err, domain.ErrInvalidPrice), errors.Is(err, domain.ErrPhotoMissing):
        http.Error(w, err.Error(), http.StatusBadRequest)
    case errors.Is(err, domain.ErrNotFound):
        http.Error(w, err.Error(), http.StatusNotFound)
    default:
        http.Error(w, "internal error", http.StatusInternalServerError)
    }
}
```

Ошибка должна «переодеваться» на границе каждого слоя: репозиторий не должен
знать про HTTP-статусы, хендлер не должен знать про SQL-коды.

Что будет, если ошибку НЕ переводить:

```go
// repository возвращает sql.ErrNoRows как есть
func (r *PostgresListingRepository) Get(...) (*domain.Listing, error) {
    err := r.db.QueryRowContext(...).Scan(...)
    return &l, err // sql.ErrNoRows течёт наружу как есть
}
// handler получает sql.ErrNoRows и не знает, что с ним делать
if err != nil {
    w.WriteHeader(http.StatusInternalServerError) // 500 вместо 404!
}
```

Клиент запросил объявление, которого не существует - должен получить 404. Но
если `sql.ErrNoRows` утечёт до хендлера нетронутым, он получит 500, потому что
хендлер не знает, что эта конкретная ошибка значит «не найдено», а не
«сломалась БД».

Обратная ошибка - если хендлер сам начинает трогать SQL (`if err ==
sql.ErrNoRows` прямо в `handler`). Технически сработает, но хендлер теперь
импортирует `database/sql`, и слой пробит насквозь.

## Порты, адаптеры, Dependency Injection

### Порты и адаптеры (гексагональная архитектура)

```go
type ListingRepository interface {
    Create(ctx context.Context, l *domain.Listing) (int64, error)
    UpdateStatus(ctx context.Context, id int64, status domain.Status) error
    Get(ctx context.Context, id int64) (*domain.Listing, error)
}

type Moderator interface {
    Check(ctx context.Context, listingID int64) (approved bool, err error)
}
```

`ListingRepository` и `Moderator` - порты. `service` зависит только от этих
интерфейсов, а не от конкретной БД или HTTP-клиента. `PostgresListingRepository`
и HTTP-реализация `Moderator` - конкретные адаптеры, подключённые к портам
снаружи.

Без порта сервис был бы жёстко привязан к одной реализации:

```go
type ListingService struct {
    db *sql.DB // не интерфейс — конкретный тип
}
func (s *ListingService) Publish(...) {
    s.db.QueryRowContext(...) // SQL прямо в бизнес-логике
}
```

Что придётся переписать, если завтра решим перейти с PostgreSQL на другую БД?
С портом - только новый адаптер в `repository`, `service` не меняется ни
строкой. Без порта пришлось бы трогать сам сервисный слой.

### Dependency Injection

```go
func NewListingService(repo ListingRepository, moderator Moderator) *ListingService {
    return &ListingService{repo: repo, moderator: moderator}
}
```

Конструктор принимает уже готовые реализации портов снаружи, а не создаёт их
сам внутри себя. Это и есть внедрение зависимостей: зависимость не прописана
жёстко внутри `ListingService`, а передаётся ему извне - через аргумент
конструктора.

Контраст без DI:

```go
func NewListingService() *ListingService {
    db, _ := sql.Open("postgres", "...") // жёстко внутри, нельзя заменить
    return &ListingService{repo: &PostgresListingRepository{db: db}}
}
```

Порт определяет, что можно подставить вместо реальной реализации, а DI - это
механизм, как конкретная реализация туда попадает. У нас это самый простой вид
DI в Go - через аргумент конструктора, без всякого DI-фреймворка или
контейнера.

### Тесты без БД и без сети

Именно порты делают это возможным:

```go
type fakeRepo struct{ created *domain.Listing }

func (f *fakeRepo) Create(_ context.Context, l *domain.Listing) (int64, error) {
    f.created = l
    return 42, nil
}
// ...

func TestPublish_ModerationDown_StaysPending(t *testing.T) {
    repo := &fakeRepo{}
    svc := service.NewListingService(repo, &fakeModerator{err: context.DeadlineExceeded})

    listing, _ := svc.Publish(context.Background(), service.PublishInput{
        Title: "lamp", Price: 500, PhotoURL: "http://x/1.jpg", SellerID: 1,
    })
    if listing.Status != domain.StatusPending {
        t.Errorf("want pending when moderation is down, got %s", listing.Status)
    }
}
```

Ни одного SQL-запроса, ни одного HTTP-вызова - тест проверяет только
бизнес-сценарий. `before/handler.go` так протестировать не получится: там
`Publish` неотделим от `*sql.DB` и реального HTTP-клиента.

## Знакомство с DDD

**Bounded context** - одна и та же сущность выглядит по-разному в разных
частях системы, и это нормально. В сервисе поиска то же самое объявление может
быть представлено совсем другим набором полей, чем в сервисе публикации -
важны только `ID`, `Title` и признак «доступно к показу». Это два разных
контекста одной реальной сущности. Слепить их в одну универсальную модель «на
все случаи» обычно кончается разбухшей структурой с кучей необязательных
полей.

**Агрегат** - `Listing` в нашем коде уже агрегат, просто маленький. Корень
агрегата - сам `Listing`, и менять его состояние можно только через его же
методы (`Approve`/`Reject`), а не напрямую полем `Status =`. Та же идея, что в
разделе про богатые модели, только с новым именем: агрегат это богатая модель
плюс правило «снаружи трогать внутренности напрямую нельзя».

## Когда слои - оверинжиниринг

Цифры: `before/handler.go` - 107 строк, весь `after/` - 347 строк. Три слоя
ради CRUD из одного запроса - лишняя индирекция, а не автоматическое благо.

| Метрика | Всё в одном файле (before) | Слои (after) |
|---|---|---|
| Написать первую ручку | быстро | дольше - нужно решить, что в каком пакете |
| Добавить 10-ю похожую ручку | время растёт - копипаста валидации/SQL/HTTP расползается | дешевле - новый сценарий в `service`, остальное уже есть |
| Найти баг в бизнес-правиле | искать по всему хендлеру вперемешку с SQL/HTTP | искать в одном маленьком файле `domain` |
| Протестировать бизнес-правило | нельзя без БД и мока HTTP | `go test` без БД и без сети |
| Влить нового человека в команду | дольше - нужно удержать в голове весь путь запроса | быстрее - можно разобраться в одном слое |

Слои не бесплатны и не всегда нужны с первого дня. Для одной-двух ручек строка
«быстрее написать первую ручку» весит больше всех остальных строк таблицы.
Граница появляется, когда число ручек и бизнес-правил растёт - тогда остальные
строки начинают весить больше первой.

Вот и ответ на вопрос из начала лекции: что будет, если сервис вырастет до 10
ручек. Слои - это ответ на рост, а не универсальное правило с первого дня.

## Итог

- Слой знает только своего соседа, а не всю систему сразу
- Модель защищает свои инварианты сама, а не надеется на внешнюю проверку
- Ошибка переодевается на каждой границе слоя
- Порт отделяет бизнес-сценарий от конкретной БД/HTTP-реализации
- Dependency Injection - механизм, которым конкретная реализация попадает в
  сервис через порт
- Архитектура - это не папки, а направление зависимостей; собственная
  раскладка допустима, если это правило соблюдается
