# Лекция 6. Архитектура сервиса — сквозной пример

Один сценарий — публикация объявления — в двух версиях: `before/` (как
выглядит код, если не следить за границами) и `after/` (тот же сценарий,
разнесённый по слоям). Пример для занятия, план на 90 минут — в
[[Лекция 6. Архитектура сервиса — план]] в Obsidian.

## before/

`before/handler.go` — один файл, одна функция. Парсинг запроса, две
бизнес-проверки, SQL-запрос, HTTP-вызов в сервис модерации и решение,
что ответить клиенту — всё вперемешку. 107 строк, но попробуйте
протестировать бизнес-правило "нет фото — нет публикации" без поднятия
базы и мока HTTP — не получится, код неотделим от инфраструктуры.

Код рабочий (компилируется), но намеренно не подключён к реальной БД —
это иллюстрация, а не рантайм-сервис.

## after/

Тот же сценарий, четыре пакета:

```
after/
├── domain/      Listing — богатая модель, инварианты и переходы статусов
├── service/     ListingService.Publish — бизнес-сценарий + порты (интерфейсы)
├── repository/  адаптеры: Postgres для хранилища, HTTP для модерации
└── handler/     транспортный слой: JSON <-> доменные ошибки <-> HTTP-статусы
```

Направление зависимостей: `handler` → `service` → `domain`.
`repository` реализует интерфейсы из `service/ports.go`, но ничего
не знает про `domain` кроме типов — `service` не знает про `database/sql`
вообще.

## Демо на паре

1. **Открыть before/handler.go, прочитать вслух** — где тут бизнес-правило,
   где SQL, где HTTP-вызов, где ответ клиенту. Обычно на второй-третьей
   строке аудитория перестаёт успевать это разделять в уме — это и есть
   аргумент.
2. **Открыть after/ по очереди**: domain → service/ports.go →
   service/listing_service.go → repository → handler. На каждом файле —
   один вопрос: что этот слой знает, а что принципиально не может знать.
3. **Прогнать тесты**: `go test ./after/... -v`. Обратить внимание на
   `TestPublish_ModerationDown_StaysPending` — то самое решение, которое
   в `before` было неявным "ну пусть будет 201 pending", здесь явное
   и проверяемое.
4. **Посчитать строки**: `wc -l before/handler.go` против суммы файлов
   `after/`. Код вырос почти в 3 раза — это честная цена архитектуры,
   повод для блока "когда слои — оверинжиниринг".

## Запуск

```bash
go build ./...
go vet ./...
go test ./after/... -v
```

`before/` собирается, но не запускается как сервер — в нём нет `main`,
только иллюстративный хендлер.
