# Практика к лекции 6. Архитектура сервиса - вариант 2: бронирование переговорок

Сервис бронирования переговорок - работает правильно по ТЗ, но
архитектурно устроен плохо: весь код в одном файле `main.go`, без
слоёв, без богатых моделей, без явного перевода ошибок, без портов.
Задача команды - за 90 минут привести сервис к такой же структуре, как
`after/` в лекционном репозитории
[lecture6-architecture](https://github.com/course-go-autumn-2026/lecture6-architecture),
**не меняя поведение** сервиса.

## ТЗ (как сервис должен себя вести - это не меняется рефакторингом)

Три ручки:

1. **`POST /bookings`** - забронировать переговорку.
   - Тело: `{"room_id": int64, "employee_id": int64, "start_at": string, "end_at": string}` (время - RFC3339)
   - Правило: `end_at` должно быть позже `start_at` → 400
   - Правило: если на эту комнату на это время уже есть бронь —
     обычному сотруднику (`role = "regular"`) нельзя забронировать
     поверх → 409 `room is already booked for this time`. Админу
     (`role = "admin"`) можно - чужая бронь при этом отменяется.
     Роль смотрим по `employee_id = 1` (`regular`) и `employee_id = 2`
     (`admin`); любой другой `employee_id` считается обычным сотрудником.
   - Перед записью бронь проверяется через сервис доступности комнаты
     (не закрыта ли она на обслуживание). Если сервис ответил, что
     комната свободна - бронь сразу `confirmed`. Если сервис ответил,
     что занята, или был недоступен - бронь уходит в
     `pending_confirmation`.
   - После создания бронь пытается уведомить участников через сервис
     рассылки - это не блокирует создание и не влияет на статус.
   - Успех → 201, тело `{"id": int64, "status": "confirmed"|"pending_confirmation"}`

2. **`GET /bookings/{id}`** - получить бронь.
   - Существует → 200, тело брони целиком
   - Не существует → 404 (пустое тело)

3. **`PATCH /bookings/{id}/time`** - перенести бронь на другое время.
   - Тело: `{"start_at": string, "end_at": string}`
   - Правило: `end_at` должно быть позже `start_at` → 400
   - Бронь не существует → 404
   - Правило: отменённую бронь (`cancelled`) переносить нельзя → 409
     `cannot reschedule cancelled booking`
   - Если бронь была `confirmed`, а новое начало ближе двух часов от
     текущего момента - статус откатывается в `rescheduling` (нужно
     подтвердить заново). Если новое начало дальше двух часов —
     остаётся `confirmed`.
   - Для `pending_confirmation` и `rescheduling` статус после переноса
     не меняется.
   - Успех → 200, тело брони с новым временем

### Машина состояний брони

| Откуда | Куда | Когда |
|---|---|---|
| (создание) | `confirmed` | сервис доступности комнаты подтвердил, что она свободна |
| (создание) | `pending_confirmation` | сервис доступности сказал "занята" или был недоступен |
| (создание) | чужая бронь → `cancelled` | админ бронирует поверх занятого времени |
| `confirmed` | `rescheduling` | `PATCH time`, новое начало ближе двух часов |
| `confirmed` | `confirmed` | `PATCH time`, новое начало дальше двух часов |
| `pending_confirmation` / `rescheduling` | тот же статус | `PATCH time`, время просто меняется |
| `cancelled` | - | `PATCH time` запрещён, 409 |

## Что не так с текущей версией (ориентиры для рефакторинга)

Пять проблем из `main.go`, по одной на каждую тему лекции - они
размазаны по коду, не разложены по отдельным функциям:

1. **Слои.** Валидация, поиск пересечений по времени, роль сотрудника,
   поход в сервис доступности комнаты и в сервис рассылки, запись в
   "БД" (`map[int64]*storedBooking`) и формирование ответа клиенту —
   всё в одной функции `createBookingHandler`. Нет границы между
   HTTP-слоем, бизнес-правилами и хранилищем.

2. **Богатые модели.** `storedBooking` - анемичная структура, все поля
   публичные, статус (`Status string`) - просто строка без ограничений
   на допустимые значения, меняется напрямую (`booking.Status =
   "cancelled"` при победе админа, `booking.StartAt = newStart` в
   `updateTimeHandler`) без прохода через методы модели. Переход
   `confirmed → rescheduling` решается прямым чтением и записью полей,
   а не методом вроде `booking.Reschedule(...)`.

3. **Ошибки по слоям.** Функция `findByID` возвращает `sql.ErrNoRows`
   как есть вызывающему коду, ничего не переводя в доменную ошибку —
   посмотрите на её комментарий. Сами хендлеры используют `map`
   прямо, без всякого слоя хранения, и решение по HTTP-статусу
   размазано по каждому хендлеру отдельно.

4. **Порты и адаптеры.** Ничего не абстрагировано интерфейсом - ни
   хранилище (`map[int64]*storedBooking` используется прямо), ни
   сервис доступности комнаты, ни сервис рассылки (оба раза
   `http.DefaultClient.Do` вызывается прямо в хендлере). Это две
   разные внешние зависимости с разной семантикой отказа: недоступная
   проверка доступности даёт `pending_confirmation`, недоступная
   рассылка молча пропускается (fail-open). Разница видна только по
   месту в коде, а не по сигнатуре порта - нужно решить, как завести
   два порта так, чтобы она была видна в самой абстракции, а не
   терялась внутри реализации.

5. **DDD / границы контекста.** Единственная модель `storedBooking`
   используется одинаково во всех трёх ручках без разделения на то,
   что является бизнес-инвариантом брони (время, статус, переходы) и
   что - деталью хранения (сам факт, что это строка в map). Сотрудник
   (`storedEmployee`, `role`) влияет на правила брони, но живёт в
   отдельной карте без какой-либо связи с бронью кроме `EmployeeID` —
   граница между "бронь как агрегат" и "сотрудник как контекст" никак
   не зафиксирована.

## Как сдавать

1. Форкнуть или склонировать этот репозиторий себе в команду.
2. Отрефакторить, не меняя поведение по ТЗ выше.
3. Открыть Pull Request с рефакторингом до конца пары - преподаватель
   и ревьюер смотрят диф после занятия, не во время.
4. В описании PR - какие из пяти пунктов (слои / модели / ошибки /
   порты / DDD) успели закрыть, честно отметить, если что-то не успели.

## Критерии оценки (2 балла на команду)

Балл дробится по пяти пунктам программы, по 0.4 балла за каждый —
частичный зачёт за то, что успели сделать, не "всё или ничего":

| Пункт | 0.4 балла, если... |
|---|---|
| Слои | Хендлеры, бизнес-правила и хранение разнесены по отдельным файлам/пакетам, граница видна по импортам |
| Богатые модели | Доменная модель брони сама проверяет свои инварианты и переходы статуса (включая откат `confirmed → rescheduling`), а не выставляется полями напрямую |
| Ошибки по слоям | Есть доменные ошибки, которые транспортный слой явно переводит в HTTP-статусы (не `sql.ErrNoRows`/внутренние ошибки наружу) |
| Порты и адаптеры | Хранилище, проверка доступности комнаты и рассылка спрятаны за отдельными интерфейсами, их разная семантика отказа (fail-safe у доступности, fail-open у рассылки) видна в том, как сервис их использует, а не в условиях внутри адаптера |
| DDD | Видно, что модель домена отделена от деталей хранения, а сотрудник (`role`) участвует в правилах брони как часть контекста, а не как случайное поле рядом |

Проверка - глазами по диффу и по этому чек-листу, без автоматического
чекера бизнес-логики. Поведение по ТЗ можно и стоит проверить вручную
через `curl` (см. ниже), но это не формальный автотест, а ориентир для
ревью.

## Запуск и ручная проверка

```bash
go run .
```

```bash
# забронировать переговорку от обычного сотрудника
curl -i -X POST localhost:8080/bookings \
  -d '{"room_id":1,"employee_id":1,"start_at":"2026-11-01T10:00:00Z","end_at":"2026-11-01T11:00:00Z"}'

# попытка забронировать ту же комнату на то же время другим обычным
# сотрудником - 409
curl -i -X POST localhost:8080/bookings \
  -d '{"room_id":1,"employee_id":1,"start_at":"2026-11-01T10:30:00Z","end_at":"2026-11-01T11:30:00Z"}'

# та же попытка от админа - успех, чужая бронь отменяется
curl -i -X POST localhost:8080/bookings \
  -d '{"room_id":1,"employee_id":2,"start_at":"2026-11-01T10:30:00Z","end_at":"2026-11-01T11:30:00Z"}'

# получить бронь
curl -i localhost:8080/bookings/1

# перенести бронь
curl -i -X PATCH localhost:8080/bookings/1/time \
  -d '{"start_at":"2026-11-02T10:00:00Z","end_at":"2026-11-02T11:00:00Z"}'
```

Сервисы доступности комнаты и рассылки (`http://room-availability.internal/check`,
`http://notify.internal/send`) по этим адресам реально не существуют —
в реальном прогоне оба вызова упадут по сети. Для доступности комнаты
это ожидаемо даёт `pending_confirmation` (ровно то поведение, которое
нужно проверить), для рассылки - молчаливый пропуск уведомления и
обычное движение дальше. Это сделано намеренно, чтобы оба случая
недоступности можно было проверить без поднятия сторонних сервисов.

Сценарий с подтверждённой доступностью комнаты (статус `confirmed`
сразу при создании) и откат `confirmed → rescheduling` через `curl`
вручную не воспроизвести - нужен fake за портом доступности, который
отвечает "комната свободна". При рефакторинге подставьте в тесты
fake-реализации порта доступности комнаты и порта рассылки, которые
возвращают нужный результат по запросу - ровно так же, как
`fakeModerator` в лекционном репозитории.
