# Практика к лекции 6. Архитектура сервиса

## Варианты для разных команд

Для очных занятий, где несколько команд работают одновременно, есть
пять вариантов практики - один и тот же набор архитектурных проблем
(слои / богатые модели / ошибки по слоям / порты и адаптеры / DDD) на
разных бизнес-доменах, чтобы соседние команды не могли списать друг у
друга архитектурное решение. Преподаватель один раз раздаёт номера
командам, дальше команда работает только со своим вариантом.

| Вариант | Домен |
|---|---|
| 1 (этот файл, корень `practice/`) | Объявления - создание, модерация, изменение цены |
| [2](variant-2/README.md) | Бронирование переговорок - пересечения по времени, роль админа |
| [3](variant-3/README.md) | Заказ в интернет-магазине - состав заказа, проверка склада |
| [4](variant-4/README.md) | Подписка и биллинг - смена тарифа, повышение/понижение |
| [5](variant-5/README.md) | Модерация комментариев - токсичность, репутация автора |

Сервис объявлений — работает правильно по ТЗ, но архитектурно устроен
плохо: весь код в одном файле `main.go`, без слоёв, без богатых моделей,
без явного перевода ошибок, без портов. Задача команды — за 90 минут
привести сервис к такой же структуре, как `after/` в лекционном
репозитории [lecture6-architecture](https://github.com/course-go-autumn-2026/lecture6-architecture),
**не меняя поведение** сервиса.

## ТЗ (как сервис должен себя вести — это не меняется рефакторингом)

Три ручки:

1. **`POST /listings`** — создать объявление.
   - Тело: `{"title": string, "price": float64, "photo_url": string, "seller_id": int64}`
   - Правило: `price <= 0` → 400 `price must be positive`
   - Правило: пустой `photo_url` → 400 `photo is required`
   - Правило: цена выше порога подозрительности → 400 `price looks
     suspicious`. Порог зависит от продавца: для `seller_id = 1`
     (обычный, `tier = "regular"`) — `10_000_000`, для `seller_id = 2`
     (доверенный, `tier = "trusted"`) — `50_000_000`. Любой другой
     `seller_id` считается обычным продавцом.
   - Перед модерацией объявление проходит антифрод-проверку по паре
     `seller_id` + `price`. Если антифрод заблокировал — объявление
     создаётся сразу со статусом `rejected`, в модерацию уже не идём.
   - Доверенный продавец (`tier = "trusted"`) минует модерацию вообще —
     объявление создаётся сразу со статусом `approved`.
   - Обычный продавец — объявление уходит на модерацию:
     - модерация одобрила → `approved`
     - модерация отклонила → `rejected`
     - модерация недоступна (сетевая ошибка) → `pending`
     - модерация не ответила вовремя (таймаут) → `review`
   - Успех → 201, тело `{"id": int64, "status": "pending"|"approved"|"rejected"|"review"}`

2. **`GET /listings/{id}`** — получить объявление.
   - Существует → 200, тело объявления целиком
   - Не существует → 404 (пустое тело)

3. **`PATCH /listings/{id}/price`** — изменить цену объявления.
   - Тело: `{"price": float64}`
   - Правило: `price <= 0` → 400 `price must be positive`
   - Объявление не существует → 404
   - Правило: объявление со статусом `rejected` менять нельзя → 409
     `cannot update rejected listing`
   - Если объявление было `approved`, а новая цена выше порога
     подозрительности для этого продавца — статус откатывается в
     `pending` (нужна повторная модерация). Если новая цена порог не
     превышает — остаётся `approved`.
   - Для `pending` и `review` статус после смены цены не меняется.
   - Успех → 200, тело объявления с новой ценой

### Машина состояний объявления

| Откуда | Куда | Когда |
|---|---|---|
| (создание) | `rejected` | антифрод заблокировал продавца/цену |
| (создание) | `approved` | продавец `trusted` — модерация не нужна |
| (создание) | `approved` / `rejected` | продавец `regular`, модерация ответила |
| (создание) | `pending` | модерация недоступна (сетевая ошибка) |
| (создание) | `review` | модерация не ответила вовремя (таймаут) |
| `approved` | `pending` | `PATCH price`, новая цена выше порога для продавца |
| `approved` | `approved` | `PATCH price`, новая цена в пределах порога |
| `pending` / `review` | тот же статус | `PATCH price`, цена просто меняется |
| `rejected` | — | `PATCH price` запрещён, 409 |

## Что не так с текущей версией (ориентиры для рефакторинга)

Пять проблем из `main.go`, по одной на каждую тему лекции — они
размазаны по коду, не разложены по отдельным функциям:

1. **Слои.** Валидация, работа с "БД" (`map[int64]*storedListing`),
   поход в антифрод и модерацию, решение по статусу и формирование
   ответа клиенту — всё в одной функции `createListingHandler`. Нет
   границы между HTTP-слоем, бизнес-правилами и хранилищем.

2. **Богатые модели.** `storedListing` - анемичная структура, все поля
   публичные, статус (`Status string`) - просто строка без ограничений
   на допустимые значения, меняется напрямую (`listing.Price = req.Price`
   в `updatePriceHandler`) без прохода через методы модели. Переход
   `approved → pending` при подозрительной смене цены решается прямым
   чтением и записью полей, а не методом вроде `listing.ChangePrice(...)`.

3. **Ошибки по слоям.** Функция `findByID` возвращает `sql.ErrNoRows`
   как есть вызывающему коду, ничего не переводя в доменную ошибку -
   посмотрите на её комментарий. Сами хендлеры используют `map` прямо,
   без всякого слоя хранения, и решение по HTTP-статусу размазано по
   каждому хендлеру отдельно: `w.WriteHeader(http.StatusNotFound)`
   повторяется в двух местах почти одинаково.

4. **Порты и адаптеры.** Ничего не абстрагировано интерфейсом — ни
   хранилище (`map[int64]*storedListing` используется прямо), ни
   модерация, ни антифрод (оба раза `http.DefaultClient.Do` вызывается
   прямо в хендлере). Это две разные внешние зависимости с разной
   семантикой отказа: недоступная модерация даёт `pending`, недоступный
   антифрод молча пропускает проверку (fail-open). Разница видна только
   по месту в коде, а не по сигнатуре порта - нужно решить, как завести
   два порта так, чтобы она была видна в самой абстракции, а не терялась
   внутри реализации.

5. **DDD / границы контекста.** Единственная модель `storedListing`
   используется одинаково во всех трёх ручках без разделения на то,
   что является бизнес-инвариантом объявления (цена, статус, переходы)
   и что - деталью хранения (сам факт, что это строка в map). Продавец
   (`storedSeller`, `tier`) влияет на правила объявления, но живёт в
   отдельной карте без какой-либо связи с объявлением кроме `SellerID` -
   граница между "объявление как агрегат" и "продавец как контекст"
   никак не зафиксирована.

## Как сдавать

1. Форкнуть или склонировать этот репозиторий себе в команду.
2. Отрефакторить, не меняя поведение по ТЗ выше.
3. Открыть Pull Request с рефакторингом до конца пары — преподаватель
   и ревьюер смотрят диф после занятия, не во время.
4. В описании PR — какие из пяти пунктов (слои / модели / ошибки /
   порты / DDD) успели закрыть, честно отметить, если что-то не успели.

## Критерии оценки (2 балла на команду)

Балл дробится по пяти пунктам программы, по 0.4 балла за каждый —
частичный зачёт за то, что успели сделать, не "всё или ничего":

| Пункт | 0.4 балла, если... |
|---|---|
| Слои | Хендлеры, бизнес-правила и хранение разнесены по отдельным файлам/пакетам, граница видна по импортам |
| Богатые модели | Доменная модель объявления сама проверяет свои инварианты и переходы статуса (включая откат `approved → pending`), а не выставляется полями напрямую |
| Ошибки по слоям | Есть доменные ошибки, которые транспортный слой явно переводит в HTTP-статусы (не `sql.ErrNoRows`/внутренние ошибки наружу) |
| Порты и адаптеры | Хранилище, модерация и антифрод спрятаны за отдельными интерфейсами, их разная семантика отказа (fail-safe у модерации, fail-open у антифрода) видна в том, как сервис их использует, а не в условиях внутри адаптера |
| DDD | Видно, что модель домена отделена от деталей хранения, а продавец (`tier`) участвует в правилах объявления как часть контекста, а не как случайное поле рядом |

Проверка — глазами по диффу и по этому чек-листу, без автоматического
чекера бизнес-логики. Поведение по ТЗ можно и стоит проверить вручную
через `curl` (см. ниже), но это не формальный автотест, а ориентир для
ревью.

## Запуск и ручная проверка

```bash
go run .
```

```bash
# создать объявление от обычного продавца
curl -i -X POST localhost:8080/listings \
  -d '{"title":"lamp","price":500,"photo_url":"http://x/1.jpg","seller_id":1}'

# создать объявление от доверенного продавца — минует модерацию,
# сразу approved, и порог подозрительной цены для него выше
curl -i -X POST localhost:8080/listings \
  -d '{"title":"car","price":20000000,"photo_url":"http://x/2.jpg","seller_id":2}'

# получить объявление
curl -i localhost:8080/listings/1

# изменить цену
curl -i -X PATCH localhost:8080/listings/1/price -d '{"price":700}'
```

Сервисы модерации и антифрода (`http://moderation.internal/check`,
`http://antifraud.internal/check`) по этим адресам реально не
существуют — в реальном прогоне оба вызова упадут по сети. Для
модерации это ожидаемо даёт `pending` (ровно то поведение, которое
нужно проверить), для антифрода — молчаливый пропуск проверки и
обычное движение дальше. Это сделано намеренно, чтобы оба случая
недоступности можно было проверить без поднятия сторонних сервисов.

Остальные сценарии через `curl` вручную не воспроизвести — нужен fake
за портом:

- блокировку антифродом,
- таймаут модерации (статус `review`),
- одобрение/отклонение модерацией (статус `approved`/`rejected` для
  обычного продавца),
- откат `approved → pending` при подозрительной смене цены.

При рефакторинге подставьте в тесты fake-реализации порта модерации и
порта антифрода, которые возвращают нужный результат по запросу —
ровно так же, как `fakeModerator` в лекционном репозитории.
