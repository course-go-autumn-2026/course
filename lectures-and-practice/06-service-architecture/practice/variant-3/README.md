# Практика к лекции 6. Архитектура сервиса - вариант 3: заказ в интернет-магазине

Сервис заказов интернет-магазина - работает правильно по ТЗ, но
архитектурно устроен плохо: весь код в одном файле `main.go`, без
слоёв, без богатых моделей, без явного перевода ошибок, без портов.
Задача команды - за 90 минут привести сервис к такой же структуре, как
`after/` в лекционном репозитории
[lecture6-architecture](https://github.com/course-go-autumn-2026/lecture6-architecture),
**не меняя поведение** сервиса.

## ТЗ (как сервис должен себя вести - это не меняется рефакторингом)

Три ручки:

1. **`POST /orders`** - создать заказ.
   - Тело: `{"customer_id": int64, "items": [{"sku": string, "quantity": int, "price": float64}]}`
   - Правило: заказ без позиций → 400 `order must have at least one item`
   - Правило: `quantity <= 0` или `price <= 0` у любой позиции → 400
   - Правило: сумма заказа выше лимита → 400 `order total exceeds
     limit for this customer`. Лимит зависит от уровня клиента: для
     `customer_id = 1` (`regular`) - `100_000`, для `customer_id = 2`
     (`vip`) - `1_000_000`. Любой другой `customer_id` считается новым
     клиентом (`new`) с лимитом как у `regular`.
   - Перед проверкой склада заказ проходит антифрод-проверку платежа.
     Если антифрод заблокировал - 403 `payment looks fraudulent`,
     заказ не создаётся.
   - После создания заказ проверяется через сервис склада:
     - склад подтвердил наличие → `confirmed`
     - склад отказал или недоступен → `pending_stock`
   - Успех → 201, тело `{"id": int64, "status": "confirmed"|"pending_stock"}`

2. **`GET /orders/{id}`** - получить заказ.
   - Существует → 200, тело заказа целиком
   - Не существует → 404 (пустое тело)

3. **`PATCH /orders/{id}/items`** - изменить состав заказа.
   - Тело: `{"items": [{"sku": string, "quantity": int, "price": float64}]}`
   - Правило: заказ без позиций → 400
   - Заказ не существует → 404
   - Правило: отменённый заказ (`cancelled`) менять нельзя → 409
     `cannot update cancelled order`
   - Если заказ был `confirmed`, а новый состав требует больше единиц
     товара суммарно, чем подтвердил склад при создании - статус
     откатывается в `pending_stock` (нужна повторная проверка склада).
     Если состав не превышает подтверждённое количество - остаётся
     `confirmed`.
   - Для `created` и `pending_stock` статус после изменения состава не
     меняется.
   - Успех → 200, тело заказа с новым составом и пересчитанной суммой

### Машина состояний заказа

| Откуда | Куда | Когда |
|---|---|---|
| (создание) | - (403, заказ не создаётся) | антифрод заблокировал платёж |
| (создание) | `confirmed` | склад подтвердил наличие товара |
| (создание) | `pending_stock` | склад отказал или был недоступен |
| `confirmed` | `pending_stock` | `PATCH items`, новый состав требует больше товара, чем подтвердил склад |
| `confirmed` | `confirmed` | `PATCH items`, новый состав не превышает подтверждённое количество |
| `created` / `pending_stock` | тот же статус | `PATCH items`, состав просто меняется |
| `cancelled` | - | `PATCH items` запрещён, 409 |

## Что не так с текущей версией (ориентиры для рефакторинга)

Пять проблем из `main.go`, по одной на каждую тему лекции - они
размазаны по коду, не разложены по отдельным функциям:

1. **Слои.** Валидация, уровень клиента, лимит суммы, антифрод-проверка
   платежа, запись в "БД" (`map[int64]*storedOrder`), поход в сервис
   склада и формирование ответа клиенту - всё в одной функции
   `createOrderHandler`. Нет границы между HTTP-слоем, бизнес-правилами
   и хранилищем.

2. **Богатые модели.** `storedOrder` - анемичная структура, все поля
   публичные, статус (`Status string`) - просто строка без ограничений
   на допустимые значения, меняется напрямую (`order.Items =
   req.Items` в `updateItemsHandler`) без прохода через методы модели.
   Переход `confirmed → pending_stock` решается прямым чтением и
   записью полей, а не методом вроде `order.ChangeItems(...)`.

3. **Ошибки по слоям.** Функция `findByID` возвращает `sql.ErrNoRows`
   как есть вызывающему коду, ничего не переводя в доменную ошибку —
   посмотрите на её комментарий. Сами хендлеры используют `map`
   прямо, без всякого слоя хранения, и решение по HTTP-статусу
   размазано по каждому хендлеру отдельно.

4. **Порты и адаптеры.** Ничего не абстрагировано интерфейсом - ни
   хранилище (`map[int64]*storedOrder` используется прямо), ни сервис
   склада, ни антифрод платежа (оба раза `http.DefaultClient.Do`
   вызывается прямо в хендлере). Это две разные внешние зависимости с
   разной семантикой отказа: недоступный склад даёт `pending_stock`,
   недоступный антифрод молча пропускает проверку (fail-open). Разница
   видна только по месту в коде, а не по сигнатуре порта - нужно
   решить, как завести два порта так, чтобы она была видна в самой
   абстракции, а не терялась внутри реализации.

5. **DDD / границы контекста.** Единственная модель `storedOrder`
   используется одинаково во всех трёх ручках без разделения на то,
   что является бизнес-инвариантом заказа (состав, сумма, статус,
   переходы) и что - деталью хранения (сам факт, что это строка в
   map). Клиент (`storedCustomer`, `level`) влияет на правила заказа,
   но живёт в отдельной карте без какой-либо связи с заказом кроме
   `CustomerID` - граница между "заказ как агрегат" и "клиент как
   контекст" никак не зафиксирована.

## Как сдавать

1. Форкнуть или склонировать этот репозиторий себе в команду.
2. Отрефакторить, не меняя поведение по ТЗ выше.
3. Открыть Pull Request с рефакторингом до конца пары - преподаватель
   и ревьюер смотрят диф после занятия, не во время.
4. В описании PR - какие из пяти пунктов (слои / модели / ошибки /
   порты / DDD) успели закрыть, честно отметить, если что-то не успели.

## Критерии оценки (2 балла на команду)

Балл дробится по пяти пунктам программы, по 0.4 балла за каждый —
частичный зачёт за то, что успели сделать, не "всё или ничего":

| Пункт | 0.4 балла, если... |
|---|---|
| Слои | Хендлеры, бизнес-правила и хранение разнесены по отдельным файлам/пакетам, граница видна по импортам |
| Богатые модели | Доменная модель заказа сама проверяет свои инварианты и переходы статуса (включая откат `confirmed → pending_stock`), а не выставляется полями напрямую |
| Ошибки по слоям | Есть доменные ошибки, которые транспортный слой явно переводит в HTTP-статусы (не `sql.ErrNoRows`/внутренние ошибки наружу) |
| Порты и адаптеры | Хранилище, проверка склада и антифрод платежа спрятаны за отдельными интерфейсами, их разная семантика отказа (fail-safe у склада, fail-open у антифрода) видна в том, как сервис их использует, а не в условиях внутри адаптера |
| DDD | Видно, что модель домена отделена от деталей хранения, а клиент (`level`) участвует в правилах заказа как часть контекста, а не как случайное поле рядом |

Проверка - глазами по диффу и по этому чек-листу, без автоматического
чекера бизнес-логики. Поведение по ТЗ можно и стоит проверить вручную
через `curl` (см. ниже), но это не формальный автотест, а ориентир для
ревью.

## Запуск и ручная проверка

```bash
go run .
```

```bash
# создать заказ от обычного клиента
curl -i -X POST localhost:8080/orders \
  -d '{"customer_id":1,"items":[{"sku":"lamp","quantity":2,"price":500}]}'

# создать заказ от vip-клиента на большую сумму - лимит для него выше
curl -i -X POST localhost:8080/orders \
  -d '{"customer_id":2,"items":[{"sku":"sofa","quantity":1,"price":300000}]}'

# получить заказ
curl -i localhost:8080/orders/1

# изменить состав заказа
curl -i -X PATCH localhost:8080/orders/1/items \
  -d '{"items":[{"sku":"lamp","quantity":5,"price":500}]}'
```

Сервисы склада и антифрода (`http://stock-check.internal/check`,
`http://payment-fraud.internal/check`) по этим адресам реально не
существуют - в реальном прогоне оба вызова упадут по сети. Для склада
это ожидаемо даёт `pending_stock` (ровно то поведение, которое нужно
проверить), для антифрода - молчаливый пропуск проверки и обычное
движение дальше. Это сделано намеренно, чтобы оба случая недоступности
можно было проверить без поднятия сторонних сервисов.

Сценарий с подтверждённым складом (статус `confirmed` сразу при
создании) и откат `confirmed → pending_stock` через `curl` вручную не
воспроизвести - нужен fake за портом склада, который отвечает "товар в
наличии". При рефакторинге подставьте в тесты fake-реализации порта
склада и порта антифрода, которые возвращают нужный результат по
запросу - ровно так же, как `fakeModerator` в лекционном репозитории.
