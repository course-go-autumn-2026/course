# Практика к лекции 6. Архитектура сервиса - вариант 5: модерация комментариев

Сервис комментариев - работает правильно по ТЗ, но архитектурно
устроен плохо: весь код в одном файле `main.go`, без слоёв, без
богатых моделей, без явного перевода ошибок, без портов. Задача
команды - за 90 минут привести сервис к такой же структуре, как
`after/` в лекционном репозитории
[lecture6-architecture](https://github.com/course-go-autumn-2026/lecture6-architecture),
**не меняя поведение** сервиса.

## ТЗ (как сервис должен себя вести - это не меняется рефакторингом)

Три ручки:

1. **`POST /comments`** - опубликовать комментарий.
   - Тело: `{"author_id": int64, "text": string}`
   - Правило: пустой `text` → 400 `text is required`
   - Комментарий проходит спам-фильтр. Если фильтр заблокировал → 400
     `comment looks like spam`, комментарий не создаётся.
   - Дальше комментарий проходит проверку токсичности:
     - сервис ответил "токсично" → `hidden`
     - сервис ответил "не токсично", автор доверенный
       (`reputation = "trusted"`) → `published`
     - сервис ответил "не токсично", автор новый
       (`reputation = "new"`) → остаётся `pending` (у нового автора
       нет пути мимо ручной модерации, даже если текст не токсичен)
     - сервис проверки токсичности недоступен → `pending`
   - Репутацию смотрим по `author_id = 1` (`new`) и `author_id = 2`
     (`trusted`); любой другой `author_id` считается новым автором.
   - Успех → 201, тело `{"id": int64, "status": "pending"|"published"|"hidden"}`

2. **`GET /comments/{id}`** - получить комментарий.
   - Существует → 200, тело комментария целиком
   - Не существует → 404 (пустое тело)

3. **`PATCH /comments/{id}/text`** - отредактировать текст.
   - Тело: `{"text": string}`
   - Правило: пустой `text` → 400
   - Комментарий не существует → 404
   - Правило: скрытый комментарий (`hidden`) редактировать нельзя →
     409 `cannot edit a hidden comment`
   - Если комментарий был `published`, новый текст заново проходит
     проверку токсичности:
     - сервис ответил "токсично" или был недоступен → статус
       откатывается в `pending`
     - сервис ответил "не токсично" → остаётся `published`
   - Для `pending` статус после редактирования не меняется.
   - Успех → 200, тело комментария с новым текстом

### Машина состояний комментария

| Откуда | Куда | Когда |
|---|---|---|
| (создание) | - (400, комментарий не создаётся) | спам-фильтр заблокировал |
| (создание) | `published` | автор доверенный, токсичность не превышена |
| (создание) | `pending` | автор новый (всегда), или токсичность недоступна |
| (создание) | `hidden` | проверка токсичности ответила "токсично" |
| `published` | `pending` | `PATCH text`, новый текст токсичен или сервис проверки недоступен |
| `published` | `published` | `PATCH text`, новый текст не токсичен |
| `pending` | тот же статус | `PATCH text`, текст просто меняется |
| `hidden` | - | `PATCH text` запрещён, 409 |

## Что не так с текущей версией (ориентиры для рефакторинга)

Пять проблем из `main.go`, по одной на каждую тему лекции - они
размазаны по коду, не разложены по отдельным функциям:

1. **Слои.** Валидация, спам-фильтр, репутация автора, поход в сервис
   проверки токсичности, запись в "БД" (`map[int64]*storedComment`) и
   формирование ответа клиенту - всё в одной функции
   `createCommentHandler`. Нет границы между HTTP-слоем, бизнес-
   правилами и хранилищем.

2. **Богатые модели.** `storedComment` - анемичная структура, все поля
   публичные, статус (`Status string`) - просто строка без ограничений
   на допустимые значения, меняется напрямую (`comment.Text =
   req.Text` в `updateTextHandler`) без прохода через методы модели.
   Переход `published → pending` решается прямым чтением и записью
   полей, а не методом вроде `comment.ChangeText(...)`.

3. **Ошибки по слоям.** Функция `findByID` возвращает `sql.ErrNoRows`
   как есть вызывающему коду, ничего не переводя в доменную ошибку —
   посмотрите на её комментарий. Сами хендлеры используют `map`
   прямо, без всякого слоя хранения, и решение по HTTP-статусу
   размазано по каждому хендлеру отдельно.

4. **Порты и адаптеры.** Ничего не абстрагировано интерфейсом - ни
   хранилище (`map[int64]*storedComment` используется прямо), ни
   спам-фильтр, ни проверка токсичности (оба раза
   `http.DefaultClient.Do` вызывается прямо в хендлере). Это две
   разные внешние зависимости с разной семантикой отказа: недоступная
   проверка токсичности даёт `pending`, недоступный спам-фильтр молча
   пропускает проверку (fail-open). Разница видна только по месту в
   коде, а не по сигнатуре порта - нужно решить, как завести два
   порта так, чтобы она была видна в самой абстракции, а не терялась
   внутри реализации.

5. **DDD / границы контекста.** Единственная модель `storedComment`
   используется одинаково во всех трёх ручках без разделения на то,
   что является бизнес-инвариантом комментария (текст, статус,
   переходы) и что - деталью хранения (сам факт, что это строка в
   map). Автор (`storedAuthor`, `reputation`) влияет на правила
   комментария, но живёт в отдельной карте без какой-либо связи с
   комментарием кроме `AuthorID` - граница между "комментарий как
   агрегат" и "автор как контекст" никак не зафиксирована.

## Как сдавать

1. Форкнуть или склонировать этот репозиторий себе в команду.
2. Отрефакторить, не меняя поведение по ТЗ выше.
3. Открыть Pull Request с рефакторингом до конца пары - преподаватель
   и ревьюер смотрят диф после занятия, не во время.
4. В описании PR - какие из пяти пунктов (слои / модели / ошибки /
   порты / DDD) успели закрыть, честно отметить, если что-то не успели.

## Критерии оценки (2 балла на команду)

Балл дробится по пяти пунктам программы, по 0.4 балла за каждый —
частичный зачёт за то, что успели сделать, не "всё или ничего":

| Пункт | 0.4 балла, если... |
|---|---|
| Слои | Хендлеры, бизнес-правила и хранение разнесены по отдельным файлам/пакетам, граница видна по импортам |
| Богатые модели | Доменная модель комментария сама проверяет свои инварианты и переходы статуса (включая откат `published → pending`), а не выставляется полями напрямую |
| Ошибки по слоям | Есть доменные ошибки, которые транспортный слой явно переводит в HTTP-статусы (не `sql.ErrNoRows`/внутренние ошибки наружу) |
| Порты и адаптеры | Хранилище, спам-фильтр и проверка токсичности спрятаны за отдельными интерфейсами, их разная семантика отказа (fail-safe у токсичности, fail-open у спам-фильтра) видна в том, как сервис их использует, а не в условиях внутри адаптера |
| DDD | Видно, что модель домена отделена от деталей хранения, а автор (`reputation`) участвует в правилах комментария как часть контекста, а не как случайное поле рядом |

Проверка - глазами по диффу и по этому чек-листу, без автоматического
чекера бизнес-логики. Поведение по ТЗ можно и стоит проверить вручную
через `curl` (см. ниже), но это не формальный автотест, а ориентир для
ревью.

## Запуск и ручная проверка

```bash
go run .
```

```bash
# опубликовать комментарий от нового автора
curl -i -X POST localhost:8080/comments \
  -d '{"author_id":1,"text":"hello there"}'

# опубликовать комментарий от доверенного автора
curl -i -X POST localhost:8080/comments \
  -d '{"author_id":2,"text":"hello there"}'

# получить комментарий
curl -i localhost:8080/comments/1

# отредактировать текст
curl -i -X PATCH localhost:8080/comments/1/text \
  -d '{"text":"edited text"}'
```

Сервисы спам-фильтра и проверки токсичности
(`http://spam-filter.internal/check`, `http://toxicity-check.internal/score`)
по этим адресам реально не существуют - в реальном прогоне оба вызова
упадут по сети. Для проверки токсичности это ожидаемо даёт `pending`
(ровно то поведение, которое нужно проверить и для нового, и для
доверенного автора), для спам-фильтра - молчаливый пропуск проверки и
обычное движение дальше. Это сделано намеренно, чтобы оба случая
недоступности можно было проверить без поднятия сторонних сервисов.

Сценарий `published` при создании (нужен доверенный автор и ответ "не
токсично" от сервиса) и откат `published → pending` через `curl`
вручную не воспроизвести - нужен fake за портом проверки токсичности,
который отвечает "не токсично" или "токсично" по запросу. При
рефакторинге подставьте в тесты fake-реализации порта спам-фильтра и
порта проверки токсичности - ровно так же, как `fakeModerator` в
лекционном репозитории.
