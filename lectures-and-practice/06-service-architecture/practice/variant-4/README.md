# Практика к лекции 6. Архитектура сервиса - вариант 4: подписка и биллинг

Сервис подписок - работает правильно по ТЗ, но архитектурно устроен
плохо: весь код в одном файле `main.go`, без слоёв, без богатых
моделей, без явного перевода ошибок, без портов. Задача команды - за
90 минут привести сервис к такой же структуре, как `after/` в
лекционном репозитории
[lecture6-architecture](https://github.com/course-go-autumn-2026/lecture6-architecture),
**не меняя поведение** сервиса.

## ТЗ (как сервис должен себя вести - это не меняется рефакторингом)

Три ручки:

1. **`POST /subscriptions`** - оформить подписку.
   - Тело: `{"account_id": int64, "plan": string}` (`plan` - один из
     `basic`, `pro`, `max`)
   - Правило: неизвестный `plan` → 400 `unknown plan`
   - Перед созданием подписка проходит антифрод-проверку карты. Если
     антифрод заблокировал - 403 `card looks fraudulent`, подписка не
     создаётся.
   - Успех → 201, тело `{"id": int64, "status": "trial"}` - любая
     новая подписка начинается с пробного периода.

2. **`GET /subscriptions/{id}`** - получить подписку.
   - Существует → 200, тело подписки целиком
   - Не существует → 404 (пустое тело)

3. **`PATCH /subscriptions/{id}/plan`** - сменить тариф.
   - Тело: `{"plan": string}`
   - Правило: неизвестный `plan` → 400
   - Подписка не существует → 404
   - Правило: приостановленную подписку (`suspended`) менять нельзя →
     409 `cannot change plan of a suspended subscription`
   - Понижение тарифа (`max → pro`, `pro → basic` и так далее)
     разрешено только если у аккаунта нет активной задолженности →
     иначе 409 `cannot downgrade plan with an active debt`. Задолженность
     смотрим по `account_id = 1` (без долга) и `account_id = 2` (с
     долгом); любой другой `account_id` считается без задолженности.
   - Повышение тарифа у активной подписки (`status = "active"`)
     требует успешного биллинга у платёжного провайдера:
     - биллинг прошёл → подписка остаётся `active`
     - биллинг отказал или провайдер недоступен → подписка
       откатывается в `payment_pending`
   - Для `trial` и `payment_pending` повышение/понижение тарифа просто
     меняет поле `plan`, без похода к провайдеру.
   - Успех → 200, тело подписки с новым тарифом

### Машина состояний подписки

| Откуда | Куда | Когда |
|---|---|---|
| (создание) | `trial` | подписка оформлена, антифрод не заблокировал |
| (создание) | - (403, подписка не создаётся) | антифрод заблокировал карту |
| `active` | `payment_pending` | `PATCH plan` (повышение), биллинг отказал или провайдер недоступен |
| `active` | `active` | `PATCH plan` (повышение), биллинг прошёл успешно |
| `active` | `active` | `PATCH plan` (понижение), у аккаунта нет задолженности |
| `active` / `trial` / `payment_pending` | - | `PATCH plan` (понижение), у аккаунта есть задолженность → 409 |
| `trial` / `payment_pending` | тот же статус | `PATCH plan`, тариф меняется без похода к провайдеру |
| `suspended` | - | `PATCH plan` запрещён, 409 |

## Что не так с текущей версией (ориентиры для рефакторинга)

Пять проблем из `main.go`, по одной на каждую тему лекции - они
размазаны по коду, не разложены по отдельным функциям:

1. **Слои.** Валидация тарифа, антифрод-проверка карты, запись в "БД"
   (`map[int64]*storedSubscription`) и формирование ответа клиенту —
   всё в одной функции `createSubscriptionHandler`. В `updatePlanHandler`
   к этому добавляется поход в платёжного провайдера. Нет границы
   между HTTP-слоем, бизнес-правилами и хранилищем.

2. **Богатые модели.** `storedSubscription` - анемичная структура, все
   поля публичные, статус (`Status string`) - просто строка без
   ограничений на допустимые значения, меняется напрямую (`sub.Plan =
   req.Plan` в `updatePlanHandler`) без прохода через методы модели.
   Переход `active → payment_pending` решается прямым чтением и
   записью полей, а не методом вроде `sub.ChangePlan(...)`.

3. **Ошибки по слоям.** Функция `findByID` возвращает `sql.ErrNoRows`
   как есть вызывающему коду, ничего не переводя в доменную ошибку —
   посмотрите на её комментарий. Сами хендлеры используют `map`
   прямо, без всякого слоя хранения, и решение по HTTP-статусу
   размазано по каждому хендлеру отдельно.

4. **Порты и адаптеры.** Ничего не абстрагировано интерфейсом - ни
   хранилище (`map[int64]*storedSubscription` используется прямо), ни
   платёжный провайдер, ни антифрод карты (оба раза
   `http.DefaultClient.Do` вызывается прямо в хендлере). Это две
   разные внешние зависимости с разной семантикой отказа: недоступный
   провайдер даёт `payment_pending`, недоступный антифрод молча
   пропускает проверку (fail-open). Разница видна только по месту в
   коде, а не по сигнатуре порта - нужно решить, как завести два порта
   так, чтобы она была видна в самой абстракции, а не терялась внутри
   реализации.

5. **DDD / границы контекста.** Единственная модель `storedSubscription`
   используется одинаково во всех трёх ручках без разделения на то,
   что является бизнес-инвариантом подписки (тариф, статус, переходы)
   и что - деталью хранения (сам факт, что это строка в map). Аккаунт
   (`storedAccount`, `HasDebt`) влияет на правила подписки, но живёт в
   отдельной карте без какой-либо связи с подпиской кроме `AccountID`
   - граница между "подписка как агрегат" и "аккаунт как контекст"
   никак не зафиксирована.

## Как сдавать

1. Форкнуть или склонировать этот репозиторий себе в команду.
2. Отрефакторить, не меняя поведение по ТЗ выше.
3. Открыть Pull Request с рефакторингом до конца пары - преподаватель
   и ревьюер смотрят диф после занятия, не во время.
4. В описании PR - какие из пяти пунктов (слои / модели / ошибки /
   порты / DDD) успели закрыть, честно отметить, если что-то не успели.

## Критерии оценки (2 балла на команду)

Балл дробится по пяти пунктам программы, по 0.4 балла за каждый —
частичный зачёт за то, что успели сделать, не "всё или ничего":

| Пункт | 0.4 балла, если... |
|---|---|
| Слои | Хендлеры, бизнес-правила и хранение разнесены по отдельным файлам/пакетам, граница видна по импортам |
| Богатые модели | Доменная модель подписки сама проверяет свои инварианты и переходы статуса (включая откат `active → payment_pending`), а не выставляется полями напрямую |
| Ошибки по слоям | Есть доменные ошибки, которые транспортный слой явно переводит в HTTP-статусы (не `sql.ErrNoRows`/внутренние ошибки наружу) |
| Порты и адаптеры | Хранилище, платёжный провайдер и антифрод карты спрятаны за отдельными интерфейсами, их разная семантика отказа (fail-safe у провайдера, fail-open у антифрода) видна в том, как сервис их использует, а не в условиях внутри адаптера |
| DDD | Видно, что модель домена отделена от деталей хранения, а аккаунт (`HasDebt`) участвует в правилах подписки как часть контекста, а не как случайное поле рядом |

Проверка - глазами по диффу и по этому чек-листу, без автоматического
чекера бизнес-логики. Поведение по ТЗ можно и стоит проверить вручную
через `curl` (см. ниже), но это не формальный автотест, а ориентир для
ревью.

## Запуск и ручная проверка

```bash
go run .
```

```bash
# оформить подписку
curl -i -X POST localhost:8080/subscriptions \
  -d '{"account_id":1,"plan":"basic"}'

# получить подписку
curl -i localhost:8080/subscriptions/1

# сменить тариф (trial - повышение без похода к провайдеру)
curl -i -X PATCH localhost:8080/subscriptions/1/plan \
  -d '{"plan":"pro"}'
```

Сервисы провайдера и антифрода (`http://billing-provider.internal/charge`,
`http://card-fraud.internal/check`) по этим адресам реально не
существуют - в реальном прогоне оба вызова упадут по сети. Для
провайдера это имеет значение только у `active`-подписки при повышении
тарифа (ожидаемо даёт `payment_pending`), для антифрода - молчаливый
пропуск проверки и обычное движение дальше при создании. Это сделано
намеренно, чтобы оба случая недоступности можно было проверить без
поднятия сторонних сервисов.

Сценарий с подпиской в статусе `active` и успешным биллингом через
`curl` вручную не воспроизвести - изначально любая подписка создаётся
в `trial`, а провайдер по факту недоступен. При рефакторинге подставьте
в тесты fake-реализации порта провайдера и порта антифрода, которые
возвращают нужный результат по запросу, и fake-репозиторий, позволяющий
завести подписку сразу в статусе `active` - ровно так же, как
`fakeModerator` в лекционном репозитории.
