## 1. Базовые понятия

| Термин | Что значит | Пример |
| --- | --- | --- |
| Конкурентность | Программа ведёт несколько задач сразу и переключается между ними | Один официант обслуживает пять столиков |
| Параллелизм | Задачи физически выполняются в один момент на разных ядрах | Пять официантов, у каждого свой столик |
| Асинхронность | Запустили операцию и не ждём её, результат придёт потом | Заказали кофе и сели за столик, вас позовут |

- **I/O-bound** — задача в основном ждёт: базу, сеть, диск. Ускоряется конкурентностью:
  пока один запрос ждёт ответа, остальные тоже ждут, а не стоят в очереди.
  5 запросов по 200 мс: по очереди — 1 с, конкурентно — 200 мс.
- **CPU-bound** — задача считает. Ускоряется только параллелизмом, то есть ядрами.
  Больше горутин, чем ядер, такой задаче не поможет.

## 2. Горутины

```go
go send(email)            // запустить функцию в новой горутине
go func() { work() }()    // то же для анонимной функции: () в конце — вызов
```

- Горутина — лёгкая задача, которой управляет рантайм Go, а не ОС.
  Стек начинается с ~2 КБ (у потока ОС — 1–8 МБ), поэтому горутин могут быть сотни тысяч.
- Рантайм раскладывает горутины по нескольким потокам ОС; Go-код одновременно выполняют
  столько потоков, сколько ядер (модель GMP, `GOMAXPROCS`).
  Горутина ждёт сеть — засыпает только она, поток берёт другую горутину.
- **Когда `main` завершается, все горутины умирают.** Ждать их нужно явно: через WaitGroup или канал.
- С Go 1.22 переменная цикла своя на каждой итерации. Писать `go func(i int) {...}(i)` больше не обязательно.

## 3. sync.WaitGroup — дождаться группы горутин

WaitGroup — счётчик горутин, которые ещё не закончили.

```go
var wg sync.WaitGroup
for i := range 3 {
	wg.Add(1)          // +1: «запускаю ещё одну» — ДО go
	go func() {
		defer wg.Done() // −1: «я закончила» — через defer
		work(i)
	}()
}
wg.Wait()              // ждём, пока счётчик станет 0
```

С Go 1.25 то же короче: `wg.Go(func() { work(i) })` сам делает `Add(1)` и `Done()`.

| Ошибка | Что будет |
| --- | --- |
| `wg.Add` внутри горутины | `Wait` может увидеть 0 и вернуться раньше времени. Ловит `go vet` |
| Забыли `Done` на раннем `return` | Счётчик не дойдёт до 0, `Wait` ждёт вечно → deadlock |

## 4. Каналы

```go
ch := make(chan int)          // небуферизованный: отправитель ждёт получателя
buffered := make(chan int, 10) // буферизованный: отправка не ждёт, пока есть место

ch <- 1                   // отправить
v := <-ch                 // получить
v, ok := <-ch             // ok == false — канал закрыт и пуст
for v := range ch {}      // читать, пока канал не закроют
close(ch)                 // «данных больше не будет»
```

**Что происходит с операциями:**

| Операция | Открытый канал | Закрытый канал |
| --- | --- | --- |
| Получить `<-ch` | ждёт значение | сразу отдаёт нулевое значение, `ok == false` |
| Отправить `ch <- v` | ждёт получателя или места в буфере | **panic** |
| Закрыть `close(ch)` | закрывает | **panic** |

**Правила:**

- **Закрывает канал только отправитель** (владелец). Получатель не закрывает: отправитель упадёт с panic.
  Если отправителей несколько, канал закрывают после того, как остановились все.
- Закрывать канал нужно, только если получатель ждёт конца данных (`range`). Иначе это не обязательно.
- Направление в сигнатуре: `<-chan int` — только читать, `chan<- int` — только писать.
  Компилятор не даст функции писать в канал для чтения или закрыть его.
- Канал-сигнал — `chan struct{}`: данные не передаём, канал закрываем.
  `close` будит **всех**, кто ждёт на `<-ch`. Так устроен `ctx.Done()`.

## 5. select — ждать несколько каналов

```go
select {
case msg := <-ch1:        // что готово первым, то и выполнится
	handle(msg)
case ch2 <- value:
case <-ctx.Done():
	return ctx.Err()
case <-time.After(time.Second):
	return ErrTimeout
}
```

- Если готовы несколько веток, выбирается одна псевдослучайно.
- `default` срабатывает сразу, если ни одна ветка не готова. Это **неблокирующая** операция:

```go
select {
case queue <- task:  // место есть — поставили
default:             // очередь полна — не ждём, считаем задачу отброшенной
}
```

- **Не ставьте `default` в цикл ожидания.** Без событий цикл крутится миллионы раз в секунду и держит
  ядро на 100%. Ожидающий `select` должен быть без `default`: тогда горутина спит до события.

## 6. context — отмена и таймауты

Контекст передают первым аргументом по всей цепочке вызовов. С его помощью сверху можно сказать
«хватит» всем, кто работает над задачей.

```go
ctx, cancel := context.WithCancel(parent) // отменим сами, вызвав cancel()
// или: ctx, cancel := context.WithTimeout(parent, time.Second) — отменится через секунду
defer cancel()

<-ctx.Done()   // канал, который закрывается при отмене
ctx.Err()      // context.Canceled или context.DeadlineExceeded
```

- **Отмена не убивает горутину.** Горутина остановится, только если сама проверяет `ctx.Done()`
  или вызывает функции, которые принимают `ctx` (база, HTTP-клиент).
- Отмена уходит вниз по дереву: отменили родителя — отменены все производные контексты.
- **Явный `cancel()` и `defer cancel()` нужны оба.** Явный останавливает в нужный момент.
  `defer` — страховка на любой выход, включая ранний `return` по ошибке. Повторный вызов безопасен.
  Если функция ждёт тех, кого контекст должен остановить (`wg.Wait()`), одного `defer` мало:
  функция не завершится, и `defer` не сработает.
- `defer` срабатывает при выходе из **функции**, а не из итерации цикла. В цикле вызывайте `cancel()`
  в конце итерации или вынесите тело цикла в отдельную функцию.
- `context.WithValue` — для данных всего запроса (request ID, trace ID), а не для параметров функций.

**Сигнал ОС → отмена контекста:**

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
defer stop()
```

Kubernetes останавливает сервис так: присылает **SIGTERM** и ждёт (по умолчанию 30 с), потом убивает
процесс **SIGKILL**. SIGKILL перехватить нельзя. Ctrl+C в терминале — это SIGINT (`os.Interrupt`).

> **Частая ошибка:** SIGTERM слушают в одном контексте, а воркерам передают новый `context.Background()`.
> Сигнал пришёл, а воркеры о нём не знают, и сервис не останавливается.
> Все компоненты должны получать контексты, производные от того, который отменяется.

## 7. Паттерны

**Воркер с выходом по отмене или по закрытию очереди:**

```go
func worker(ctx context.Context, jobs <-chan Job) {
	for {
		select {
		case <-ctx.Done():
			return
		case job, ok := <-jobs:
			if !ok {      // без проверки ok закрытый канал даст бесконечный поток нулевых значений
				return
			}
			handle(ctx, job)
		}
	}
}
```

**Fan-out — один канал задач, несколько воркеров.** Канал сам раздаёт задачи: каждая достаётся ровно
одному воркеру. Число воркеров ограничивает нагрузку на внешний сервис.

```go
for range workers {
	go func() {
		for job := range jobs { // выйдет, когда jobs закрыт и пуст
			results <- process(job)
		}
	}()
}
```

**Fan-in — несколько каналов в один.** Горутина на каждый вход, выход закрываем после всех входов:

```go
func merge(inputs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, in := range inputs {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for v := range in {
				out <- v
			}
		}()
	}
	go func() {
		wg.Wait()  // все входы кончились
		close(out) // только теперь закрываем выход
	}()
	return out
}
```

Закрыть `out` раньше — panic при отправке. Не закрыть — читатель `range out` ждёт вечно.
Fan-in не сохраняет порядок.

**Worker pool** — fan-out с фиксированным числом воркеров, которые живут всё время работы сервиса.
Не «горутина на каждую задачу»: 100 000 задач — это 100 000 одновременных запросов во внешний сервис.

## 8. Mutex, RWMutex, atomic

**Мьютекс** — замок на общих данных. **Критическая секция** — код между `Lock()` и `Unlock()`:
в него заходит одна горутина за раз, остальные ждут.

```go
type Counter struct {
	mu    sync.Mutex
	views map[int]int // создаётся через make в конструкторе: в nil-map писать нельзя
}

func (c *Counter) Add(itemID int) {
	c.mu.Lock()
	defer c.mu.Unlock() // сразу после Lock — отпустим на любом выходе
	c.views[itemID]++
}
```

- **Гонка данных** — две горутины обращаются к одной памяти, и хотя бы одна пишет.
  `counter++` — это три шага (прочитать, прибавить, записать), часть увеличений теряется.
- **`map` не потокобезопасна.** Одновременная запись — `fatal error: concurrent map writes`, recover не поможет.
- **Проверка и изменение — под одним замком.** Так нельзя:
  `Lock; есть := count > 0; Unlock; ...; Lock; count--; Unlock` — между двумя секциями другая горутина
  успеет забрать последнее. «Проверить и взять» должно быть одной критической секцией.
- **Под замком — только работа с общими данными.** Сетевой запрос под мьютексом выстраивает
  все горутины в очередь: 10 запросов по 100 мс идут 1 с вместо 100 мс.
- Мьютекс нельзя копировать: передавайте структуру с мьютексом по указателю.
- `sync.RWMutex`: `RLock` — читателей сразу много, `Lock` — писатель один. Для кеша, где читают чаще, чем пишут.
- `sync/atomic` (`atomic.Int64`, `Add`, `Load`) — для одного счётчика. Несколько связанных полей — мьютекс.

**Что выбрать:** передаёте данные или задачи между горутинами — канал. Защищаете общее состояние — мьютекс.

## 9. Таймеры и тикеры

| Инструмент | Что делает | Когда брать |
| --- | --- | --- |
| `time.NewTimer(d)` | один сигнал в `timer.C` через `d`; есть `Stop` и `Reset` | таймаут, который надо останавливать или перезапускать |
| `time.After(d)` | тот же таймер, но на руках только канал | разовый таймаут прямо в `select` |
| `time.NewTicker(d)` | сигнал в `ticker.C` каждые `d`; есть `Stop` | периодическая работа: сканер, heartbeat |
| `context.WithTimeout` | отменяет контекст через `d` | таймаут запроса в базу или по HTTP |

```go
timer := time.NewTimer(timeout)
defer timer.Stop()

select {
case v := <-ready:
	return v, nil
case <-timer.C:
	return zero, ErrTimeout
case <-ctx.Done():
	return zero, ctx.Err()
}
```

**Периодическая работа с остановкой** — шаблон сканера:

```go
ticker := time.NewTicker(interval)
defer ticker.Stop()
for {
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-ticker.C:
		check() // синхронно: пока идёт проверка, новая не начнётся
	}
}
```

- `Stop` **не закрывает** канал `C`. После успешного `Stop` чтение `<-timer.C` ждёт вечно.
  Ждите `C` только в `select` вместе с другим сигналом.
- `for range ticker.C` без выхода — горутина работает вечно, даже после `Stop`.
- Тикер не копит тики: если обработка дольше интервала, лишние тики пропадают.
  Проверки не накладываются друг на друга и не копятся в очередь.
- `time.After` в цикле создаёт новый таймер на каждой итерации, и отсчёт начинается заново.
  Общий таймаут на весь цикл так не сделать: нужен один `NewTimer` или контекст.
- С Go 1.23 `Stop` и `Reset` надёжны: после них старое значение из `C` уже не придёт.

## 10. Graceful shutdown — корректная остановка

Правило: **новое не берём → начатое доделываем → ждём выхода горутин → закрываем ресурсы.**

```go
func main() {
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()

	jobs := make(chan Job, 100)
	var workers sync.WaitGroup
	for range 4 {
		workers.Go(func() {
			for job := range jobs { // доделывают очередь до конца
				handle(job)
			}
		})
	}

	produce(ctx, jobs) // кладёт задачи, пока ctx не отменён; вернётся после SIGTERM

	close(jobs)        // 1. новых задач не будет: единственный отправитель уже остановился
	workers.Wait()     // 2. воркеры доделали очередь
	closeDatabase()    // 3. только теперь закрываем базу и клиентов
}
```

**Ждать не бесконечно** — ограничить остановку таймаутом:

```go
done := make(chan struct{})
go func() {
	workers.Wait()
	close(done)
}()
select {
case <-done:
case <-time.After(shutdownTimeout):
	log.Println("не дождались воркеров")
}
```

- Если остановить компоненты в обратном порядке, воркеры начнут писать в закрытый канал (panic)
  или ходить в уже закрытую базу.
- Если воркеры при доделывании очереди ходят в сеть с контекстом из `signal.NotifyContext`,
  их запросы оборвутся сразу по SIGTERM. Для доделывания им нужен контекст, который отменяется
  по истечении таймаута остановки, а не по сигналу.
- Без `wg.Wait()` `main` может выйти раньше, чем горутина заметит отмену.

## 11. Типичные ошибки — сводка

| Симптом | Причина | Решение |
| --- | --- | --- |
| `fatal error: all goroutines are asleep - deadlock!` | отправка без получателя, `range` по незакрытому каналу, забытый `Done` или `Unlock` | проверить, кто читает, кто закрывает, `defer Done/Unlock` |
| `panic: send on closed channel` | канал закрыл получатель или закрыли раньше времени | закрывает только отправитель, после всех отправок |
| Бесконечные нулевые значения | читаем закрытый канал без проверки `ok` | `v, ok := <-ch` или `range` |
| Горутины копятся (утечка) | горутина ждёт канал, в который никто не напишет | закрывать каналы, давать выход по `ctx.Done()`, буфер на 1 для единственного ответа |
| Программа завершилась, работа не сделана | `main` не дождалась горутин | WaitGroup |
| Неверные числа, `concurrent map writes` | гонка данных | мьютекс или atomic; проверить `-race` |
| Ядро загружено на 100% без работы | `default` в цикле ожидания | `select` без `default` |
| Зависание на ответе | `select` без таймаута | `time.After`, `context.WithTimeout` |
| Сервис не останавливается по SIGTERM | воркерам передали другой контекст или у цикла нет выхода | один корневой контекст, `case <-ctx.Done(): return` |
| Короткие задачи ждут долгую | одна долгая задача держит воркер | таймаут на задачу или отдельная очередь |

**Важно:** рантайм ловит deadlock, только когда спят **все** горутины. В сервисе, где работает
HTTP-сервер, паники не будет: зависшие горутины просто тихо копятся.

## 12. Инструменты проверки

```sh
go test -race ./...   # детектор гонок: ловит одновременный доступ к памяти во время тестов
go vet ./...          # статические проверки: Add в горутине, неиспользованный cancel, копия мьютекса
gofmt -w .            # форматирование
```

- `-race` находит гонку только в том коде, который реально выполнился в тестах. Тесты должны
  запускать горутины одновременно.
- **goleak** проверяет, что после тестов не осталось лишних горутин:

```go
func TestMain(m *testing.M) {
	goleak.VerifyTestMain(m) // для всего пакета
}

func TestScanner(t *testing.T) {
	defer goleak.VerifyNone(t) // для одного теста
	// ...
}
```

- **Тесты без `time.Sleep`.** `Sleep` делает тесты медленными и нестабильными. Время прячут за интерфейсом,
  а в тесте подставляют управляемую реализацию:

```go
type Ticker interface {
	C() <-chan time.Time
	Stop()
}

// В тесте: тик отправляем вручную, когда нужно.
type fakeTicker struct{ ticks chan time.Time }

func (f *fakeTicker) C() <-chan time.Time { return f.ticks }
func (f *fakeTicker) Stop()               {}

// ticker.ticks <- time.Now() — «прошёл интервал»
```

  Дождаться результата помогает канал или мок, а не пауза: тест ждёт сигнал «обработано»
  в `select` с ограничением по времени.

## 13. Практика: что понадобится

| Задание | Что вспомнить | Разделы |
| --- | --- | --- |
| 1. Горутины и Mutex | горутина на элемент, `work` вне замка, запись в `map` под одним мьютексом, `Add` до `go`, `defer Done` | 3, 8 |
| 2. Fan-out и Fan-in | функции сразу возвращают каналы; у каждого воркера свой выход, он закрывает его сам; `FanIn` закрывает выход через WaitGroup | 4, 7 |
| 3. Тикер или таймер и отмена | сначала проверки из условия (интервал, уже отменённый `ctx`), один `NewTicker`/`NewTimer`, `defer Stop()`, `select` с `ctx.Done()`, `v, ok` для закрытого канала | 5, 6, 9 |

- Читайте README варианта построчно: каждая фраза в нём — это тест.
- Нельзя `time.Sleep` для синхронизации и пустой цикл с `default` в `select`.
- Проверка перед сдачей:

```sh
gofmt -w practice.go student_test.go
go test -timeout 30s ./...
go test -race -timeout 30s ./...
```

## 14. Лабораторная работа 3: на что опереться

| Требование лабы | Инструмент | Раздел |
| --- | --- | --- |
| Сканер раз в `POSITION_CHECK_INTERVAL` | `time.Ticker` + `select` с `ctx.Done()` | 9 |
| Тики не накладываются | обработка тика синхронно в одной горутине | 9 |
