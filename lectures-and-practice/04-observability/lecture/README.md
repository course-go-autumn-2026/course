# Наблюдаемость Go-сервисов с OpenTelemetry

Лекция на 90 минут для курса «Разработка микросервисов на Go». После неё предусмотрены 90 минут практики. Нужны основы Go, HTTP и `context.Context`; окружение поднимаем до занятия.

Наш пример: сервис заказов резервирует курьера через HTTP. Сначала разбираем логи и трейсы одного запроса, затем измеряем поток, ошибки и задержки, переходим к алертам и целям качества. В конце собираем общий путь телеметрии.

Фрагменты Go показывают отдельные части [готового примера](../example/README.md), а не один файл для последовательного копирования. Импорты, обработку ошибок и полный порядок запуска смотрим в исходниках. Учебные упрощения отмечены отдельно. На практике запускаем уже инструментированные сервисы и расследуем неисправности; настройка алертинга не входит в обязательное задание.

## 1. Пользовательская проблема

Пользователь оформляет заказ. Процессы запущены, порты открыты, но ответ приходит через две секунды с ошибкой. Проверка «контейнер работает» не объясняет, что получил пользователь и где произошёл сбой.

```text
Клиент → POST /orders → order-service → POST /reserve → courier-service
```

`POST /orders` без параметров оформляет фиксированный учебный заказ. Успех означает, что курьер подтвердил резервирование; сервис заказов отвечает `201`. Ошибка или тайм-аут зависимости дают `503`. Мы не реализуем базу данных, оплату и кухню. Успех этого API не обещает долговременное хранение заказа или физическую доставку еды.

**Мониторинг**: регулярный сбор и анализ данных о запросах, ошибках, задержках и ресурсах. Он помогает заметить известные отклонения.

**Наблюдаемость**: возможность судить о внутреннем состоянии системы по её внешним данным, в том числе исследовать заранее неизвестную проблему. Установленного инструмента недостаточно: если важная операция нигде не отражена, её подробности не восстановить.

Начнём с отдельного запроса и событий внутри него. Затем перейдём к метрикам: насколько проблема массовая и как она меняется во времени.

## 2. Один заказ: логи и трейсы

### Один заказ, три сигнала

Метрика показывает масштаб отклонения, трейс показывает путь одного запроса, лог хранит подробности события. Например, по графику видим ошибки оформления заказа, по трейсу находим ожидание курьеров, по логу уточняем отказ или отмену.

Это не обязательный порядок расследования: начать можно и с конкретного Trace ID или сообщения об ошибке.

### Структурированное событие

Лог хранит подробности события: какую операцию выполняли, с каким результатом она закончилась и что помогло бы понять отказ. Структурированные поля позволяют искать записи без разбора произвольного текста.

Упрощённое представление записи, **не буквальный формат stdout-exporter**:

```json
{
  "service.name": "order-service",
  "body": "order completed",
  "outcome": "error",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7"
}
```

### Поиск логов одного сервиса

В Grafana → Explore → Loki доступны запросы:

```logql
{service_name="order-service"} |= "order completed"
{service_name="order-service"} | outcome="error"
{service_name=~"order-service|courier-service"} | trace_id="ВСТАВЬТЕ_TRACE_ID"
```

Одинаковое время двух событий не доказывает принадлежность одному запросу. Trace ID связывает запрос между сервисами, Span ID сопоставляет запись с конкретной операцией.

### Трейс и спаны

Трейс состоит из связанных операций. Спан описывает отдельную операцию: у него есть Trace ID, Span ID, время начала и окончания, ссылка на родителя, если он есть, атрибуты, события и статус.

```text
POST /orders                  order-service, серверный спан
└─ orders.create              ручной спан бизнес-операции
   └─ HTTP POST               клиентский спан
      └─ POST /reserve        courier-service, серверный спан
```

Trace ID общий для всего пути, Span ID различает операции. Долгий клиентский спан покажет ожидание зависимости; по её серверному спану уточняем длительность обработки.

Длительности нельзя просто сложить: дочерние операции входят во время родительских, часть работы может идти параллельно. Трейс показывает, где потрачено время; причину задержки иногда приходится уточнять логами или метриками зависимости.

### Проверка трейса

В Grafana → Explore → Jaeger ищем запрос `order-service`. В одном трейсе должны быть обе службы. Если появились два трейса, проверяем текущий контекст, propagator и HTTP-инструментирование; если частей нет, проверяем ещё экспорт и сэмплирование.

### Контекст запроса и экспорт

```text
order-service ── HTTP + traceparent ──→ courier-service
       │                                     │
       └──────────── OTLP ──→ Collector ←────┘
```

`traceparent` передаётся вместе с рабочим HTTP-запросом между сервисами. OTLP отдельно доставляет спаны в Collector. Collector не передаёт бизнес-запросы и не восстанавливает потерянное родительство по похожим сообщениям.

## 3. OpenTelemetry и трейсы на Go

### От кода к экспорту

Для инструментирования используем **OpenTelemetry, или OTel**: спецификации, API, SDK и компоненты для создания и передачи телеметрии. Это не хранилище и не интерфейс дашбордов. Подробную схему доставки разберём в конце; пока Collector считаем получателем данных приложения.

| Компонент | Задача |
| --- | --- |
| API | Начать спан, записать измерение или событие |
| SDK | Обработать, агрегировать, сэмплировать и экспортировать данные |
| Provider | Дать приложению настроенный Tracer, Meter или Logger |
| Resource | Описать источник: сервис, экземпляр, версию |
| Instrumentation scope | Описать библиотеку инструментирования |
| Exporter | Передать данные приёмнику или вывести в stdout |
| OTLP | Передать трейсы, метрики и логи по общему протоколу |
| Collector | Принять, обработать и отправить телеметрию |
| Бэкенд | Хранить данные и выполнять запросы |
| Grafana | Запрашивать и показывать данные; для Grafana-managed alerting вычислять правила |

Общие API позволяют библиотеке создавать телеметрию, не выбирая хранилище за приложение. В каждом процессе один раз вызывается `telemetry.Setup`, который настраивает три provider и возвращает логгер и функцию завершения. HTTP-сервером этот пакет не управляет.

### Стандартные атрибуты и наши бизнес-имена

**Semantic conventions** задают согласованные имена и смысл полей, например `service.name`, `service.namespace`, `http.request.method`, `http.route`, `http.response.status_code`. Пакет `semconv` привязан к версии соглашений; в [telemetry.go](../example/telemetry/telemetry.go) используется `go.opentelemetry.io/otel/semconv/v1.43.0`.

Фрагмент `telemetry.Setup`: `ctx` здесь относится к инициализации, `defaultName` приходит из точки входа сервиса, `shutdown` освобождает уже созданные ресурсы:

```go
res, err := resource.New(ctx,
    resource.WithAttributes(semconv.ServiceName(defaultName)),
    resource.WithFromEnv(),
    resource.WithTelemetrySDK(),
    resource.WithAttributes(semconv.ServiceInstanceID(rand.Text())),
)
if err != nil {
    return nil, shutdown, err
}
```

**Resource** описывает источник данных: сервис, экземпляр, версию. `WithFromEnv` позволяет задать имя и другие атрибуты через `OTEL_*`; в окружении курса namespace равен `tripgo`, имена процессов различаются: `order-service` и `courier-service`. На слайде 11 показан упрощённый Resource с явно заданными именем и namespace; полный пример учитывает окружение и идентификатор экземпляра.

**Instrumentation scope** описывает библиотеку или часть кода, создавшую телеметрию. В нашем коде это `example.com/food-observability`. Scope и имя сервиса не взаимозаменяемы.

`orders.attempts`, `orders.duration` и атрибут `outcome=success|error` задаём сами по смыслу операции. Semantic conventions не придумывают бизнес-метрики за нас. Источник: [семантические соглашения OTel](https://opentelemetry.io/docs/concepts/semantic-conventions/).

### SDK при запуске

Фрагмент [telemetry.Setup](../example/telemetry/telemetry.go), где `ctx` относится к инициализации, `res` уже создан:

```go
traceExporter, err := otlptracehttp.New(ctx, otlptracehttp.WithTimeout(2*time.Second))
if err != nil {
    return nil, shutdown, err
}
tp := sdktrace.NewTracerProvider(
    sdktrace.WithResource(res),
    sdktrace.WithBatcher(traceExporter, sdktrace.WithBatchTimeout(time.Second)),
)
```

После успешной настройки всех provider приложение подключает `tp` через `otel.SetTracerProvider(tp)`. Batch processor принимает законченные спаны и передаёт их exporter пакетами. `span.End()` завершает спан, но не обещает немедленную сетевую отправку.

### HTTP-инструментирование и propagation

При запуске задаём propagator:

```go
otel.SetTextMapPropagator(propagation.TraceContext{})
```

В [orders.go](../example/orders/orders.go) инструментируем используемый клиент и конкретный маршрут:

```go
client.Transport = otelhttp.NewTransport(client.Transport)
```

```go
mux.Handle("POST /orders", otelhttp.NewHandler(create, "POST /orders"))
```

Входящая обёртка извлекает W3C Trace Context и создаёт серверный спан. Исходящий транспорт создаёт клиентский спан и добавляет заголовки контекста в запрос. Нужны обе стороны; серверная обёртка не инструментирует произвольный исходящий клиент.

`reserveCourier` использует `http.NewRequestWithContext`, передавая полученный `ctx`, и выполняет запрос этим клиентом. Затем читает и закрывает тело ответа: это нужно для завершения клиентского спана и повторного использования соединения. Тайм-аут клиента заказов составляет две секунды.

### Ручной спан и ошибка

Теперь выделим бизнес-операцию. `tracer` создаётся один раз через `otel.Tracer(scope)`:

```go
ctx, span := tracer.Start(r.Context(), "orders.create")
defer span.End()

err := reserveCourier(ctx, courierURL, client)
outcome := "success"
if err != nil {
    outcome = "error"
    span.RecordError(err)
    span.SetStatus(codes.Error, "courier reservation failed")
}

result := attribute.String("outcome", outcome)
span.SetAttributes(result)
```

`Start` возвращает **новый контекст** с текущим спаном. Его передаём зависимости, метрикам и логам. Подмена на `context.Background()` в середине запроса разорвёт родительскую связь и передачу отмены.

`RecordError` записывает сведения об ошибке как событие. `SetStatus` отдельно отмечает ошибочный результат спана; одно не заменяет другое. Текст ошибки тоже может содержать секреты, поэтому нельзя без проверки записывать произвольные ответы зависимости.

Начинаем с входящих запросов, зависимостей и значимых бизнес-операций. Спан на каждую маленькую функцию обычно добавляет объём, а не полезную диагностику. [Инструментирование Go](https://opentelemetry.io/docs/languages/go/instrumentation/), [пакет `otelhttp`](https://pkg.go.dev/go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp).

## 4. Логи на Go

### slog, мост и два пути экспорта

Используем стандартный `log/slog`, направляя записи через `otelslog` в OTel Logs SDK. Фактическая схема нашего примера:

```text
logger.InfoContext(ctx, ...) → otelslog → LoggerProvider
                                          ├─ BatchProcessor → OTLP/HTTP → Collector → Loki
                                          └─ BatchProcessor → stdout-exporter → терминал
```

Сетевой экспорт нужен для поиска логов в Grafana, stdout оставлен для локальной диагностики. Collector не читает stdout Go-процессов на хосте.

На дату сверки, 03.10.2026, документация обозначает traces и metrics Go как Stable, Go Logs API и SDK как Release Candidate. Статусы экспортёров и мостов проверяют отдельно; RC не означает стабильность всех компонентов цепочки. Версии модулей закреплены в [go.mod](../example/go.mod), не обновляем их на занятии наугад. Источники: [OpenTelemetry Go](https://opentelemetry.io/docs/languages/go/), [объявление Go Logs RC](https://opentelemetry.io/blog/2026/go-logs-api-sdk-rc/).

### Настройка и запись

Фрагмент [telemetry.go](../example/telemetry/telemetry.go). Два готовых exporter подключаются к одному provider:

```go
consoleExporter, err := stdoutlog.New()
if err != nil {
    return nil, shutdown, err
}
logExporter, err := otlploghttp.New(ctx, otlploghttp.WithTimeout(2*time.Second))
if err != nil {
    return nil, shutdown, errors.Join(err, consoleExporter.Shutdown(ctx))
}
lp := sdklog.NewLoggerProvider(
    sdklog.WithResource(res),
    sdklog.WithProcessor(sdklog.NewBatchProcessor(consoleExporter)),
    sdklog.WithProcessor(sdklog.NewBatchProcessor(logExporter)),
)
closers = append(closers, lp.Shutdown)
logger := otelslog.NewLogger(scope, otelslog.WithLoggerProvider(lp))
```

В обработчике, пока текущий бизнес-спан находится в `ctx`:

```go
logger.InfoContext(ctx, "order completed", "outcome", outcome)
```

Мост извлекает Trace ID и Span ID из контекста. Exporters получают OTel-запись с этими идентификаторами, телом события, атрибутами и Resource. Для OTLP используется тот же адрес Collector из `.env`, что и для трейсов и метрик.

Один `InfoContext` не добавляет Trace ID, если handler не умеет его извлечь. Стартовый лог вне спана не связан с трейсом; это не ошибка корреляции запроса. [Документация `otelslog`](https://pkg.go.dev/go.opentelemetry.io/contrib/bridges/otelslog).

### Переход из лога в трейс

У записи `order completed` действие **TraceID → View trace** открывает трейс через источник Jaeger внутри Grafana. Span ID записи должен совпасть со спаном `orders.create`. Автоматический обратный переход из трейса в логи не настроен: используем поиск по Trace ID.

Идентификаторы и атрибуты события хранятся в Loki как structured metadata; `| json` для [этих запросов](#поиск-логов-одного-сервиса) не требуется. Не переносим Trace ID и другие неограниченные идентификаторы в индексные labels Loki.

Вывод в stdout проверяет локальный экспорт, но не доставку в Loki. Логи и спаны отправляются независимо, поэтому ссылка может начать работать после пакетного экспорта обоих сигналов. Jaeger хранит трейсы в памяти, Loki сохраняет логи на PVC; после перезапуска Jaeger старый лог может остаться без доступного трейса.

### Уровни логов

- `DEBUG`: подробности диагностики; объём обычно велик.
- `INFO`: штатные значимые события и учёт результата операции.
- `WARN`: отклонение, на которое стоит обратить внимание.
- `ERROR`: неуспешная операция, требующая диагностики.

В нашем примере `order completed` всегда пишется как итоговое `INFO`-событие с `outcome`. При искусственном отказе сервис курьеров пишет `ERROR`; ошибка вызова также видна в спане заказов. Поэтому неуспехи ищем по `outcome=error`, а не только по уровню логов.

## 5. Метрики и RED

### RED: общая картина

Метрики показывают общую картину во времени, обычно без подробностей каждого события. Для сервисов начинаем с **RED**:

| Показатель | Что смотрим у заказов |
| --- | --- |
| Rate | Завершённые попытки в секунду |
| Errors | Доля неуспешных попыток |
| Duration | Длительность операции в секундах |

Для Errors можно использовать панель успешности, если явно читать её как `100% − успешность`. Все панели сравниваем за один диапазон времени, с видимыми единицами и легендой. CPU и память дополняют картину, но сами по себе не доказывают успех оформления заказа.

### Граница измерения

Для нашего примера фиксируем:

- **Операция:** оформление заказа через `POST /orders`.
- **Хороший результат:** резервирование подтверждено, сервис принимает заказ и выбирает ответ `201`.
- **Знаменатель:** все завершённые попытки, дошедшие до обработчика `POST /orders`, включая неуспешные.
- **Неуспех:** ошибка или тайм-аут при резервировании; сервис выбирает ответ `503`.
- **Исключения:** health checks, другие методы и маршруты, управление учебными неисправностями.
- **Точка измерения:** код операции в сервисе заказов, перед отправкой HTTP-ответа.

В модели нет валидации состава заказа. В настоящем API нужно отдельно решить, какие некорректные запросы исключать. Отказ допустимой операции из-за перегрузки нельзя спрятать за формулировкой «ошибка пользователя» только потому, что вернулся `4xx`.

HTTP-код свидетельствует о результате, но не определяет его. Если операция обещает сохранение заказа, один `200` без записи в БД успехом не будет. Наш пример такого обещания не даёт.

Серверное измерение не видит запросы, не дошедшие до обработчика, и операции, которые процесс не успел учесть перед аварийным завершением. Не подтверждает оно и получение ответа клиентом. Для всего пользовательского пути могут понадобиться метрики шлюза, клиентские измерения и внешние проверки.

### Counter, Gauge, Histogram

| Инструмент | Что измеряет | Пример |
| --- | --- | --- |
| Counter | Неотрицательные прибавления к счётчику | Завершённые попытки оформления заказа |
| Gauge | Текущее значение, способное расти и падать | Длина очереди или занятая память |
| Histogram | Распределение записанных значений | Длительность операции |

Сброс счётчика после перезапуска допустим; запросы к нему должны это учитывать. Гистограмма группирует длительности по интервалам, бакетам, и хранит агрегаты вместо каждого отдельного измерения. По ним можно оценить долю быстрых операций и хвост задержек.

### Среднее и хвост задержек

Условные 100 запросов, не измерения нашего стенда:

| Количество | Длительность, с |
| --- | --- |
| 60 | 0,1 |
| 25 | 0,2 |
| 10 | 0,4 |
| 4 | 1,2 |
| 1 | 2,0 |

Среднее равно `0,218 с`. Если отсортировать эти 100 значений и брать квантиль по ближайшему рангу вверх, 95-е значение даёт **p95 = 0,4 с**, 99-е даёт **p99 = 1,2 с**. Среднее скрывает различие между большинством быстрых ответов и медленным хвостом.

В этом примере известны все длительности. Реальный `histogram_quantile` работает с агрегатами и оценивает квантиль внутри бакета. Точность зависит от границ; p99 не означает, что самый медленный запрос длился ровно столько.

## 6. Метрики на Go

### SDK и экспорт

SDK настраиваем один раз при запуске процесса. Фрагмент [telemetry.Setup](../example/telemetry/telemetry.go), где `res` уже создан:

```go
metricExporter, err := otlpmetrichttp.New(ctx, otlpmetrichttp.WithTimeout(2*time.Second))
if err != nil {
    return nil, shutdown, err
}
mp := sdkmetric.NewMeterProvider(
    sdkmetric.WithResource(res),
    sdkmetric.WithReader(sdkmetric.NewPeriodicReader(metricExporter)),
)
```

После успешной настройки всех provider приложение подключает `mp` через `otel.SetMeterProvider(mp)`. `PeriodicReader` собирает агрегированные метрики и экспортирует их по OTLP/HTTP. API без настроенного SDK и exporter не гарантирует появление данных.

В окружении курса `OTEL_METRIC_EXPORT_INTERVAL=5000`, значение в миллисекундах. SDK не читает файл `.env` сам: его загружает команда запуска из инструкции примера.

### Counter и Histogram

В [orders.go](../example/orders/orders.go) создаём инструменты один раз при сборке обработчика. `scope` содержит имя библиотеки инструментирования:

```go
meter := otel.Meter(scope)
attempts, err := meter.Int64Counter("orders.attempts")
if err != nil {
    return nil, err
}
duration, err := meter.Float64Histogram("orders.duration", metric.WithUnit("s"),
    metric.WithExplicitBucketBoundaries(0.05, 0.1, 0.3, 0.8, 1, 2, 5))
if err != nil {
    return nil, err
}
for _, outcome := range []string{"success", "error"} {
    attempts.Add(context.Background(), 0, metric.WithAttributes(attribute.String("outcome", outcome)))
}
```

Нулевые прибавления создают оба ожидаемых набора атрибутов счётчика до первого события. Они не добавляют попыток. В гистограмму фиктивные нулевые наблюдения не записываем: они исказят распределение.

### Одна завершённая попытка

Для объяснения измерений временно опустим ручной спан и запись HTTP-ответа. `r`, `client` и `courierURL` принадлежат обработчику; полный вариант находится в `orders.go`:

```go
started := time.Now()
ctx := r.Context()
err := reserveCourier(ctx, courierURL, client)
outcome := "success"
if err != nil {
    outcome = "error"
}
attrs := metric.WithAttributes(attribute.String("outcome", outcome))
attempts.Add(ctx, 1, attrs)
duration.Record(ctx, time.Since(started).Seconds(), attrs)
```

Каждая завершённая попытка учитывается один раз, включая ошибки и тайм-ауты зависимости. Измеряем время операции в обработчике, до отправки HTTP-ответа, а не путь от клиента до сервера и обратно. Health checks и другие маршруты в эти инструменты ничего не записывают.

`outcome` описывает результат бизнес-операции и не требует уже созданного спана. Те же сведения передаём в трейс и лог, а измерениям передаём контекст текущего бизнес-спана.

`Add` и `Record` работают с локальной агрегацией SDK, не выполняя HTTP-запрос на каждую попытку. В примере экспорт накопительный, cumulative: счётчик содержит итог с начала периода накопления, а не число событий за последние пять секунд. Delta-экспорт передаёт прирост за интервал; незаметно подставлять его в тот же путь данных и запросы нельзя.

### Метки и кардинальность

После экспорта атрибут `outcome` становится меткой временного ряда. Каждый уникальный набор имени метрики и меток создаёт отдельный ряд. Два результата и четыре экземпляра сервиса дают до восьми рядов счётчика. Классическая гистограмма дополнительно создаёт ряды бакетов, суммы и количества.

Используем ограниченные значения: результат, метод, шаблон маршрута. Trace ID, `order_id`, пользовательский идентификатор или произвольный URL растят число рядов вместе с трафиком. Resource attributes тоже могут стать метками: OTel не устраняет проблему кардинальности автоматически.

### Поля событий и метрик

Не повторяем одну ошибку на каждом уровне вызовов без новых сведений. Не записываем пароли, токены, адрес доставки и полные тела запросов «на всякий случай». Если нужен `order_id`, его можно включить в лог или спан с учётом доступа и хранения. В метриках используем ограниченные значения вроде `outcome`, метода и шаблона маршрута, а не идентификаторы запросов.

### Накопительные бакеты и общий p99

В SDK выбраны явные границы в секундах: `0.05, 0.1, 0.3, 0.8, 1, 2, 5`. В OTLP explicit histogram передаются количества по интервалам; после преобразования в классический формат Prometheus видим **накопительные** бакеты `le`.

Если операция заняла `0.42` секунды:

| Ряд в Prometheus | Изменение |
| --- | --- |
| `_bucket{le="0.3"}` и меньшие границы | Без изменений |
| `_bucket{le="0.8"}` и большие границы, включая `+Inf` | `+1` в каждом |
| `_count` | `+1` |
| `_sum` | `+0.42` |

`le` означает «меньше или равно». Прибавление в нескольких накопительных бакетах не означает несколько операций.

Граница `0.8` позволяет посчитать долю наблюдений не дольше 800 мс без интерполяции внутри бакета. Это точность классификации по порогу, а не обещание точного числа событий из `rate` за любое окно.

Для общего p99 сначала объединяем совместимые распределения, затем вычисляем квантиль. Среднее от p99 двух экземпляров не даёт общего p99. Отдельные значения внутри бакета неизвестны, поэтому квантиль остаётся оценкой. [Гистограммы и перцентили](https://prometheus.io/docs/practices/histograms/).

## 7. PromQL и Grafana

### Имена в приложении и в хранилище

В нашем стенде после Collector и scrape:

| OTel-инструмент | Ряды Prometheus |
| --- | --- |
| `orders.attempts` | `orders_attempts_total` |
| `orders.duration`, единица `s` | `orders_duration_seconds_bucket`, `_count`, `_sum` |

Scrape задаёт `job="otel-collector"`. Приложение выбираем через `exported_job="tripgo/order-service"`. Это метки конкретного стенда, не универсальный результат любого OTLP-приёма. При смене приёмника сначала изучаем реальные имена, единицы и метки.

### Поток попыток

PromQL выбирает временные ряды, вычисляет скорости, доли и агрегаты. Окно `[5m]` означает последние пять минут на каждом шаге графика, а не весь выбранный в Grafana диапазон.

```promql
sum(rate(orders_attempts_total{job="otel-collector",exported_job="tripgo/order-service"}[5m]))
```

`rate` оценивает прирост счётчика **в секунду**, `sum` объединяет ряды. Результат `2` означает две завершённые попытки в секунду, а не две попытки за пять минут. Для оценки числа событий за окно есть `increase`; его результат в PromQL может быть дробным из-за экстраполяции к границам окна.

Обе функции учитывают обнаруженные сбросы счётчика. Сначала вычисляем изменение каждого ряда, потом складываем: `sum(rate(...))`. Иначе сброс одного экземпляра может скрыться в сумме. Для `rate` нужны хотя бы две точки.

### Доля успешных попыток

```promql
100 * sum(rate(orders_attempts_total{job="otel-collector",exported_job="tripgo/order-service",outcome="success"}[5m]))
/ (sum(rate(orders_attempts_total{job="otel-collector",exported_job="tripgo/order-service"}[5m])) > 0)
```

Знаменатель содержит **все результаты**, не только успешные. Сравнение `> 0` без `bool` отфильтровывает нулевой знаменатель, сохраняя его значение при наличии трафика. Нет попыток — доля не определена, не показываем 100%. Только ошибки — заранее созданный нулевой счётчик успехов даёт 0%.

### Перцентили

p99 длительности всех учтённых попыток:

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(orders_duration_seconds_bucket{job="otel-collector",exported_job="tripgo/order-service"}[5m])
  )
)
```

`sum by (le)` сохраняет границы бакетов и объединяет экземпляры и оба результата. Для p95 меняем `0.99` на `0.95`; результат выражен в секундах.

### Быстрый успех

Числитель: успешные попытки не дольше 800 мс. Знаменатель: **все** попытки. Быстрая ошибка не должна улучшать этот показатель.

На слайде 37 показаны компоненты расчёта. Полное выражение с обработкой отсутствующего успешного ряда:

```promql
100 * (
  sum(rate(orders_duration_seconds_bucket{job="otel-collector",exported_job="tripgo/order-service",outcome="success",le="0.8"}[5m]))
  or (0 * sum(rate(orders_duration_seconds_count{job="otel-collector",exported_job="tripgo/order-service"}[5m])))
)
/ (sum(rate(orders_duration_seconds_count{job="otel-collector",exported_job="tripgo/order-service"}[5m])) > 0)
```

`or (0 * ...)` нужен, когда успешного ряда гистограммы ещё нет, но ошибки уже есть. Получаем 0%, а не пустой результат. Если нет и знаменателя, выражение не выдумывает данные. Записывать фиктивную нулевую длительность для создания ряда нельзя: она станет ложным быстрым успехом.

Эталонные выражения, включая p95, находятся в [queries.json](../example/queries.json). Сначала читаем числитель и знаменатель словами, затем разбираем синтаксис.

### Четыре панели

[Готовый дашборд](../example/dashboard.json) использует источник Prometheus и показывает:

1. Завершённые попытки в секунду.
2. Успешность, проценты.
3. p95 и p99 длительности, секунды.
4. Успешные попытки не дольше 800 мс, проценты от всех попыток.

Указываем окно и единицы. Формулы долей выше уже умножены на 100, поэтому для них подходит шкала Percent (0–100), не Percent (0.0–1.0). Линии 99,9% и 99% служат учебными целями за пять минут. Позже отличим их от целей за 30 дней: короткий прогон не подтверждает месячный SLO.

Генератор отправляет параллельные запросы до остановки. Сейчас темп по умолчанию составляет 5 RPS; практика задаёт 100 RPS явно через `RPS=100`. `actual_rps` в его логах считает начатые попытки за интервал между сводками; наша панель считает завершённые операции с пятиминутным окном. Значения не обязаны совпадать, особенно при старте, остановке и изменении задержки. Медленный ответ увеличивает число активных запросов, а не вынуждает последовательный генератор ждать. Это не бенчмарк предельной производительности.

Сравниваем нормальную работу, задержку и ошибку за один диапазон времени. Быстрые отказы могут снизить p95, одновременно ухудшив успешность. При отсутствии трафика скорость может быть нулевой, а доли оставаться без данных. Старые ошибки ещё входят в пятиминутное окно после восстановления.

Четыре панели не различают все причины отсутствия новых событий. Collector может продолжать отдавать прежние значения после остановки приложения. Нулевой `rate` и успешный scrape не доказывают ни отсутствие спроса, ни свежесть телеметрии: отдельно проверяем приложение и доставку данных.

## 9. Grafana Alerting

График помогает человеку увидеть проблему. Алерт нужен, когда при заданном условии кто-то должен действовать, даже если дашборд никто не открыл. Здесь рассматриваем **Grafana-managed alert rule**, которое вычисляется на сервере Grafana по расписанию.

### От запроса к уведомлению

Учебный пример со слайда 42:

```text
Доля ошибок за 5 минут = 100% − успешность
    → Reduce: последнее значение, если запрос вернул временной ряд
    → условие: больше 5%
    → оценка каждые 30 секунд, pending period 2 минуты
    → Alerting
    → notification policy по labels
    → contact point
```

Запрос, преобразование результата и условие определяют состояние алерта. Для каждого набора меток результата может существовать отдельный **alert instance**. Наш запрос с общей суммой по сервису даёт один агрегированный результат; разбивка по экземплярам дала бы несколько независимых состояний.

`Reduce` сводит временной ряд к числу для проверки условия; если запрос уже возвращает подходящее мгновенное значение, отдельный шаг может не потребоваться. Затем notification policy выбирает маршрут по меткам, а contact point задаёт получателя или интеграцию доставки.

Порог 5%, интервал 30 секунд и pending 2 минуты выбраны для объяснения механики. Это не производственная рекомендация и не правило, уже настроенное в стенде.

### Короткий всплеск и устойчивое нарушение

Упрощённая схема, без `keep firing for`:

| Наблюдение на очередной оценке | Состояние |
| --- | --- |
| Условие не выполняется | Normal |
| Нарушение обнаружено впервые | Pending, начинается отсчёт |
| Условие перестало выполняться до истечения двух минут | Возврат в Normal |
| Условие продолжает выполняться на оценках и подтверждено после pending period | Alerting, или firing |

Pending отсчитывается от первой оценки, обнаружившей нарушение, а не от неизвестного нам момента начала инцидента. Интервал оценки, pending period и задержка доставки уведомления — разные вещи. Группировка уведомлений и работа канала доставки могут отложить сообщение после перехода в Alerting.

**No Data** означает отсутствие пригодных данных результата, **Error** — ошибку или тайм-аут вычисления. Для них выбирают отдельное поведение правила. Не приравниваем пустой результат к здоровью сервиса: он может быть следствием отсутствия трафика, недоступного источника или потери телеметрии. В частности, наши запросы долей намеренно не возвращают значение при нулевом знаменателе.

Источник: [оценка правил и состояния Grafana Alerting](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/).

### Уведомление, с которым можно действовать

Макет с условными значениями, не результат измерения стенда:

```text
FIRING · order-service
Ошибки оформления заказа: 8,2%
Условие: больше 5%, нарушение держится 2 минуты
Ссылки на нужную панель и runbook с первыми действиями
```

В сообщении нужны сервис, проблема, измеренное значение, условие, время или длительность, ссылка на конкретный dashboard/panel и инструкция первых действий.

- **Labels**, например `service`, `team`, `severity`, помогают идентифицировать и маршрутизировать алерт.
- **Annotations** описывают проблему и действия, содержат ссылки и подробности.
- Группировка, mute timings и silences управляют шумом уведомлений. Они не устраняют причину нарушения.

Источники: [notification policies](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/notification-policies/), [уведомления Grafana](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/). На практике этой лекции правила и contact points не настраиваем.

## 10. SLI, SLO, SLA и бюджет ошибок

Мы уже умеем считать попытки, различать результаты и измерять длительность. Теперь договоримся, какую долю успешных попыток считать достаточной и за какой период оценивать качество. «Сервис работает хорошо» без правила расчёта и цели проверить нельзя.

### Три понятия

| Термин | Значение | Учебный пример |
| --- | --- | --- |
| SLI — Service Level Indicator | Измеряемый показатель качества с правилами расчёта | Доля успешных допустимых попыток оформления заказа |
| SLO — Service Level Objective | Целевое значение SLI за установленный период | Не менее 99,9% за последние 30 дней |
| SLA — Service Level Agreement | Соглашение с потребителем: обязательства, измерение и последствия нарушения | Согласованная компенсация при невыполнении условий сервиса |

SLI отвечает на вопрос «что измеряем», SLO — «какого значения хотим», SLA — «что обещали потребителю и что произойдёт при нарушении». У SLI есть определение и измеренное значение: формула доли успешных попыток и полученные 99,7% не одно и то же.

Внутренний SLO полезен и без SLA. Нарушение внутренней цели не означает автоматически нарушение договора: в нём могут быть другое окно, исключения и способ измерения. [Определения в книге Google SRE](https://sre.google/sre-book/service-level-objectives/).

### Два SLI и две цели

```text
SLI успешности = успешные допустимые попытки / все допустимые попытки
SLO: не менее 99,9% за последние 30 дней

SLI успешного быстрого завершения =
    допустимые попытки, завершённые успешно за ≤ 800 мс
    / все допустимые попытки
SLO: не менее 99% за последние 30 дней
```

Вторая цель включает успех: быстрая ошибка не улучшает этот SLI. Знаменатель в обоих случаях относится к одной группе попыток. Длительность измеряется в обработчике, не на стороне клиента.

Значения учебные, не производственные обязательства. Реальные цели выбирают по потребностям пользователей, измерениям и стоимости улучшений. Панель p99 полезна для диагностики, но не заменяет долю успешных быстрых событий. Пятиминутные панели практики используют отдельное короткое окно и не подтверждают выполнение месячного SLO.

### Бюджет ошибок и burn rate

Бюджет ошибок задаёт допустимую долю плохих событий для выбранного SLO и его окна:

```text
Допустимая доля неуспеха = 1 − 0,999 = 0,001 = 0,1%
100 000 допустимых попыток → бюджет 100 неуспешных попыток
60 неуспешных попыток → израсходовано 60% бюджета, осталось 40%
```

У каждой цели свой бюджет. Для быстрого успеха плохими будут и ошибки, и успешные операции дольше 800 мс.

Бюджет на основе запросов нельзя автоматически перевести в минуты простоя: при разной нагрузке один и тот же интервал сбоя затронет разное число попыток. В скользящем окне «последние 30 дней» бюджет пересчитывается вместе с окном, а не обнуляется первого числа.

**Burn rate** показывает, во сколько раз наблюдаемая доля плохих событий больше допустимой:

```text
Текущая доля ошибок 1% / допустимые 0,1% = burn rate 10
```

Он помогает реагировать до исчерпания бюджета, но не задаёт точное время до исчерпания без предположений о дальнейшем трафике и ошибках.

Команда заранее договаривается, что делать при быстром расходовании бюджета: сократить рискованные изменения, устранить причины отказов, проверить восстановление. Это не запрет на исправления безопасности или надёжности. [Политика бюджета ошибок](https://sre.google/workbook/error-budget-policy/).

### Алерт по двум окнам

Пример со слайда 49 для SLO успешности 99,9% за 30 дней:

```text
burn rate за окно = доля плохих событий в окне / (1 − SLO)

burn rate за 1 час > 14,4
И
burn rate за 5 минут > 14,4
→ алерт
```

Оба окна используют одно определение плохого события и допустимой доли. Длинное окно подтверждает значимый расход бюджета, короткое проверяет, что нарушение ещё активно. Должны выполняться **оба** условия, а не любое одно.

При SLO 99,9% burn rate 14,4 соответствует 1,44% плохих событий. При сопоставимом потоке событий за час это около 2% бюджета 30-дневного окна: `14,4 × 1 / (30 × 24) = 0,02`. Для непостоянного трафика доля израсходованного бюджета зависит от числа событий, поэтому перевод по времени требует этой оговорки.

Это **не то же самое, что pending period**. Pending требует удержания условия на последовательных оценках, а два окна оценивают доли ошибок за разные периоды. Порог ошибок 5% из блока Grafana Alerting объяснял механику правила; он не заменяет этот SLO-ориентированный расчёт.

Порог и окна выбирают под скорость реакции и характер трафика. Пример не добавляет готовое правило в стенд. [Алерты по SLO и расходу бюджета](https://sre.google/workbook/alerting-on-slos/).

## 11. OpenTelemetry: компоненты и доставка

### Общая схема

Мы использовали OTel для трёх сигналов. Теперь отделим инструментирование от доставки, хранения и просмотра:

```text
Прикладной код → OTel API → SDK → exporter → Collector → бэкенд ← Grafana
```

Смена бэкенда обычно не требует переписывать `tracer.Start` или `counter.Add`. Но имена рядов после преобразования, запросы, дашборды, алерты и поддержка типов данных могут различаться. Общий протокол не гарантирует перенос всего решения без проверки.

### Push и pull

**Для сервисов курса предпочитаем OTLP push в Collector.** SDK или агент инициирует отправку в известный приёмник. Приложению достаточно адреса Collector, маршрутизация по хранилищам вынесена из бизнес-кода.

При **pull** сборщик по расписанию запрашивает метрики у известных или обнаруженных целей, обычно на `/metrics`. Это исторически основной способ сбора в экосистеме Prometheus, полезный для долгоживущих доступных по сети целей и инфраструктурных exporters.

| Вопрос | Push | Pull |
| --- | --- | --- |
| Кто начинает соединение? | SDK или агент | Сборщик |
| Кто задаёт интервал? | Reader/exporter или агент | Настройка scrape |
| Что нужно знать? | Адрес приёмника | Адреса целей или service discovery |
| Что видно при сбое? | Ошибки экспорта, заполнение очереди, отсутствие новых данных | Неуспешный scrape; для известной цели `up=0` |

Push не означает сетевой запрос на каждый `Add`: SDK агрегирует измерения и экспортирует их по расписанию. Очереди имеют предел, при длительном сбое возможны потери. Pull тоже не восстановит события, потерянные процессом до опроса. Для короткого процесса push может передать итог при корректном shutdown, тогда как процесс способен завершиться между scrape.

Это не спор «OTel против Prometheus»: у OTel есть Prometheus exporter для pull, Prometheus умеет принимать OTLP/HTTP при включённом receiver. VictoriaMetrics поддерживает push и scrape. Способ доставки не определяет единственный SDK или бэкенд.

**Pushgateway** подходит некоторым сервисным batch-задачам: задание пишет результат в шлюз, Prometheus опрашивает шлюз. Это не универсальный OTLP-приёмник; устаревшими рядами нужно управлять. [Когда использовать Pushgateway](https://prometheus.io/docs/practices/pushing/).

### Альтернатива: сбор stdout и файлов агентом

Другой путь сбора:

```text
Приложение → структурированные JSON-логи в stdout или файл
           → агент: filelog / tail → хранилище логов
```

Здесь приложение пишет записи, а агент читает доступный ему поток или файлы и отправляет данные дальше. Это концептуальная схема со слайда 52, не дополнительный настроенный маршрут нашего стенда. Чтение файла не следует приравнивать к Prometheus pull/scrape.

Для корреляции Trace ID и Span ID нужно явно включить в JSON или добавить через инструментирование. Один `slog.NewJSONHandler` не извлекает эти идентификаторы из контекста автоматически. Мост и Logs SDK позволяют работать с OTel log record напрямую; сбор агентом позволяет принимать уже существующие журналы. [Модель работы с логами OTel](https://opentelemetry.io/docs/specs/otel/logs/).

### Фактический путь на стенде

```text
Трейсы:  Go SDK ── OTLP/HTTP push ──→ Collector ──→ Jaeger
Метрики: Go SDK ── OTLP/HTTP push ──→ Collector ←── scrape ── Prometheus
Логи:    slog → otelslog → Logs SDK ── OTLP/HTTP ──→ Collector ──→ Loki
                         └── stdout-exporter ──→ терминал

Просмотр: Grafana обращается к Prometheus, Jaeger и Loki
Связь: запись Loki в Grafana ── View trace ──→ трейс Jaeger в Grafana
```

Стрелка scrape показывает запрос Prometheus к Collector; данные возвращаются в ответе. Приложение экспортирует метрики раз в пять секунд, Prometheus опрашивает Collector тоже раз в пять секунд. Интервалы независимы, новая точка появляется не мгновенно.

Стенд смешанный: push от приложения, pull на последнем участке метрик. `up=1` у Collector означает успешный scrape Collector, не доступность сервиса заказов и не свежесть его измерений.

В материалах занятия используется последняя версия `tripgoctl`; подготовка описана в [README примера](../example/README.md). Логи отправляет само приложение, Collector не читает stdout процессов на хосте. Grafana здесь служит интерфейсом к хранилищам, не хранилищем самих сигналов.

Вне локального стенда нужны защищённая сеть, аутентификация и ограничения нагрузки для обоих способов доставки. Операции приложения не должны бесконтрольно ждать восстановления телеметрии.

## 12. Итог и переход к практике

```text
Метрика → отклонение → алерт
Трейс + лог → исследование причины
SLI → SLO → бюджет ошибок
```

Проверяем понимание:

1. Кто начинает соединение на каждом участке пути метрик? SDK отправляет в Collector, Prometheus опрашивает Collector.
2. Почему `RecordError`, `SetStatus` и контекстный лог не заменяют друг друга? Они записывают событие ошибки, отмечают статус спана и описывают событие в журнале.
3. Что входит в знаменатель быстрого успеха? Все допустимые завершённые попытки, включая ошибки и медленные успехи.
4. Почему алерт не обязательно приходит через две минуты после начала сбоя? Нарушение сначала обнаруживается на оценке; затем действуют pending, маршрутизация и доставка.

На [практике](../practice/README.md) запускаем готовые сервисы, создаём непрерывную нагрузку и сравниваем задержку, отказ и тайм-аут по трём сигналам. Импорт дашборда, команды, критерии сдачи и порядок остановки находятся там и в [README примера](../example/README.md). Код уже инструментирован; собственный спан, метрика или панель остаются дополнительным заданием. Настройку алертов не требуем.

## 13. Для самостоятельного чтения

### Происхождение OpenTelemetry

До OTel общие подходы развивали OpenTracing и OpenCensus. Первый предоставлял общий API трассировки, второй развивал библиотеки для трассировок и метрик. В 2019 году проекты объявили об объединении в OpenTelemetry, в том числе из-за стоимости поддержки двух похожих, но несовместимых подходов. [История объединения](https://www.cncf.io/blog/2019/05/21/a-brief-history-of-opentelemetry-so-far/).

### Экспоненциальные гистограммы

У **OTel ExponentialHistogram** границы задаются геометрической сеткой вместо ручного списка. При `scale=0` пример границ: `… 0.125, 0.25, 0.5, 1, 2, 4 …`. Чем выше `scale`, тем плотнее сетка и выше разрешение. Это позволяет покрыть широкий диапазон значений с контролируемой относительной погрешностью.

SDK может уменьшать разрешение, объединяя соседние бакеты, чтобы уложиться в лимит их числа. Это уменьшает детализацию. Гистограмма всё равно хранит агрегаты, не все исходные длительности.

Инструмент в бизнес-коде остаётся Histogram с вызовом `Record`; представление выбирается настройкой агрегации SDK. Экспоненциальная сетка не гарантирует границу ровно 800 мс, поэтому доля до произвольного порога может требовать оценки. На практике оставляем явные бакеты, чтобы разобрать показатель без этой дополнительной погрешности. [Модель ExponentialHistogram](https://opentelemetry.io/docs/specs/otel/metrics/data-model/#exponentialhistogram).

### Prometheus и VictoriaMetrics

Здесь сравниваем именно бэкенды метрик; для логов и трейсов на стенде другие получатели.

| Свойство | Prometheus | VictoriaMetrics |
| --- | --- | --- |
| Роль | Сбор, локальная TSDB, запросы и вычисление правил | Хранилище и запросы; сбор и правила могут выполнять `vmagent` и `vmalert` |
| Push-приём | OTLP/HTTP при включённом `--web.enable-otlp-receiver`; есть и другие пути приёма | OTLP/HTTP Protobuf, Prometheus remote write и другие протоколы |
| Pull | Встроенный scrape и service discovery | Scrape в single-node варианте или через `vmagent` |
| Развёртывание | Локальная TSDB одного узла; встроенного распределённого хранилища нет | Single-node или кластер с `vminsert`, `vmstorage`, `vmselect` |
| Масштабирование хранения | Дополнительные экземпляры и/или внешнее хранилище; local TSDB сама не становится кластером | Кластер распределяет запись, хранение и запросы; репликацию настраивают отдельно |
| Язык запросов | PromQL | MetricsQL с поддержкой привычных PromQL-выражений и отличиями семантики |

Prometheus сам хранит метрики, не ограничиваясь ролью сборщика. VictoriaMetrics не требует обязательного кластера. Выбор зависит от объёма рядов, срока хранения, нагрузки запросов, требований к отказоустойчивости и возможностей команды. Обещание «всегда быстрее и дешевле» без измерений ничего не решает.

OTLP/HTTP receiver Prometheus принимает метрики на `/api/v1/otlp/v1/metrics`, если его явно включить. В single-node VictoriaMetrics путь приёма `/opentelemetry/v1/metrics`; в кластере используется адрес и маршрут `vminsert` для нужного tenant. Это альтернативы для проектирования, не адреса нашего Collector. Публично открывать незащищённый endpoint приёма нельзя.

Источники: [Prometheus как OTLP-бэкенд](https://prometheus.io/docs/guides/opentelemetry/), [локальное хранение Prometheus](https://prometheus.io/docs/prometheus/latest/storage/), [OTLP в VictoriaMetrics](https://docs.victoriametrics.com/victoriametrics/integrations/opentelemetry/), [кластер VictoriaMetrics](https://docs.victoriametrics.com/victoriametrics/cluster-victoriametrics/), [`vmagent`](https://docs.victoriametrics.com/victoriametrics/vmagent/).

### PromQL и MetricsQL

PromQL — язык вычислений над временными рядами, не формат хранения и не протокол приёма. MetricsQL развивает похожую модель: selectors, `rate`, `sum`, `histogram_quantile` и другие знакомые конструкции.

Одинаковое выражение не всегда означает одинаковый результат:

- PromQL `rate` и `increase` работают с точками внутри окна и экстраполируют результат к его границам.
- MetricsQL учитывает последнюю точку перед окном и не делает такую экстраполяцию. На редких событиях и границах окна значения могут отличаться.
- MetricsQL допускает дополнительные конструкции, например `WITH`, и может автоматически выбирать окно для `rate`, если оно опущено. Для учебных показателей оставляем явное `[5m]`.

При миграции проверяем типичный и редкий трафик, пропуски и перезапуски. Различия не сводятся к гистограммам. [Документация MetricsQL](https://docs.victoriametrics.com/victoriametrics/metricsql/).

VictoriaMetrics при OTLP-приёме по умолчанию сохраняет OTel-имена; Prometheus-совместимое именование включается настройкой. Правила переноса Resource attributes в метки тоже различаются. Запрос с `exported_job` из нашего scrape-стенда нельзя просто перенести в прямой OTLP-приём и ожидать те же ряды.

### Представления гистограмм и запросы

| Представление | Как выглядит после приёма | Что сохраняем при агрегации |
| --- | --- | --- |
| Классическая гистограмма Prometheus | Накопительные ряды `_bucket{le="..."}`, `_count`, `_sum` | `le` |
| Prometheus native histogram | Составной histogram sample в каждой точке ряда | Саму гистограмму; `le` не нужен |
| Гистограмма VictoriaMetrics | Ряды интервалов с меткой `vmrange` | `vmrange` |

OTLP receiver Prometheus преобразует OTel ExponentialHistogram в native histogram. VictoriaMetrics преобразует его в собственный формат с `vmrange`. Это разные представления схожего распределения, не два названия одного wire-формата. У native histograms есть вариант с пользовательскими границами; слово native не означает только экспоненциальную сетку.

Поддержку проверяют по конкретным версиям SDK, exporter, Collector, хранилища и интерфейса. Поддержка OTLP в целом не доказывает прохождение нужного типа гистограммы через любой маршрут. [Prometheus native histograms и OTLP](https://prometheus.io/docs/specs/native_histograms/#otlp), [ExponentialHistogram в VictoriaMetrics](https://docs.victoriametrics.com/victoriametrics/integrations/opentelemetry/#exponential-histograms).

Имена ниже условные и **не существуют в нашей лабораторной**. Предполагаем накопительные гистограммы одной операции с совместимыми бакетами; в реальной системе добавляем фильтры сервиса и окружения.

PromQL для native histogram получает составные histogram samples, без `le` и суффикса `_bucket`:

```promql
histogram_quantile(0.99, sum(rate(request_duration_seconds[5m])))
```

MetricsQL для преобразованных интервалов VictoriaMetrics:

```metricsql
histogram_quantile(0.99, sum by (vmrange) (rate(request_duration_seconds_bucket[5m])))
```

MetricsQL умеет считать квантили и по классическим бакетам `le`; тогда сохраняем `le`, как в лабораторных запросах. При объединении гистограмм в VictoriaMetrics проверяем одинаковые наборы границ. Совместимость языка не делает несовместимые распределения совместимыми.

Экспоненциальная сетка не отменяет погрешность квантиля и доли до порога внутри бакета. Для точного учёта хороших событий по заданной границе нужен соответствующий явный бакет или отдельный счётчик таких событий.

Источники: [`histogram_quantile` в PromQL](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile), [`histogram_quantile` в MetricsQL](https://docs.victoriametrics.com/victoriametrics/metricsql/#histogram_quantile).

### За пределами учебного стенда

У Collector pipeline состоит из receiver, processors и exporters. Для production отдельно настраивают лимиты памяти, ограниченные очереди, повторные отправки, доступ и наблюдение за самим Collector. Доставка телеметрии не должна бесконтрольно задерживать пользовательские запросы. Наличие Collector не обещает сохранение данных после любой аварии.

**Head sampling** принимает решение в начале трейса, когда ещё неизвестен результат. **Tail sampling** принимает решение после получения спанов, например отдаёт приоритет медленным или ошибочным операциям. Ему нужны буферизация и согласованная доставка спанов одного трейса; отброшенные ранее данные он не восстановит. Пользовательский SLI не считаем простым подсчётом произвольно отобранных трейсов. [Сэмплирование OTel](https://opentelemetry.io/docs/concepts/sampling/).

Для ресурсов полезен **USE**: Utilization — занятость, Saturation — ожидающая работа, Errors — ошибки. У пула соединений смотрим занятые соединения и ожидание, у очереди — длину и возраст старого сообщения. Сопоставляем эти данные с пользовательскими SLI.

Кроме Grafana-managed alerting существуют правила Prometheus и `vmalert` в экосистеме VictoriaMetrics. Alertmanager маршрутизирует и группирует уведомления; эти роли не следует смешивать с вычислением условия. Потерю телеметрии проверяем отдельно от доли ошибок.

После инцидента фиксируем влияние, временную шкалу, причины, пробелы в измерениях и проверяемые задачи. Наблюдаемость помогает найти задержку, но медленный запрос или отказ зависимости всё равно нужно исправить.
