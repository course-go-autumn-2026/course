# Практика: найдите сбой по метрикам, трейсам и логам

**Время: 90 минут.** Вы запустите два Go-сервиса, создадите поток запросов и исследуете их работу в Grafana. Код уже инструментирован: писать SDK bootstrap, бизнес-логику или собственный генератор нагрузки не требуется.

## Сценарий

Сервис заказов принимает `POST /orders` и резервирует курьера через второй сервис. Нормальный результат — `201`. Отказ курьеров или тайм-аут — `503`.

Ваша задача — объяснить три разных неисправности: медленное подтверждение, быстрый отказ и превышение тайм-аута. Для каждого случая найдите изменения на графике, нужный спан и связанный лог.

Все три сигнала смотрим в **Grafana: <http://localhost:22300>**:

| Сигнал | Источник | Что искать |
| --- | --- | --- |
| Метрики | Prometheus | Частоту операций, успешность, p95/p99 и долю быстрого успеха |
| Трейсы | Jaeger | Оба сервиса в одном трейсе, длительность и статус спанов |
| Логи | Loki | Результат операции, режим курьеров, причину ошибки и идентификаторы |

## До занятия

Установите зависимости и **последнюю версию `tripgoctl`**, проверьте Docker и скачайте образы по [README примера](../example/README.md#подготовка-до-занятия). Первичная установка не входит в 90 минут практики.

Все команды ниже выполняйте из общего проекта [`../example/`](../example/). Исходники доступны для чтения: [заказы](../example/orders/orders.go), [курьеры](../example/couriers/couriers.go), [настройка OTel](../example/telemetry/telemetry.go).

## План работы

| Минуты | Задача |
| --- | --- |
| 0–15 | Запустить окружение и сервисы, импортировать дашборд |
| 15–30 | Создать нагрузку и найти три сигнала нормального запроса |
| 30–60 | Сравнить задержку, отказ и тайм-аут |
| 60–80 | Разобрать проблемный запрос по трейсу и логам, проверить восстановление |
| 80–90 | Сохранить результаты и остановить сервисы |

## 1. Запустите сервисы

```sh
make infra-up
```

В двух отдельных терминалах:

```sh
make run-couriers
```

```sh
make run-orders
```

В третьем терминале проверьте готовность:

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8081/health
```

Оба запроса должны вернуть `204`. Импортируйте готовый дашборд:

```sh
make dashboard
```

Откройте [«Заказы: метрики, трейсы и логи»](http://localhost:22300/d/food-observability). Если Grafana вернула HTTP `409`/`412`, дашборд уже существует: используйте его. `make dashboard OVERWRITE=true` явно заменяет его содержимым [dashboard.json](../example/dashboard.json), включая ваши изменения панелей. Ручной импорт через **Dashboards → New → Import** также доступен.

**Контрольная точка:** оба сервиса отвечают, Grafana открывается, в списке источников есть Prometheus, Jaeger и Loki. Пустые графики до нагрузки допустимы.

## 2. Найдите нормальный запрос

Дождитесь первых измерений метрик, затем запустите нагрузку:

```sh
make mode MODE=normal
make load RPS=100
```

Нагрузка идёт непрерывно до `Ctrl+C`. Оставьте её работать, а режимы переключайте из свободного терминала. В логах генератора видны номера запросов, HTTP-коды, длительности, счётчики и фактический RPS.

1. На дашборде найдите частоту завершённых заказов, успешность и длительность. Прочитайте единицы и окно расчёта каждой панели.
2. Через ссылку **«Трейсы (Jaeger)»** вверху дашборда или **Explore → Jaeger** выберите **Query type → Search**, сервис `order-service` и последние 15 минут. Нажмите **Run query**.
3. Раскройте трейс. Найдите входящий серверный спан, `orders.create`, исходящий HTTP-вызов и серверный спан `courier-service`.
4. Скопируйте Trace ID. В **Explore → Loki** переключитесь в **Code**, вставьте запрос и нажмите **Run query**:

   ```logql
   {service_name=~"order-service|courier-service"} | trace_id="ВСТАВЬТЕ_TRACE_ID"
   ```

5. Найдите события `order completed` и `courier reserved`. Trace ID должен совпасть, Span ID — различаться: логи относятся к разным операциям.
6. Раскройте лог и нажмите **TraceID → View trace**. Вы должны попасть в тот же трейс, не выходя из Grafana.

Если запись только что появилась, подождите несколько секунд: экспорт логов и спанов выполняется независимо. Не используйте `server started` для проверки корреляции: этот лог записан вне спана.

**Контрольная точка:** вы нашли один запрос в обоих сервисах и умеете перейти из лога к его трейсу.

## 3. Прочитайте четыре панели

| Панель | Вопрос для проверки понимания |
| --- | --- |
| Завершённые заказы в секунду | Почему накопленный Counter нельзя показывать вместо `rate`? |
| Успешные заказы | Какие попытки входят в знаменатель? |
| p95 / p99 длительности | Почему это оценки, а не точные длительности отдельных запросов? |
| Успешные заказы ≤ 800 мс | Почему быстрая ошибка не улучшает этот показатель? |

Запросы доступны в редакторе панелей и в [queries.json](../example/queries.json). Попробуйте найти в них фильтр сервиса, окно `[5m]`, атрибут результата и границу `le="0.8"`.

Цели 99,9% и 99% на дашборде учебные, с окном **пять минут**. По этому прогону нельзя подтвердить месячный SLO из лекции.

## 4. Включите неисправности

При работающем `make load RPS=100` переключайте режимы курьеров из свободного терминала. Между режимами сохраните наблюдения и время переключения.

| Команда | Ожидаемый результат | Что проверить |
| --- | --- | --- |
| `make mode MODE=slow` | `201`, резервирование около 1,2 с | Медленный успешный спан; ухудшение быстрого успеха без роста ошибок |
| `make mode MODE=error` | Быстрый `503` | Ошибочный спан, причина в логе курьеров, падение успешности |
| `make mode MODE=timeout` | `503` примерно через 2 с | Тайм-аут HTTP-клиента заказов и отмена запроса у курьеров |
| `make mode MODE=normal` | Снова `201`, резервирование около 20 мс | Новые успешные запросы и начало восстановления графиков |

Режимы уже реализованы. Не меняйте бизнес-код ради нужной картинки и не открывайте управляющие endpoints в общую сеть.

Запишите для каждого сбоя:

- время и выбранный режим;
- HTTP-код и заметное изменение панелей;
- Trace ID одного характерного запроса;
- какой спан указывает на проблему и какой лог уточняет причину.

Учитывайте особенности измерений:

- Метрики экспортируются и опрашиваются раз в пять секунд. Для `rate` нужны хотя бы две точки.
- Старые ошибки остаются в пятиминутном окне после восстановления. График не обязан исправиться мгновенно.
- Генератор отправляет запросы параллельно с целевыми 100 RPS. При медленных ответах растёт число активных запросов; фактический темп проверяйте по `actual_rps` в логах. Это не измерение предельной производительности.
- Быстрые ошибки могут снизить p95: ухудшение результата не обязано увеличивать длительность.
- Перцентили оцениваются по бакетам. Тайм-аут чуть больше 2 с попадает в бакет `(2; 5]`: оценка p99 может оказаться близкой к 5 с. Точное время отдельного запроса ищите в трейсе.
- Нет трафика — доля успеха не определена. Только ошибки при наличии трафика — 0%, а не отсутствие ряда. Для чистой серии учитывайте всё пятиминутное окно.

## 5. Разберите один проблемный запрос

Начните с логов неуспешных заказов:

```logql
{service_name="order-service"} | outcome="error"
```

Выберите запись, перейдите по **View trace** и объясните путь запроса. Затем найдите логи обоих сервисов по Trace ID. Сопоставьте `span_id` каждой записи с конкретным спаном.

Для `error` ожидается явный отказ курьеров. Для `timeout` сервис заказов перестаёт ждать через две секунды, хотя искусственная задержка курьеров задана в три секунды; контекст исходящего запроса отменяется. Найдите подтверждение этой разницы в трейсе и логах.

`trace_id`, `span_id` и `outcome` приходят из OTel как structured metadata. `| json` для этих запросов не нужен. Не превращайте идентификаторы в индексные labels Loki или метки метрик.

**Контрольная точка:** вы объяснили причину конкретного неуспеха с помощью обоих сервисов, а не только показали красную панель.

## Если чего-то не видно

- **Нет Loki:** проверьте `tripgoctl version`; после обновления CLI повторите `make infra-up`.
- **Нет данных:** проверьте ответы `/health`, поток запросов, ошибки экспорта в терминалах и выбранный период Grafana.
- **Виден только `trip-service`:** запускайте сервисы через Makefile; он переопределяет общее имя из `.env` для каждого процесса.
- **Логи есть в терминале, но нет в Grafana:** stdout не доказывает доставку в Loki. Проверьте OTLP-адрес и ошибки экспорта.
- **View trace ничего не находит:** подождите экспорта спана и проверьте, не перезапускался ли Jaeger. Он хранит трейсы в памяти, а Loki сохраняет логи на PVC.
- **Панель пустая:** проверьте имена метрик, фильтры, достаточное число точек и наличие трафика. Доля при нулевом знаменателе намеренно не показывается.

Успешный scrape Collector (`up=1`) не подтверждает, что приложение отправляет свежие измерения.

## Что сдать

1. Скриншот дашборда с периодом нормальной работы и неисправностей.
2. Короткую таблицу наблюдений для `slow`, `error`, `timeout` и восстановления.
3. Trace ID проблемного запроса, скриншот его спанов и связанные логи обоих сервисов.
4. Объяснение знаменателя успешности и причины, по которой быстрый отказ может снизить p95.

Работа готова, если оба сервиса видны в одном трейсе, переход из лога работает, различия трёх сбоев объяснены, а нормальный режим восстановлен. Экспортируйте JSON дашборда, если меняли панели.

Сначала остановите нагрузку через `Ctrl+C`, затем сервисы и выполните `make infra-down`. Для завершения работы не нужны `environment reset` или удаление кластера.

## Дополнительно: собственное инструментирование

Если обязательная часть закончена, выберите одно небольшое расширение:

- добавьте в лог полезное поле с ограниченным набором значений и найдите записи по нему;
- создайте дочерний спан вокруг выбранного этапа и передайте его контекст в выполняемую операцию;
- добавьте собственную метрику или панель, например сравнение длительности успешных и ошибочных заказов.

Объясните, на какой новый вопрос отвечает изменение. Сохраняйте исходные сигналы, учитывайте операции по одному разу и не помещайте идентификаторы запросов в метрики. SDK и инфраструктуру менять не требуется. Расчёт стоимости доставки в обязательном примере не реализуется.
