# Два Go-сервиса с OpenTelemetry

Готовый пример для [лекции](../lecture/README.md) и [практики](../practice/README.md): запускаем сервисы, создаём поток запросов и исследуем метрики, трейсы и логи в Grafana. Дописывать Go-код для обязательной части не нужно.

`POST /orders` без параметров создаёт фиксированный учебный заказ. Если курьер подтвердил резервирование, сервис заказов отвечает `201`; при ошибке или тайм-ауте зависимости — `503`. Базы данных, оплаты и гарантий физической доставки в примере нет.

## Схема

```text
Бизнес-запросы, локальные процессы:

load.sh ── POST /orders ──► order-service :8080
                                  │
                                  │ POST /reserve + traceparent
                                  ▼
                           courier-service :8081

Телеметрия, стек tripgoctl:

order-service ───┐
                ├── traces, metrics, logs ── OTLP/HTTP ──► Collector
courier-service ┘                                      localhost:22318
                                                           │
                                           ┌───────────────┤
                                           ▼               ▼
                                         Jaeger           Loki
                                        [трейсы]         [логи]

                          Prometheus ── scrape ──► Collector
                          [метрики] ◄── ответ ────

Grafana localhost:22300 ── запросы ──► Prometheus / Jaeger / Loki
                                      Jaeger ◄── View trace ── Loki
```

`telemetry` — Go-пакет внутри каждого процесса, а не сетевой сервис. Контекст передаётся с HTTP-запросом через `traceparent`; Collector получает телеметрию отдельно и не участвует в резервировании курьера. Стрелка scrape обозначает запрос Prometheus к Collector.

## Структура

```text
orders/main.go                  запуск заказов, HTTP-клиент, завершение SDK
orders/orders.go                обработчик, вызов курьеров, спаны и метрики
couriers/main.go                запуск курьеров, завершение SDK
couriers/couriers.go            резервирование и режимы неисправностей
telemetry/telemetry.go          три provider, exporters, Resource, propagation, slog
internal/httpserver/server.go   HTTP-сервер и graceful shutdown
Makefile                       сборка, запуск, нагрузка, режимы, проверки
load.sh                        сборка и запуск генератора нагрузки
load/main.go                   непрерывные параллельные POST-запросы
import-dashboard.sh            импорт дашборда через HTTP API Grafana
dashboard.json                 четыре готовые панели Grafana
queries.json                   PromQL тех же панелей
```

Один Go-модуль, два сервиса и генератор нагрузки. `telemetry.Setup(ctx, serviceName)` вызывается один раз в каждом сервисе и возвращает логгер, функцию завершения и ошибку. Пакет использует стандартные `OTEL_*`; `.env` загружает команда запуска. Прикладное инструментирование остаётся в сервисах и использует OTel API напрямую.

## Подготовка до занятия

Нужны Go ≥1.25, Docker, `make`, `curl` ≥7.76, POSIX shell и **последняя версия `tripgoctl`**. Документация и исходники — в [основной ветке `main` репозитория `course-infra`](https://github.com/course-go-autumn-2026/course-infra/tree/main).

Установка или обновление CLI до последнего релиза:

```sh
installer=$(mktemp)
curl --proto '=https' --proto-redir '=https' --tlsv1.2 -fsSL \
  https://github.com/course-go-autumn-2026/course-infra/releases/latest/download/install-tripgoctl \
  -o "$installer" && sh "$installer"
rm -f "$installer"
tripgoctl version
```

При желании перед выполнением разделите скачивание и запуск, чтобы прочитать скрипт. Установщик проверяет SHA-256 архива и сообщает каталог установки. Проверьте, что каталог есть в `PATH`, а версия в выводе `tripgoctl version` совпадает с указанной установщиком.

Дальнейшие команды выполняются из `example/`:

```sh
tripgoctl doctor
go mod download
make infra-up
make build
```

`infra-up` выполняет `tripgoctl cluster start`, `tripgoctl environment start` и `tripgoctl connect`. Первое скачивание образов может занять несколько минут. Профиль `lab = 2` содержит PostgreSQL, но приложения его не используют.

После обновления CLI `environment start` добавляет Loki и обновляет конфигурации существующего окружения. Сбрасывать окружение, менять `environment.toml` или OTLP-адрес для логов не нужно. Используйте только свой сгенерированный `.env`: запуск загружает его как shell-файл.

## Запуск готовой части

В первом терминале:

```sh
make run-couriers
```

Во втором:

```sh
make run-orders
```

Обе команды собирают бинарники, загружают `.env` и **после загрузки** задают разные `OTEL_SERVICE_NAME`: `courier-service` и `order-service`. Общее имя из `.env` не объединит сервисы. SDK сам файл не читает.

Проверка из третьего терминала:

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8081/health
```

Ожидается `204` от обоих сервисов. Health checks не входят в бизнес-метрики. Серверы слушают только loopback, управление учебными сбоями нельзя открывать в общую сеть.

При необходимости можно запускать бинарники напрямую: у обоих есть `-port`, у `bin/orders` ещё `-courier URL`. Например:

```sh
set -a; . ./.env; set +a
OTEL_SERVICE_NAME=order-service ./bin/orders -port 8090 -courier http://127.0.0.1:8081/reserve
```

## Генерация нагрузки

В третьем терминале:

```sh
make load                         # 5 RPS до Ctrl+C
make load RPS=200
make load URL=http://127.0.0.1:8090/orders RPS=100
```

`load.sh` собирает и запускает Go-генератор без дополнительных зависимостей. Он отправляет пустые `POST` параллельно, без лимита общего числа запросов. Прямой запуск: `sh load.sh [url] [rps]`. `Ctrl+C` или `SIGTERM` прекращает отправку, отменяет активные запросы и печатает итог.

Для каждого запроса видны время, порядковый номер, метод, URL, пустое тело, HTTP-код, длительность и результат. Раз в секунду выводятся накопленные `requests`, `completed`, `success`, `error`, `cancelled`, число активных запросов `in_flight` и фактический `actual_rps`. `requests` считает начатые попытки, а `actual_rps` — их частоту за время с предыдущей сводки; эти числа не гарантируют доставку до сервера.

HTTP `4xx`/`5xx`, сетевые ошибки и тайм-ауты не останавливают нагрузку. Тайм-аут отдельного запроса — четыре секунды. При медленных ответах растёт число одновременных запросов. `RPS` задаёт целевой темп: фактический зависит от ресурсов машины и скорости вывода логов. Это источник данных для графиков, не бенчмарк предельной производительности.

Короткая проверка нормального режима:

```sh
make mode MODE=normal
make load                         # проверьте status=201 и actual_rps, затем Ctrl+C
```

## Режимы неисправностей

Из свободного терминала во время нагрузки:

```sh
make mode MODE=slow
make mode MODE=error
make mode MODE=timeout
make mode MODE=normal
```

| Режим | Что делают курьеры | Результат заказа |
| --- | --- | --- |
| `normal` | Подтверждение через 20 мс | `201` |
| `slow` | Подтверждение через 1,2 с | `201`, но дольше 800 мс |
| `error` | Немедленный отказ | `503` |
| `timeout` | Ожидание до 3 с; клиент заказов отменяет запрос через 2 с | `503` примерно через 2 с |

Makefile вызывает готовый `POST /admin/mode/{mode}` на порту `8081`. Для нестандартного порта используйте `curl -X POST http://127.0.0.1:PORT/admin/mode/normal`.

## Метрики в Grafana

После `make infra-up` импортируйте готовый дашборд:

```sh
make dashboard
# Без Makefile, в том числе из другого каталога:
sh /путь/к/example/import-dashboard.sh
```

Скрипт отправляет соседний [`dashboard.json`](dashboard.json) в `POST /api/dashboards/db`. Нужны только shell и curl, без jq или Python. Используется анонимный Admin локального стенда. Сам скрипт окружение не поднимает и источники данных не создаёт.

Откройте [«Заказы: метрики, трейсы и логи»](http://localhost:22300/d/food-observability). Локальный доступ: `admin` / `admin`; разрешён и анонимный вход. Не публикуйте этот стенд в интернет.

По умолчанию существующий дашборд **не перезаписывается**: Grafana вернёт HTTP `409`/`412`, команда завершится с ошибкой. Откройте имеющуюся копию либо явно замените её содержимым файла:

```sh
make dashboard OVERWRITE=true
```

Перезапись заменяет и изменения, сделанные в интерфейсе Grafana. Для другого адреса:

```sh
make dashboard GRAFANA_URL=http://localhost:24300
# То же напрямую:
GRAFANA_URL=http://localhost:24300 sh import-dashboard.sh
```

По умолчанию используется `http://localhost:22300`, адрес профиля 2. Ошибки HTTP и соединения не скрываются. Ручной импорт через **Dashboards → New → Import** также остаётся доступен.

Источники `prometheus`, `jaeger` и `loki` подготовлены инфраструктурой. В дашборде четыре панели:

- частота завершённых операций;
- доля успешных операций и учебная цель 99,9%;
- p95 и p99 длительности;
- доля успешных операций не дольше 800 мс и учебная цель 99%.

Окно запросов — пять минут, диапазон дашборда по умолчанию — 15 минут. Экспорт метрик и scrape происходят раз в пять секунд, независимо друг от друга. Дождитесь первых точек до нагрузки; для `rate` нужны хотя бы две точки.

[`queries.json`](queries.json) содержит те же запросы. В этом стенде `job="otel-collector"`, сервис выбирается через `exported_job="tripgo/order-service"`. Фактические имена: `orders_attempts_total`, `orders_duration_seconds_bucket`, `_count`, `_sum`. Для диагностики можно открыть Prometheus на <http://localhost:22909>.

Считаются все завершённые операции `POST /orders`, включая ошибки. Знаменатель быстрого успеха включает **все** результаты, числитель — успешный бакет `le="0.8"`. Нет трафика — доля не определена; только ошибки — 0%. Короткий прогон не подтверждает месячный SLO. Перцентили оцениваются по бакетам: тайм-аут чуть больше 2 с попадает в бакет `(2; 5]`, поэтому оценка p99 может приблизиться к 5 с, хотя запросы столько не длились. Старые ошибки остаются в пятиминутном окне после восстановления. Collector может отдавать последние метрики после остановки приложения: `up=1` проверяет scrape, а не свежесть телеметрии приложения.

## Трейсы и логи в Grafana

Через ссылки вверху дашборда или **Explore** выберите источник **Jaeger**, переключите **Query type → Search**, выберите сервис `order-service`, подходящий период и нажмите **Run query**. В одном трейсе ожидаются четыре спана:

```text
POST /orders                  order-service
└─ orders.create              ручной бизнес-спан
   └─ HTTP POST               исходящий вызов
      └─ POST /reserve        courier-service
```

В **Explore → Loki** переключитесь в **Code**, вставьте один из запросов и нажмите **Run query**:

```logql
{service_name=~"order-service|courier-service"}
{service_name="order-service"} | outcome="error"
{service_name=~"order-service|courier-service"} | trace_id="ВСТАВЬТЕ_TRACE_ID"
```

Раскройте запись `order completed` или `reservation failed`: `TraceID → View trace` открывает связанный трейс в Grafana через источник Jaeger. Проверьте также `span_id`: логи разных сервисов относятся к разным спанам одного трейса. Обратный автоматический переход из трейса в логи не настроен; для него копируем Trace ID в запрос Loki.

`trace_id`, `span_id` и `outcome` приходят как structured metadata, поэтому `| json` здесь не требуется. Идентификаторы не становятся индексными labels Loki или метками метрик.

Логи идут по цепочке `slog → otelslog → Logs SDK → OTLP/HTTP → Collector → Loki`. Второй exporter сохраняет их в терминале для диагностики. Collector не читает stdout процессов на хосте. Лог запуска вне активного спана не имеет связи с трейсом. Записи и спаны отправляются пакетами, поэтому связь может появиться спустя несколько секунд.

Отдельный интерфейс Jaeger доступен на <http://localhost:22686>, но для задания достаточно Grafana.

## Остановка и проверки

Сначала остановите нагрузку через `Ctrl+C`, затем оба сервиса и выполните:

```sh
make infra-down
```

Обработчики завершаются до SDK; для последнего экспорта используется отдельный контекст с тайм-аутом. `infra-down` выполняет только `environment stop`, сохраняя PVC. **Не используйте `environment reset` и `cluster stop` для обычного завершения практики:** они удаляют данные. Экспортируйте свою копию дашборда отдельно. Loki сохраняет логи на PVC, Jaeger хранит трейсы в памяти и теряет их при перезапуске.

```sh
make check
```

Проверки с race detector отправляют три сигнала в локальный тестовый OTLP-приёмник и проверяют импорт дашборда на тестовом HTTP-сервере. Для SDK проверяются имя сервиса, счётчик и идентификаторы лога и спана; для импорта — содержимое JSON, защита от перезаписи, явное обновление и запуск из другого каталога. Для генератора проверяются темп 100 RPS на медленных ответах, логи и счётчики, продолжение после ошибок и отмена активных запросов. Docker не нужен. Затем запускается `go vet`.

Версии зависимостей закреплены: OTel `1.46.0`, Logs SDK/exporters `0.22.0`, `otelhttp` `0.71.0`, `otelslog` `0.20.1`. Сквозной прогон выполнен на Linux с Go `1.27.0` и `tripgoctl v0.1.0`: нормальный режим, задержка, ошибка, тайм-аут, счётчик и бакеты, запросы дашборда, логи двух сервисов и соответствующий трейс через API источников Grafana. Также проверены отсутствие трафика, серия только ошибок, завершение активного запроса при остановке и недоступность Collector. В браузере проверены четыре панели, поиск трейсов и переход `View trace` из лога. macOS отдельно не проверен.
