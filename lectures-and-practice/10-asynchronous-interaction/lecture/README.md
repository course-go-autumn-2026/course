# Асинхронное взаимодействие на Go

Лекция 10 · Конспект студентов

[Практика](../practice/README.md)

Kafka, consumer groups, гарантии доставки, retry и DLQ. Практика использует один контейнер Kafka и Go-процессы без базы данных.

## Заказ и доставка

При асинхронном взаимодействии обработка в другом сервисе не входит в критический путь ответа. Но продукт должен отличать состояние «заказ принят» от «доставка назначена». Пользователю нужен способ увидеть окончательный результат. Принятие публикации брокером ещё не говорит об успешной работе доставки. Сам вызов отправки в брокер при этом может синхронно ждать подтверждения.

## Когда полезна асинхронность

Например, уведомление и аналитика могут обработать факт создания заказа позже. Для немедленной проверки остатка или получения точного расчёта синхронный запрос часто проще. Асинхронность переносит часть сложности в состояние, повторы и наблюдение за задержкой. Она не ускоряет автоматически саму бизнес-операцию.

## Команда и событие

Команда выражает намерение и предполагает конкретного исполнителя. Событие фиксирует уже произошедший факт и может иметь независимых подписчиков. Название OrderCreated в прошедшем времени помогает не путать модели. Не стоит публиковать событие о факте, которого ещё нет в надёжном состоянии сервиса.

## Очередь и журнал

Это модели, а не строгая классификация всех возможностей продуктов. В Kafka обычные consumer groups независимо читают журнал, а retention управляет сроком хранения. У традиционной очереди подтверждение часто завершает жизненный цикл конкретной доставки. Kafka поддерживает и другие модели, но на занятии рассматриваем обычные consumer groups.

## Обзор брокеров

Обзор помогает выбрать модель, а не ранжировать продукты по качеству. RabbitMQ также имеет streams; Kafka не сводится к одной очереди; Core NATS и JetStream имеют разные свойства хранения и доставки. На практике используем Kafka, чтобы явно работать с offset и группами. Все продукты требуют настройки под конкретную нагрузку.

## Стенд занятия

Kafka в режиме KRaft совмещает роли broker и controller. Одна реплика удобна для локального занятия, но не защищает от потери единственного узла или диска. Go-клиенты работают на хосте через localhost:19092. Внутренний listener нужен проверке готовности контейнера. Обработчик только логирует результат: дедупликации и реального бизнес-эффекта здесь нет.

## Topic и partition

Topic — именованный поток. Он разбит на партиции, каждая хранит упорядоченные записи. Offset 12 в partition 0 и offset 12 в partition 1 — разные позиции. Нельзя сравнить эти числа и вывести глобальный порядок. Чтение события не удаляет его из журнала.
```
orders
  partition 0:  [10] [11] [12]
  partition 1:  [ 7] [ 8] [ 9]
  partition 2:  [21] [22] [23]
```

## Ключ сообщения

В kafka-go используем Hash balancer. При неизменном количестве партиций и алгоритме один ключ направляется в одну партицию. Изменение числа партиций может изменить распределение. Общий порядок разных ключей не обещается. Обработка одной партиции конкурентными горутинами тоже может разрушить порядок бизнес-эффектов.

## Consumer group

В обычной consumer group в устойчивом назначении одну партицию читает один участник. Один consumer может читать несколько партиций. Если участников больше, чем партиций, часть будет ждать без назначений. Новая группа читает тот же журнал независимо: это подходит для доставки и аналитики.
```
group delivery:   A → partitions 0, 1
                  B → partition 2

group analytics:  C → partitions 0, 1, 2
```

## Перебалансировка

При изменении состава группы происходит rebalance. Не связывайте владение партицией с вечным закреплением за конкретным процессом. После сбоя новый обработчик ориентируется на сохранённую позицию, а не на локальную память предыдущего. Долгая обработка и условия протокола группы требуют отдельного анализа в промышленной системе.

## Три разных подтверждения

Подтверждение записи Kafka, завершение пользовательского обработчика и commit offset — разные события. Commit меняет позицию группы, но не удаляет сообщение. Если обработчик выполняет внешний эффект, этот эффект и Kafka commit не становятся атомарными только потому, что находятся в одной функции. В стенде эффект представлен логом, поэтому повтор заметен, но ничего не списывает.

## Offset и commit

На уровне протокола сохраняется следующая позиция. В kafka-go в CommitMessages передают обработанный Message; библиотека сама выполняет нужное преобразование. Не прибавляйте единицу в структуре сообщения. Commit большего offset подтверждает и предыдущие позиции той же партиции, поэтому нельзя продолжать обработку и фиксировать более поздние сообщения поверх неразобранной ошибки.
```
fetch 42 → handle 42 → commit(message 42)

после рестарта: fetch 43

сбой до commit: 42 может прийти снова
```

## Контракт события

ID события и ID заказа имеют разные назначения. ID события нужен для дедупликации, order_id — идентификатор агрегата и ключ партиционирования. При повторной отправке payload и ID сохраняются. Изменение схемы должно учитывать старых читателей. В учебном контракте поддерживается только version=1 и одно событие создания на заказ.
```
{"id":"e-42", "order_id":"o-17",
 "address":"Центр", "version":1}
```

## Producer на Go

В полном примере перед этим вызывается Validate и проверяется json.Marshal. Writer переиспользуется и закрывается при завершении процесса. Async=false означает ожидание результата записи; асинхронность архитектуры относится к отдельной обработке события сервисом. RequireAll означает подтверждение всех текущих ISR, а не автоматически наличие нескольких реплик.
```
w := broker.Writer("orders.task1")
defer w.Close()
err := w.WriteMessages(ctx, kafka.Message{
    Key:   []byte(e.OrderID),
    Value: payload,
})
if err != nil { return err }
```

## Consumer на Go

Reader настроен с GroupID и CommitInterval=0. FetchMessage не фиксирует offset автоматически. ReadMessage при групповой работе делает автоматический commit и поэтому не подходит для выбранной гарантии. В практике цикл последователен и возвращает ошибку, если любой этап не выполнен.
```
m, err := r.FetchMessage(ctx)
if err != nil { return err }
if err := handle(ctx, m); err != nil {
    return err
}
return r.CommitMessages(ctx, m)
```

## Демонстрация обмена

На лекции используется решённый пример преподавателя. После задания 1 команды можно повторить в practice. Перед повтором демонстрации выбирайте новые ID и имя группы либо осознанно объясните повторное чтение старых событий. Покажите в логе key, partition и offset, затем запустите вторую независимую группу.
```
go run ./cmd/lab -mode=send -id=lec1 -order=lec1

go run ./cmd/lab -mode=consume -task=1 \
  -group=lecture10 -count=1
```

## Гарантии доставки

Всегда указывайте границу гарантии. At-most-once допускает потерю без повторной доставки; at-least-once допускает повторы при восстановлении; exactly-once относится к конкретной атомарной области. Commit до обработки оставляет окно потери работы, commit после обработки — окно повтора. Kafka-транзакции не включают произвольный внешний HTTP-вызов. Здесь используем ручной commit и демонстрируем повторную обработку; сквозную exactly-once не реализуем.

## Окно повторной обработки

После сбоя группа возвращается к сохранённой позиции и получает сообщение снова. В нашем обработчике повторится лог handled. Если вместо лога добавить отправку письма или списание денег, повтор может стать проблемой. Перестановка commit перед обработчиком лишь меняет дубль на риск потери. Поэтому отдельно обсуждаем идемпотентность, не реализуя её в этом стенде.
```
1. Прочитать событие e-42
2. Выполнить обработчик: handled e-42
3. Сбой процесса
4. Commit offset не выполнен
5. После рестарта снова e-42
```

## Идемпотентность обработчика

Идемпотентность означает одинаковый итоговый эффект при повторном выполнении операции. Присваивание значения обычно проще сделать идемпотентным, чем увеличение счётчика. Сам event_id ничего не предотвращает: получатель должен использовать его в подходящем механизме защиты. В учебном обработчике такой защиты нет. Мы наблюдаем дубли по логам и объясняем риск; реализация надёжного учёта обработанных ID не входит в занятие.

## Временная и постоянная ошибка

Неверная версия или повреждённый JSON не исправятся от короткой паузы. Временная ошибка может исчезнуть, но бесконечный повтор блокирует работу. Отмена контекста не доказывает, что событие неисправимо; её не отправляют в DLQ как плохие данные. Классификация зависит от продукта: недоступность БД нельзя автоматически считать ошибкой пользователя.

## Ограниченный retry

Во втором задании максимум три вызова обработчика: первая попытка и два повтора, паузы 100 и 200 мс. При исчерпании лимита ошибка возвращается без commit и цикл останавливается. Постоянная ошибка останавливает его сразу. После рестарта счётчик начинается заново. В третьем задании отдельно разбираем перенос в DLQ после одной попытки: это изолированный опыт с другой политикой. В рабочем сервисе retry и DLQ объединяют осознанно, задавая бюджет и классификацию ошибок.

## Dead letter queue

DLQ — отдельный Kafka topic, в который приложение помещает неуспешные сообщения для разбора. Сохраняем исходные topic, partition, offset, key/value, headers, число попыток и причину. Бинарные key/value отображаются в JSON как base64. У записи в DLQ есть и собственные partition/offset — не путайте их с позицией оригинала. Нужны ответственный за разбор, срок хранения и права доступа. Перенос в DLQ не означает успешной бизнес-обработки.

## Порядок действий при DLQ

Если запись в DLQ не подтверждена, исходный offset не фиксируем и возвращаем ошибку из цикла. Если DLQ записалась, но процесс умер до commit, в DLQ возможен дубль. Запись туда и исходный commit не атомарны в нашем решении. Оригинальная позиция помогает распознать такую повторную запись.
```
Handle: permanent error
    ↓
WriteMessages(DLQ): success
    ↓
CommitMessages(original)

DLQ unavailable → stop, no commit
```

## Порядок после проблемного события

Перенос неуспешного события в retry topic или DLQ меняет доступность и порядок обработки. Если событие «заказ изменён» требует успешного «заказ создан», слепо продолжать нельзя. В практике независимые события создания отдельных заказов, поэтому перенос допустим. Один последовательный цикл также временно задерживает другие назначенные ему партиции; масштабирование обработки здесь не реализуется.

## Демонстрация повтора

Команды выполняет преподаватель на решённом примере. После задания 2 студенты повторяют их у себя. Первый consumer завершится ошибкой после handled, до commit. Второй с той же группой снова обработает тот же event_id. Это доказательство повторной доставки, а не защиты от повторного бизнес-эффекта. Для каждого нового опыта используйте новый ID; учитывайте накопленную историю топика.
```
go run ./cmd/lab -mode=send -task=2 -id=lec2 -order=lec2
go run ./cmd/lab -mode=consume -task=2 \
  -group=lecture-retry -crash-before-commit
go run ./cmd/lab -mode=consume -task=2 \
  -group=lecture-retry
```

## Разбор записи DLQ

Сначала определите, почему событие не обработалось: ошибка данных, неподдерживаемая версия или исправимый дефект обработчика. Отметьте собственные координаты записи в DLQ. Внутри envelope лежит другая позиция — позиция оригинала. Для точечного replay CLI использует координаты DLQ. Изменение логики обработчика может позволить повторить неизменённый payload; испорченные данные сами не исправятся.

## Управляемая повторная отправка

Готовый инструмент читает ровно выбранную запись без consumer group и публикует исходные байты в разрешённый топик orders.task3. Он не удаляет DLQ и не фиксирует её offsets. Ошибку отправки возвращает вызывающему. Повторный запуск может отправить тот же факт ещё раз. Бесконечный автоматический replay не включён: он мог бы создать цикл source → DLQ → source.

## Демонстрация replay

Сначала отправьте событие в task3, обработайте с scenario=permanent и прочитайте DLQ отдельной группой. Затем выберите P/O из строки DLQ partition=... offset=... и подставьте числа. Повторный consumer запускается с той же исходной группой, но scenario=ok: так моделируем устранение причины. Event ID сохраняется, позиция в исходном топике новая. Этот сценарий студенты выполняют в задании 3.
```
go run ./cmd/lab -mode=dlq -group=lecture-dlq

# P и O — числа из заголовка DLQ
go run ./cmd/lab -mode=replay -partition=P -offset=O

go run ./cmd/lab -mode=consume -task=3 \
  -group=lecture-task3 -scenario=ok
```

## Порядок после replay

Сохранение key помогает попасть в ту же партицию при неизменных числе партиций и алгоритме. Но повторная публикация получает новый offset. Если последующие события зависят от пропущенного результата, простого replay недостаточно. На практике используем независимые события создания разных заказов, чтобы эксперимент не скрывал бизнес-зависимости.

## Ошибки повторной отправки

Сетевой тайм-аут не доказывает отсутствие записи: подтверждение могло потеряться. Если событие опубликовано, но CLI завершился до вывода результата, оператор тоже не знает результат наверняка. Стабильный ID позволяет связать попытки. В учебной реализации повтор не блокируется; студент должен понимать это ограничение и не утверждать exactly-once.

## Наблюдаемость

Lag показывает отставание группы в позициях, но не длительность ожидания каждого события. Нужны время обработки, возраст события и состояние DLQ. Снижение lag за счёт массового переноса в DLQ не означает восстановления бизнеса. Наблюдение за replay связывает исходный event ID, исходную позицию, координаты DLQ и новую публикацию.

## Границы стенда

Одна реплика не защищает от потери диска. Третий task использует одну попытку Handle, чтобы изолировать порядок DLQ/commit; retry изучен отдельно во втором. DLQ write и исходный commit не атомарны. История ограничена retention. Replay не удаляет DLQ и допускает повторную публикацию. Все эти ограничения явно отражены в приёмке.

## Основные термины

| Термин | Значение |
|---|---|
| Topic | Именованный поток, разбитый на партиции |
| Partition | Упорядоченная часть журнала |
| Key | Вход для выбора партиции |
| Offset | Позиция внутри одной партиции |
| Consumer group | Независимый подписчик с распределением партиций |
| Commit offset | Сохранение позиции группы для продолжения чтения |
| Event ID | Идентификатор факта, сохраняемый при повторе |
| DLQ | Поток сообщений, требующих отдельного разбора |
| Replay | Контролируемая повторная публикация сообщения |
